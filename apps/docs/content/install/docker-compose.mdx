title: "Install with Docker Compose"
description: "From a Linux machine with Docker to the panel's sign-in page, in about ten minutes."
summary: "One compose file brings up the server, Postgres and a pool runner."
---

## 1. Get the compose file

Download this release's compose file into an empty folder.

```sh run
mkdir ostra && cd ostra
curl -fsSLO https://github.com/JoeyKhd/ostra/releases/latest/download/compose.yaml
```

## 2. Start it

Docker pulls the images and starts three containers: Postgres, the server, and a pool runner on the `docker` executor. The server runs its migrations, creates the first admin and the first organization, and writes the default pool's join token to its data folder, where the runner reads it and registers.

```sh run
docker compose up -d
docker compose ps
```

> [!NOTE]
> The first start creates the admin `demo@demo.com` with the password `demo`. The panel asks for a new password at the first sign-in.

> [!WARNING]
> The pool runner mounts the Docker socket, which is root on this machine. Run pools on machines that do nothing else.

## 3. Check that it's up

Core answers on 8787 and the panel on 3000 once the migrations have run. These wait up to a minute for each.

```sh run
curl -fsS --retry 30 --retry-delay 2 --retry-all-errors http://localhost:8787/healthz
curl -fsS -o /dev/null --retry 30 --retry-delay 2 --retry-all-errors http://localhost:3000/sign-in
```

If either gives up, `docker compose logs server` says why. A server that can't start names the setting to fix.

## 4. Open the panel

Open `http://localhost:3000` and sign in as `demo`.

> [!CAUTION]
> A runner on the host executor runs agents in a worktree on its own machine. Its agent can reach whatever that account can.

The compose file's runner uses the `docker` executor, so each task runs in its own box. The `host` executor is what a [personal runner](/docs/runners/personal) on a laptop uses.

## Required settings

None. Every setting has a working default, listed in the [configuration reference](/docs/reference/configuration). The ones you're most likely to set:

| Setting | Default | Set it when |
|---|---|---|
| `OSTRA_PUBLIC_URL` | `http://localhost:3000` | People reach the panel at another address, such as `https://ostra.example.com`. |
| `OSTRA_CORE_PUBLIC_URL` | `http://localhost:8787` | Runners on other machines, or GitHub's and the trackers' webhooks, reach core at another address. |

To set any setting, write it in a `.env` file in the folder that holds `compose.yaml`, one `NAME=value` a line, then start or restart:

```sh
cat >> .env <<'EOF'
OSTRA_PUBLIC_URL=https://ostra.example.com
OSTRA_CORE_PUBLIC_URL=https://core.ostra.example.com
EOF
chmod 600 .env
docker compose up -d
```

Compose hands every line of `.env` to the server. The file is optional, and an upgrade, which replaces `compose.yaml`, leaves it as it is, so keep your settings there rather than in `compose.yaml`. The values `compose.yaml` sets itself, such as the database's address and the data folder, win over it. Put a value that holds a `$` in single quotes, or Compose reads it as a variable. A misspelt `OSTRA_` name stops the server at start, and `docker compose logs server` names it. Reading `.env` this way needs Docker Compose 2.24 or later.

Put a TLS-terminating proxy in front of both ports for an install others reach. Without a public address everything still works: GitHub and each tracker connection are read on a schedule instead of by webhook.

## Back up the data

Two Docker volumes hold everything: `postgres-data`, the database, and `server-data`, the server's generated keys. **Back up both.** The secrets key in `server-data` is the only way to read the provider tokens, GitHub keys and environment secrets the database holds; without it they are lost.
