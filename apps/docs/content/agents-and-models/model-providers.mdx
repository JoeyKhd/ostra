A model provider is an endpoint your organization adds for models: an API base URL and a token. ostra doesn't pick a vendor for you. A hosted API, a gateway in front of several of them, or a model server on your own network all work the same way.

## Add a provider

An organization admin adds one under **Models**, with **Add provider**.

1. Give it a **Name**, its **API base URL** and its **Token**.
2. Press **Test connection**. ostra calls the endpoint, detects its API format and lists the models it serves.
3. Pick the models you want, and **Save provider**.

The token goes to the secret store and is never shown again. Each provider is one key: an organization may hold several providers that serve the same models, one per client, and each project uses only the providers on its provider list.

> [!NOTE]
> A base URL that points at a private, loopback or link-local address is refused unless `OSTRA_MODEL_ENDPOINT_ALLOW_PRIVATE` is `true`. Cloud metadata hosts are always refused. See the [configuration reference](/docs/reference/configuration).

Two settings on a provider limit where it's used:

- **Sessions at once:** the most sessions that use this provider at the same time. Empty means no cap.
- **Allow on personal runners:** off by default. A personal runner is a member's own machine, and a key the key proxy holds there can be read by that member.

## API formats

ostra speaks two API formats, and the connection test detects which one the endpoint speaks.

| Format | What speaks it | How the token is sent |
|---|---|---|
| OpenAI-compatible | OpenAI's API, most gateways, and model servers such as vLLM and Ollama | `Authorization: Bearer` |
| Anthropic Messages | Anthropic's API, and gateways that offer its Messages API | `x-api-key` or `Authorization: Bearer` |

When the detection is wrong, correct the **API format** by hand. The agent never holds the token, in either format: it gets a base URL that points at the [key proxy](/docs/security/proxies) and a fake key for its one task.

## Models and prices

Names, context sizes, limits and prices come from the [models.dev](https://models.dev) catalog, which core fetches daily (`OSTRA_CATALOG_FETCH`; `false` uses the copy bundled with ostra). A model the catalog doesn't have is shown as **custom**: give it a name and its input and output prices per million tokens, so its spend can be counted.

An agent profile names its provider, then one of that provider's models by its model name. Its tasks use that provider's key and base URL alone, and only in projects whose list allows it: a project's list decides which profiles run there (see [Agent profiles](/docs/agents-and-models/agent-profiles)). For a profile saved before profiles named their provider, each project serves the model from exactly one provider on its list, and nothing but an organization admin's save moves it to another. No task ever falls back to another provider by itself.

Spend is counted at the key proxy, call by call, in four token kinds: fresh input, output, cache reads and cache writes, each priced on its own. See [Budgets](/docs/using-ostra/budgets).

## Images

A member's screenshot or a ticket's mock reaches the model as a picture only when the model reads images ([Attaching files](/docs/using-ostra/files#what-the-agent-gets)). ostra knows it from the catalog's list of the model's inputs, kept on the model at every sync. Each model on the provider's page shows what the catalog says, and has **Reads images**: an organization admin turns it on or off for a custom model, or for an endpoint that differs from the catalog, and clears it to follow the catalog again. The admin's word wins, a sync never undoes it, and each change is in the audit log.

A model nothing is known of counts as one that can't see images: its images go to the agent as files, and the message box says so before sending. ostra also tells the agent which inputs its model takes, so OpenCode, for one, shows the model the images its read tool opens.
