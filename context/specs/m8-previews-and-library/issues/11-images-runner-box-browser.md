# 11: Images and runner: the box's browser

Builder: runner

Spec: `../spec.md`, sections 5.2, 6 and 11; ADR 0068 ("The box's browser")

## What to build

- **The base image:** Debian bookworm's `chromium` package, at a pinned version, in the runtime stage, and its fonts (`fonts-liberation`, `fonts-noto-color-emoji`) so pages render text and emoji.
  - `pnpm check:images` checks the pin, and the notices list Chromium's licences (F-039, milestone 7's ticket 29).
  - Record the image's size before and after under `## Comments`, for ticket 34.
- **The init** (`docker` and `kubernetes`): the bridge's browser request of ticket 03, for real.
  - Start `chromium --headless=new --remote-debugging-pipe` as the agent's user, with a fresh profile in a temporary folder, `--no-first-run`, `--no-default-browser-check`, `--disable-sync`, no extensions, and no sandbox flag beyond what the container needs. Write down what Chromium's own sandbox needs in a container, and why.
  - Hand the pipe over the bridge's own channel.
  - Report `app.browser` once per box.
  - Remove the profile when the box ends.
- **The `host` process host:**
  - find a browser in the order ADR 0068 gives: `OSTRA_RUNNER_BROWSER`, then Chrome, Chromium and Edge in each OS's usual places;
  - else download Chrome for Testing's `chrome-headless-shell` at the version pinned in the runner's release, check its SHA-256 against the pin, and keep it in the runner's data folder;
  - `OSTRA_RUNNER_BROWSER_DOWNLOAD=false` skips the download and reports no browser, with the fix in the panel's words;
  - start the browser in the task's containment unit with the same flags.
- **ostra's DevTools client** in `apps/runner/src/browser/`, ported from spike 07: it opens a target, navigates, captures, screencasts with acks, dispatches input, and closes the target, over the pipe. It has a deadline on every call and refuses a reply it can't parse (Zod, tolerant of the protocol's unknown fields, since it's Chromium's format). It never passes a page's content to a log line.
- **"No browser in this box":** an organization's own base image without Chromium, or a `host` runner with none and the download off, reports `{ available: false, reason }`. The tools return that reason, and the environment page warns (ticket 17).

## Comments

- 2026-11-21, runner: `✨ add the box's browser`. What it holds:
  - **The base image** (`deploy/Dockerfile.base`): `chromium` and `chromium-common` at Debian bookworm-security's `156.0.8078.79-1~deb12u1`, with `fonts-liberation` and `fonts-noto-color-emoji`, in a layer of their own, `--no-install-recommends`. bookworm-security keeps only its newest Chromium, so a build whose pin has been superseded adds Debian's snapshot archive at `20261120T000000Z` (signed by the image's own archive keyring, checked to serve this version) for those two packages, and removes it after. The pin lives in `packages/deploy-checks/src/chromium.ts`, and `pnpm check:images` (rule `chromium-pin`) holds the Dockerfile's two package versions, the fonts, the snapshot line and `deploy/notices/chromium.json` to it. THIRD_PARTY_NOTICES lists `chromium@156.0.8078.79-1~deb12u1` under BSD-3-Clause with Chromium's own license text, which points to Debian's `/usr/share/doc/chromium/copyright` in the image for the components Chromium bundles (the slim image keeps copyright files). The catalog's extra is now checked by name, since the base image has two.
  - **The image's size, for ticket 34.** No Docker here, so estimated from Debian's indexes, not measured: bookworm's, bookworm-updates' and bookworm-security's amd64 `Packages.xz` (deb.debian.org, read 2026-11-21), the Depends and Pre-Depends closure without Recommends, against the runtime stage's other packages and the required set. **Chromium adds 165 Debian packages: about 703 MiB unpacked (their `Installed-Size`) and 204 MiB of `.deb` downloads**, about what the layer adds compressed. Before, the runtime stage's Debian packages come to about 521 MiB unpacked (183 packages), beside Node, OpenCode and the init's install. The largest additions: `chromium` 283 MiB, Mesa's `libllvm15` 112 MiB (software rendering, through `libgl1-mesa-dri`), `chromium-common` 65 MiB, `libicu72` 35 MiB, GTK 3 with its icon theme about 56 MiB, the emoji font 10.5 MiB. The slim image's dpkg rules drop docs and manuals, so the unpacked layer comes out somewhat smaller. *The measured before and after (`image-sizes` in `live-docker`) wait for the launch-gate Proof run.*
  - **The init** (`docker` and `kubernetes`): the image's Chromium with `CONTAINER_BROWSER_FLAGS`, `--no-sandbox` and `--disable-dev-shm-usage`, and nothing else (`init/box-browser-flags.ts`, cited there; ADR 0068 amended). **Chromium's own sandbox in a container:** it needs an unprivileged user namespace or its setuid helper to make each renderer's PID and network namespaces, and refuses to start without one. Docker's default seccomp profile and containerd's `RuntimeDefault` refuse `clone` with any namespace flag (`CLONE_NEWUSER` included) and `unshare` without `CAP_SYS_ADMIN`, which the box drops, and `no-new-privileges` / `allowPrivilegeEscalation: false` void a setuid helper. Granting either would loosen the box for the agent's shell too, and a renderer that escaped would only be the agent's user in the agent's container, which the shell already is: the box is the sandbox. `/dev/shm` is 64 MiB in a container, so the shared memory goes in `/tmp`. The profile's `HOME`, `XDG_CONFIG_HOME` and `XDG_CACHE_HOME` are the profile itself, in `/tmp`: writable in a pod with a read-only root, whose `/tmp` is already an in-memory volume (`pod.ts`), and gone with the profile. Every box's browser also gets `--password-store=basic` and `--use-mock-keychain` (`boxBrowserFlags`), so a `host` box's browser never touches the member's keychain.
  - **`app.browser` once per box** is `apps/runner/src/browser/box-browser.ts`'s holder: the browser starts on first use, never with the box, is reported once (its name and version, or the reason), is started again for the next caller after it dies without a second report, and ends with the box. Tickets 13 and 18 open it; nothing sends the event before them.
  - **`host`** (`adapter-executor-host`): `resolveMachineBrowser` takes `OSTRA_RUNNER_BROWSER` (a path that names no file is `not-found`, never a download), then Chrome, Chromium and Edge in each system's usual places, then Chrome for Testing's `chrome-headless-shell` **158.0.8127.36**, its zip per platform (linux64, linux-arm64, mac-arm64, mac-x64, win64; Windows on Arm has Edge) checked against the SHA-256 pinned in `headless-shell.ts` before it's unpacked, and kept in `<data folder>/browser/`. The sums were taken from the zips themselves here, each download's MD5 matching the bucket's `x-goog-hash`. The zip is read by ostra's own reader (`zip-extract.ts`: stored and deflated entries, executable modes, nothing outside its folder, no links or ZIP64), since Node reads none and `unzip` isn't on every Linux. The download happens when a box first wants a browser, never at start; a failure is tried again by the next box. `OSTRA_RUNNER_BROWSER_DOWNLOAD=false` with no browser is `download-off`, and the runner says so at start in `noBrowserWords`' words (`packages/protocol`, for the tools of ticket 13 and the environment page of ticket 17). The pinned shell was downloaded, checked, unpacked and run here once through the live test (`Chrome Headless Shell 158.0.8127.36`, a screenshot of the fixture app).
  - **A `host` pool's browser** runs as the agent's user through `sudo -n -C 5 -u <user> --`, which keeps its pipe on fds 3 and 4; the sudoers rule gains `closefrom_override` (`docs/configuration.md`, the pools page, `scripts/live/host-pool.sh`), and its profile is made and removed as that user. Without the flag, sudo refuses and the box reports `failed-to-start`. *Its live case (`host-executor.live.test.ts`) waits for the launch-gate Proof run.*
  - **ostra's DevTools client** (`apps/runner/src/browser/devtools-client.ts`, `page.ts`, ported from spike 07): a deadline on every call, every message checked with Zod (tolerant of unknown fields), a reply of another shape refused as `unparsable`, Chromium's own error words kept in `detail` and out of the message, no logging; a page opened as a target with a flat session, navigated to its load event, evaluated, captured (full page optional, capped), screencast with each frame acked once its reader is done (so ticket 18 holds the ack to cap the rate), given mouse, key and pasted text, and closed.
  - **The live jobs:** neither can run the whole executor suite in a container (it needs the sidecar's container on the box network), so each runs its browser case where the image's Chromium is: `init/browser-probe.ts`, the real init over the real bridge with this probe as the sidecar, in the base image under the agent container's hardening and a small box's size (`docker run` in `live-docker`; a pod with `pod.ts`'s security context, a read-only root and the in-memory `/tmp` in `live-kind`), starting an app process and the browser as the agent's user, loading the page at `localhost`, taking a PNG and checking the profile is gone. `live-docker` also prints the installed versions, the fonts and the notices' Chromium line. The probe's own test runs it here with the fake browser, and it ran once by hand against Edge through the real init with the container flags. *Their runs wait for the launch-gate Proof run.*
  - **Left open:** the runner's `hello` and `status` don't carry `browser` yet (no ticket names it; the runner says at start what it found); `OSTRA_BOX_BROWSER` isn't a setting, so an organization's own image needs its Chromium at `/usr/bin/chromium`, else its boxes report `not-in-image`.
  - **Checks:** typecheck and lint of `packages/protocol`, `packages/adapter-sdk`, the three executors, `apps/runner` and `packages/deploy-checks` (and the typecheck of `adapter-opencode` and `adapter-github`, which build on them); their tests; `pnpm check:images`.
