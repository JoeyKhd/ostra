## What to build

- **Starting them.** On `start_app`, the after-turn screenshots, a preview opened, or `app.start`, the runner starts the spec's app processes that aren't running, in the list's order:
  - through the init on `docker` and `kubernetes`, and in the containment unit on `host`;
  - from the command as an argument array (`sh -c <command>` only because the command is the project's own line, in the repo's folder, never with ticket or agent text in it);
  - with the repo's variables and secrets as the setup script gets them;
  - with `OSTRA_APP_<NAME>_URL` and `OSTRA_SERVICE_<NAME>_URL` from `appAddresses` (ticket 05).
- **Ready.** Each process's ready check, every 2 s for at most 120 s: an HTTP `GET` of the path answering below 500, a command exiting 0, or the port accepting a connection. Then `app.process ready`.
- **Logs.** Each process's output goes to `.ostra/app/<name>.log` in the task's config folder, never in a repo, capped at 4 MiB with the oldest lines dropped *(working value)*. A process that exits sends `exited` (code 0 after `stop`) or `failed` with its exit code, its last 64 KiB as an `app-log` blob, and a reason in ostra's words. The log's text is never in a log line.
- **Stopping.** `app.stop`, and the box's end, stop them with their trees.
- **A port already taken** (the agent ran its own dev server on the primary's port): the start reports `failed` with "port 5173 is already in use in this box", and the tool's result tells the agent to stop its own or announce it with `show_preview`.
- **Announced previews.** `show_preview` checks the port against `mayReach` (ticket 05) and the limit, adds it to the task's previews, and sends `preview.list`. The runner sends `preview.list` at box start with the declared ones too.
- **`dispatch.purpose: "app"`:** the box starts as for a reopen (the snapshot, the branches, the hidden ref), runs the setup, starts the processes, and launches no agent and no driver session. A turn on the same lease later launches the agent and restores its session from the archive (ADR 0039).
- **Services as previews:** a service with a preview label is listed in `preview.list`, reached by its name on `docker` and at `localhost` on `kubernetes`. A `host` runner never gets one (ADR 0029's first difference).

## Comments

- 2026-11-21, runner: committed as `✨ run the app's processes in the box`, on tickets 01, 03, 05 and 14, rebased over 11, 15, 19 and 23. What it holds:
  - **The box's app** (`apps/runner/src/task-host/app-processes.ts`), the same code on every executor. Nothing starts until something asks: `start_app`, `app.start` and "Start the app" now; the after-turn screenshots (13) and an opened view (18) call the same `start`. The processes that aren't running start in the list's order, each after the one before is ready or failed, one start at a time. Each runs as `<setup shell> -lc <command>`, the protocol's words in `taskSpecAppProcessSchema`, with the setup shell as a check runs (`OSTRA_RUNNER_SHELL`; on Windows Git for Windows' bash, through `resolveSetupShell`, now exported by the host adapter), in its repo's folder. Its environment is the setup script's: the runner's base variables (`baseEnv`), the repo's variables and secrets the setup gets (`availableDuringSetup`; the rest stay in the env file), then `appAddresses`, last, so no repo variable stands in for them.
  - **Ready** every 2 s for at most 120 s: an HTTP `GET` with `Host: localhost:<port>` answering below 500, the command exiting 0 (`runAgentCommand`, as the agent's user), or the port taking a connection. On `docker` the forwarder takes every connection itself, so the port check (and the taken-port check) is asked inside the box with bash's own `/dev/tcp`: a fixed script, with the port as its argument.
  - **States** follow the domain's lifecycle (ticket 05), so core's fold takes them: `starting`, then `ready` or `failed`; then `exited` (on its own, whatever its code) or `stopped` (`app.stop`, the box's end). `failed` and `exited` name the log's last 64 KiB as an `app-log` blob; `stopped` names none. A taken port is `failed` with the new reason `port-in-use` (`appProcessReasonSchema`, additive: minor 7 hadn't shipped and nothing switched over it), and `start_app`'s answer says to stop the agent's own server or show it with `show_preview` (`appProcessReasonText`; `startAppProcessResultSchema` gains `reason` and `exitCode`, and its `logPath` takes a full path, up to 1 KiB).
  - **Stopping:** the processes stop before the box's own stop, each `box-stopped`. A stop whose exit doesn't come within the grace and 10 s goes up anyway, and `HostExecutor`'s own end of the app has the same bound, so a box's stop never hangs on an app whose output stays open. The local init showed it on Windows under load; part of it was the bridge below.
  - **The bridge** (the coordinator's find, from the F-143/c2 race): `spawnApp` forgot a proc at its `exit`, which Node can report before the child's output ends, so a late `out` or `eof` was dropped and the app's `exited` hung. A proc is now forgotten once its exit and both `eof`s are in, whatever their order (`bridge/bridge-app-frames.test.ts`, with the frames reordered).
  - **The commands and tools:** `app.start` is accepted at once and starts once the box is ready; `unknown-process` and `no-app-processes` are refused once the spec is read. `app.stop` stops what runs. The sidecar's MCP server serves `start_app` and `show_preview` for the `app` set (ticket 13 adds `take_screenshot` and `record_app`); the fake agent gains `start-app` and `show-preview` scripts.
  - **Previews:** `previewTargets`, `mayReach` and `appAddresses` moved from the domain into the protocol (`task/previews.ts`): the runner may not import the domain (the license line), and both sides must apply one rule. The domain re-exports them unchanged, with `fixedReservedPorts`. Ticket 14's `inBoxServiceAddress` and a new `boxPortRefusal` (below 1024, a reserved port by name, the fixed 7101) live there too. `show_preview` refuses the box's own ports by name or number (the key proxy, the git proxy, ostra's MCP server, the profile's MCP proxy, the bridge on `docker` and `kubernetes`), then a second primary and the limit, adds the port and sends `preview.list`. The list goes up at the box's start when it holds anything. A service with a preview label is listed on `docker` and `kubernetes`, never on `host`.
  - **The log's path** (ticket 14's question): the log is `.ostra/app/<name>.log` in the task's folder, and the agent works in a repo's checkout below it, where that relative path names another folder.
