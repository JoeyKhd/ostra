## What to build

Ported from spike 08.
- **`preview.open` in `tunnel` mode:** open the preview connection, and serve one HTTP/2 connection on it, with the sidecar (on `host`, the runner) as the server, `enableConnectProtocol` on, from Node's own `http2` over the WebSocket's duplex stream.
- **Three kinds of stream:**
  - a plain request (the native preview's) forwarded to the preview's port as HTTP/1.1, with the request's headers as core rewrote them;
  - an extended CONNECT (`:protocol: websocket`) bridged to a WebSocket upgrade on the port;
  - a plain `CONNECT` (`ostra preview`'s) bridged to a raw TCP connection to the port.
- **Reaching the port:**
  - `docker`: the init's forwarder (ticket 03), opened on demand per port and closed with the view;
  - `kubernetes`: the pod's `localhost`, trying IPv6 and IPv4;
  - `host`: `localhost`, the same way. Spike 08 found Vite and webpack-dev-server on `::1` only, which `127.0.0.1` misses (ADR 0068, amended 2026-11-21).

  A service's preview is reached by its name on `docker` and at `localhost` on `kubernetes`.
- **The reach rule,** checked on every stream: `mayReach` against the task's previews and the reserved ports. A stream to anything else is answered 403 or refused with `RST_STREAM`.
- **Back-pressure:** HTTP/2's per-stream windows, and the WebSocket's `bufferedAmount` for the connection. A stream that stalls never stalls the others past HTTP/2's own head-of-line limit. Spike 08's numbers are written under `## Comments`.
- **The HTTP carrier:** no tunnel. `preview.open` with `tunnel` on it is refused with the reason, and `hello` says `tunnel: false`.

## Comments

- 2026-11-21, runner (ticket 22): built as `✨ carry previews over an HTTP/2 tunnel`, on tickets 03, 12, 19 and 23. What it holds:
  - **The box's side of a tunnel view,** the same code on every executor (in the sidecar on `docker` and `kubernetes`, in the runner on `host`): `connection/preview-connection.ts` opens `/runner/v1/preview?view=&leaseEpoch=` with `ostra-preview-tunnel.v1` and the link's own token (the box's task token, or the `host` runner's), through the environment's proxy as the session's socket, and reads a stale epoch, core's refusal and a network failure apart; `task-host/preview-tunnel.ts` serves HTTP/2 on it (`enableConnectProtocol`) with spike 08's three kinds of stream, each raw pair joined with `spliceStreams`; `task-host/preview-views.ts` holds the box's open views. `TaskRun.previewOpen` and `previewClose` and the task host's handlers drive them; `preview.open` in `stream` mode answers `stream-not-supported` until ticket 18.
  - **A finding the fake box hid:** core speaks first. Its HTTP/2 client opens the moment it takes the upgrade, so its preface comes right behind the 101, and a reader attached a few promise turns after `open` missed it: the box's session failed with `ERR_HTTP2_ERROR` and sent GOAWAY 2. The connection now comes paused and the tunnel's reader resumes it (`preview-tunnel.test.ts` opens it against an endpoint that speaks first, as core's does). The box's own WebSocket duplex (`webSocketDuplex`) never terminates the socket when the session goes, unlike `ws`'s `createWebSocketStream`, so its close code (1000, 1001) reaches core.
  - **The reach rule on every stream:** `AppProcesses.reach` (`mayReach` against the task's previews and the box's ports by name, and every port the box listens on for the task), then the way to the port: opened on the view's first stream to it and closed with the view, through `executor.reachAppPort` (the init's forwarder on `docker`, `localhost` on `kubernetes` and `host`), and a service by its name on `docker`'s box network. A refused stream is answered 403 before anything is dialled; core's own refusal of a CLI's other ports comes first (ticket 23). A stream to an app process that is getting ready waits for it (`AppProcesses.settled`, up to the ready check's 120 s): the view's open starts what isn't running, so `ostra preview`'s first request is the page, not a 502.
  - **`hostRewrite` off, for ticket 25:** the protocol gains `previewTunnel.portHeader` (`ostra-target-port`, spike 08's), additive. With it, the `:authority` is the preview's own host and goes to the app as `Host`, and the port is the header's; without it, the `:authority` is `localhost:<port>`. The box removes the header and checks the port as any other.
  - **The idle hold and the report** (ticket 19's note on ticket 18, which a tunnel view needs as much): the run's three idle timers go through `idleAfter`, held while a view is open and fired once the last one closes; every executor's runner reports `RUNNER_PREVIEW_SUPPORT`, `{ stream: false, tunnel: true }`, which ticket 18 turns `stream` on in. A comment on ticket 18 says where they are.
  - **The HTTP carrier:** the connection itself reports `tunnel: false` in `hello` and `status` on the HTTP carrier, and refuses a `preview.open` in `tunnel` mode before any handler, `tunnel-needs-websocket` (`peer.ts`), since only it knows which carrier brought the command. A box's sidecar is always on the WebSocket.
  - **Back-pressure and spike 08's numbers:** the spike carried 2 MiB answers whole at Node's default windows, three at once with 50 WebSocket echoes and 20 requests in 539 ms, and added about 30 ms to a cold Vite load on loopback (105 ms against 75 ms, medians of 8). The box advertises a 1 MiB window per stream and 16 MiB for the connection *(working values)*, and the WebSocket's send callbacks hold the session's writes. A 4 MiB answer nobody reads holds its own stream, and the next request on the tunnel is answered (`preview-tunnel.test.ts`).
  - **Tests:** `apps/core/src/previews/runner-tunnel.test.ts` is core's real tunnel code (ticket 23's CLI endpoint, hub and bridge) against the runner's real side (`createPreviewViews` and `openPreviewConnection`, exported from `@ostra/runner`), on `host` with the fixture's real Vite and API: `F-143/c2` (the page, `/api`, the API's WebSocket echo open while requests go, Vite's HMR socket and an edit's message, the runner's view ending when the CLI goes), `F-143/c3` (the API's port, the key proxy's and port 80 refused 403 by the runner on the box's session, and the runner's 403 reaching the CLI once the box's list drops the ticket's port), `F-144/c1,c5` (a plain request and an extended CONNECT to Vite's HMR, an edit's message on it), and `F-143/c6` (the runner's real connection against core's real gateway: on HTTP `Runner.preview` is `{ stream: false, tunnel: false }` and a tunnel `preview.open` is acked `rejected` `tunnel-needs-websocket` without reaching a handler; on the WebSocket `tunnel: true`, and it's handed on). `apps/runner/src/task-host/preview-tunnel.{host,docker,kubernetes}.test.ts` run one case list through the whole task host (`testing/preview-tunnel-cases.ts`, the fake core in `testing/fake-preview-core.ts`): `F-143/c2, F-144/c1,c5` (the open starts the API and Vite; CONNECTs with an HTTP request and a WebSocket at once, `/api`, HMR; plain requests, `hostRewrite` off by the port header, and the extended CONNECT with an edit's message; the subprotocol, the token and the epoch), `F-143/c3` (an unlisted port where something listens, the key proxy's, 22, 80 and 1023, each as a CONNECT, a request and an extended CONNECT, 403 with nothing dialled; a view of another key refused at its open), `F-141/c5` (the box past its idle timer while a view is open, ending once the last closes; a view core closes holds nothing) and `F-143/c2` (`preview.close` ends the connection with 1000; on `docker` the view's forwarder, opened once for many streams, is closed with it). On `host` live with this machine's bash; on `docker` and `kubernetes`, `DockerExecutor` through the real bridge to a local init. `preview-tunnel.test.ts` covers the server on its own (the port header, a stalled stream, a refusal, the close code, a stale epoch). The F-141 key follows that row's sentences as the runner's earlier tests do (c5, the warm box); core's `previews.test.ts` numbers the same sentence c4.
