## What to build

The interfaces and the fakes that tickets 11, 12, 13, 18 and 22 build on. The init is the same program on `docker` and `kubernetes`, and the `host` executor's process host offers the same operations in the runner's own process.

- **The init's bridge protocol** (`adapter-executor-docker/src/bridge/`, shared with `kubernetes`), new requests:
  - **A process with a log:** start a long-running process from an argument array in a folder, with variables, its stdout and stderr to a log file in the task's config folder; report its exit with the code; stop it. It runs as the agent's user, as every process the init starts.
  - **The browser:** start Chromium with `--remote-debugging-pipe`, `--headless=new`, a fresh profile in a temporary folder, and no first-run or sync, and hand the caller the pipe as its own channel on the bridge, so frames never wait behind control. Report `{ name, version }`, or `{ available: false, reason }` when the image has none.
  - **A forward** (`docker`): listen on the box network at a port the init picks, accept only the sidecar's address, and dial `localhost:<port>` for each connection, trying IPv6 and IPv4 (a dev server told `localhost` may listen on `::1` only, spike 08).
- **The `host` executor's process host:** the same three. Processes run in the task's containment unit (ADR 0029), and the browser is a process there too. `host` doesn't forward: the runner reaches `localhost` itself, IPv6 and IPv4.
- **`ExecutorAdapter` capabilities, new:** `boxBrowser: "image" | "machine"` and `appReach: "forwarder" | "loopback"`. `docker` declares `image` and `forwarder`, `kubernetes` `image` and `loopback`, and `host` `machine` and `loopback`.
- **The fakes:** the fake Docker engine and the fake Kubernetes API (milestone 5) answer the new bridge requests with a fake process, a fake browser that speaks enough of the DevTools protocol over the pipe (`Target.createTarget`, `Page.navigate`, `Page.captureScreenshot`, `Page.startScreencast` with acks, `Input.*`), and a forward to a fake listener.
- **The fixture app** every later ticket tests against, `e2e/m8-previews-and-library/fixtures/test-web/` (spec section 9): a Vite and React frontend whose `server.proxy` sends `/api` to a small Node API on 3001, a docs page on 4000, a page that sends `X-Frame-Options: DENY`, a page that builds a URL from `Host`, a WebSocket echo, and a counter button. It's a private workspace package that uses only versions already in `pnpm-lock.yaml` (Vite through Vitest, React from `apps/web`). If it needs anything new, stop and ask first, with its ADR 0007 line drafted. A Next.js 16 page for the native preview's tests sits beside it, on the `next` already in the lock.
- **The executor contract suite** gains, on each executor:
  - a process started, ready, logged and stopped with the box;
  - a crashed process reported with its exit code;
  - the browser started, a page loaded at the app's `localhost` and a screenshot taken;
  - a forward to an app port (`docker`), and one to a reserved port refused;
  - the browser's profile folder gone after the box ends.

  It runs against the fakes here, live on `host`, and live in the `live-docker` and `live-kind` jobs when they run.
- **The agent contract suite:**
  - the `app` tools listed for a task whose spec has `"app"`, and absent otherwise;
  - a scripted fake that calls `take_screenshot` gets the tool's result;
  - a new scripted fake without `mcp`, whose task still gets the after-turn screenshots.
- **The parity test** gains the rows of spec section 6's first table.

## Comments

- 2026-11-21, adapters: the contract went first, on its own, as `✨ add the box's app contract to the adapter SDK` (`de0427d7`), and ticket 14 built on it; the rest is `✨ add box processes, browser and forward`. Spike 08 landed while this was built, so the box's app is dialled at `localhost`, IPv6 and IPv4 (`dialApp`), never `127.0.0.1`, and a forward joins its ends with `spliceStreams`, never `stream.pipeline`; this ticket's own forward line says so now. What it holds:
  - **`ExecutorAdapter`** (`packages/adapter-sdk/src/executor/app.ts`, `base.ts`): `startAppProcess`, `stopAppProcess`, `startBrowser` and `reachAppPort`, each `unsupported` until an executor has it, and the capabilities `boxBrowser` and `appReach` (`docker`: `image`, `forwarder`; `kubernetes`: `image`, `loopback`; `host`: `machine`, `loopback`). `reachAppPort` is the base class's: it refuses a port below 1024 or one of the box's own (`portRefusal`, in `portRefusalWords`' words) before anything else, the same on every executor, then answers `localhost` or opens the init's forwarder (`openForward`).
  - **The log** is written on the executor's side from the process's output: by the sidecar on the task volume (`docker`, `kubernetes`) and by the runner (`host`), at `.ostra/app/<name>.log` in the task's folder, never in a repo, afresh at each start and capped at `APP_LOG_MAX_BYTES` (4 MiB) with the oldest lines dropped (`openAppLog`, ticket 12's working value). So the init, which is root, never writes into a folder the agent controls, and the same code runs everywhere. The handle's `exited` resolves once the output is in the file.
  - **The bridge** (`bridge/protocol.ts`): `app_spawn` and `app_stop` (no stdin, a process group of its own, a polite signal then the tree after the grace), `browser_start`, `browser_in` and `browser_kill` with `browser_started`, `browser_unavailable`, `browser_out` and `browser_gone`, and `forward_open` and `forward_close` with `forward_opened`. The init handles them as they come, outside its queue of stdio and control frames, so a frame never waits behind a reap's reply; the pipe's bytes cross in 64 KiB chunks. **Versions:** the pool runner names the features its sidecar reads in the init's `OSTRA_BRIDGE_FEATURES` (`boxes.ts`, `pod.ts`), and the init's hello lists those it has too. A snapshot whose init predates them gets none of the new frames: an app process is refused ("rebuild the environment's snapshot"), and the browser is `not-in-image`. An older sidecar never gets the hello's new field.
  - **The browser:** the init starts `OSTRA_BOX_BROWSER` (default `/usr/bin/chromium`, which ticket 11 puts in the image) with `boxBrowserFlags` (`--headless=new`, `--remote-debugging-pipe`, a fresh profile, no first run, sync, extensions or crash reporter, software rendering), as the agent's user, with the profile made and removed as that user. On `host`, `HostExecutorOptions.browser` names the program, which ticket 11 finds; without one a box reports `not-found`. The profile goes when the browser ends, however it ends, retried while its helpers hold files (spike 07). The name and version come from DevTools' own `Browser.getVersion` (`identifyBrowser`, `browserIdentity`), through IDs above 2,000,000,000, which a caller's client stays below.
  - **The forwarder:** the init listens on the bridge's local address (the box network) at a port it picks, takes connections from the bridge's remote address (the sidecar's) only, dials `localhost:<port>` over both families, and refuses a port below 1024 itself. `DockerExecutor` takes `appReach`, so a pod's sidecar can say `loopback`; the kubernetes suite does. `run-sidecar.ts` still builds it with the default (`forwarder`), which works in a pod too, through one more hop: ticket 12 or 22 passes `loopback` there.
  - **The fakes:** the fake Docker Engine and the fake cluster run no container, so, as milestone 5's suites do, the box's init is the real one, a local process the bridge drives; its browser is the fake box browser (`adapter-sdk/src/testing/fake-browser/main.ts`, through `adapter-executor-docker/src/testing/init-with-fake-browser.ts`). It speaks `Browser.getVersion` and `close`, `Target.createTarget`, `attachToTarget` and `closeTarget`, `Page.navigate` (a real HTTP fetch, so a page loads only when the app answers), `Runtime.evaluate` of the title, `Page.captureScreenshot` as a real PNG, `Page.startScreencast` with `maxFramesInFlight` and acks, and `Input.*`. Ticket 11's runner tests can start it too (`fakeBrowserProgram`).
  - **The executor suite's six cases,** passing on the `docker` and `kubernetes` fakes and live on `host` here with Edge 157: `F-140/c5,c12` (a process from its argument array, its variables, its log outside the workspace, ready through `reachAppPort`, stopped with the box), `F-140/c5` (a crash's exit code and its output), `F-121/c2,c8` (the browser with a fresh profile, a page loaded at the app's `localhost`, its title read, a PNG, its name and version), `F-121` (no browser and no profile after the box ends), `F-143/c2` (two connections at once through the reach) and `F-143/c3, F-141/c4` (below 1024 and each reserved name refused, on every executor, the tiny one too). The suite's app is an HTTP server on `localhost`, which listens on `::1` here, so the IPv6 dial is exercised. On a Linux CI machine the `host` suite runs the fake browser over the same pipe, unless `OSTRA_RUNNER_BROWSER` names one. The forwarder has its own cases (`init/forward.test.ts`): a 2 MiB answer whole, a connection from `127.0.0.2` refused before the app sees it, the init's own refusal of port 22, and an init without the features sent nothing it would refuse.
