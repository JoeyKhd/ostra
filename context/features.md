# Feature ledger

Every feature we've decided on, with a checkable "done when". It is the source of truth for what to build and what is finished.

- **Priority:** `v1` (in the first release), `later`, `won't`.
- **Status:** `planned` → `building` → `done`, or `dropped`.
- **Rules:**
  - IDs are permanent: never renumber or reuse one. New features get the next free ID.
  - Change a status in the same commit as the work. Set `done` only when every condition in "done when" holds.
  - Specs in `context/specs/` name the feature IDs they cover.
  - A row that waits on an open question names it (`Q-nn` in `open-questions.md`). Its priority isn't final until that question is settled.
  - *(working value)* marks a number we expect to tune; changing it doesn't need a new ID.
  - The plan was signed off on 2026-11-17. A change to a v1 row's "done when" from then on is agreed with the maintainer and noted in the row.
  - `build-order.md` puts every v1 row in a milestone. A row names its milestone only where that matters to its "done when".
- **The rework of 2026-11-18.** The maintainer delegated every open question, and `history/answers-2026-11-18.md` answers them (section 4.3 for this ledger). Rows it changed carry a dated note naming the questions behind the change. Rows it added say "Added 2026-11-18". Two adjustments the maintainer made afterwards override that file: Claude Code (F-018) stays v1, in milestone 7, and signed runner downloads (F-085) come after v1.
- **Count:** 132 rows. 104 are v1 and 28 are later. The next free ID is F-134.
- Terms follow `context/GLOSSARY.md`.

Using a reset link signs out the account's other sessions. Only the roles `admin` and `member` exist: an invitation for any other role, `owner` included, is refused (ADR 0026). ## Runners and boxes

| ID | Feature | Done when | Priority | Status |
|---|---|---|---|---|
| F-013 | Runner | The runner is `ostra runner`, from the npm CLI or the runner image (ADR 0046). A pool runner joins with its pool's join token (F-091), and a personal runner signs in with a device code that the member approves in the browser. It connects out over a WebSocket, so it works behind NAT. When a proxy blocks the WebSocket, it falls back to HTTP by itself within 30 seconds *(working value)*. It reconnects on its own. It reports its executor, capacity, labels and version, and the panel shows each runner's state (ADR 0029, ADR 0034). A personal runner uses the device code's session once: it trades it at once for its own runner key, and the server revokes the session, so the runner can connect and receive its dispatches and can do nothing else a member can (ADR 0029, ADR 0034, Q115). The CLI needs Node 24.5 or later (ADR 0046). *Changed 2026-11-18: the `ostra` CLI, join tokens and device codes instead of a one-time code, and the HTTP fallback (Q80, Q94). Changed again 2026-11-18 after spike 9: the runner-only key (Q115).* | v1 | planned |
| F-014 | Personal runner | A member runs `ostra runner` on their own machine, on the `host` executor. It runs only that member's tasks, in worktrees, and the panel labels it "personal, not isolated". The member picks it when they start a task. Its tasks use an organization's model provider only when an admin allows that provider on personal runners, which is off by default. No subscription login is used, stored or passed on (ADR 0030). When a task ends, nothing it started is left running: the runner puts each task's processes in a Windows job object or a Linux cgroup and ends it with the task (ADR 0029). On macOS the runner reaps the agent's process tree and the panel says detached processes may not be contained, until Q126 is settled. *Changed 2026-11-18: renamed from "Local runner", on provider keys instead of the member's own agent logins (Q44, Q47). | F-015 | Pool runners | An admin runs pool runners on servers, VMs or a cluster, and every project allowed on the pool can dispatch to them. A pool runner only creates and removes boxes. Credentials reach only the sidecar, for one task, and are never saved on the host. A pool may use the `host` executor when an admin opts in, with the agent as a separate OS user, and the panel labels that pool "not isolated" (ADR 0029, ADR 0030). *Changed 2026-11-18: renamed from "Remote runner", and built on boxes and sidecars (Q32, Q38, Q27, Q44).* | v1 | planned |
| F-091 | Runner pools and join tokens | An organization admin creates named pools, and each project lists the pools it may use. A join token is shown once, stored hashed, and expires after 30 days by default *(working value)*. An admin can set another lifetime or none, and can revoke it. Rotating a token doesn't disconnect runners that already joined, and each runner can be revoked on its own. A pool can require an admin to approve each new runner. | F-017 | A box per task | On the `docker` executor, each task gets its own box: the agent's container, the sidecar and the environment's services, on a private network of their own. A box serves one task and is never reused for another. | F-090 | Git proxy | The agent's own `git` clones, fetches and pushes through a proxy in the sidecar, which adds a token for one repo. It refuses every ref except the task's branches and its hidden ref, so a push to the default branch, a delete or a push to another repo is refused before a byte reaches GitHub. No GitHub token is ever in the agent's container. A refine or review task's proxy accepts fetches only. After every turn, the box commits what's left and pushes the task's branches (ADR 0030, Q26, Q41, Q66). What spike 4 settled on GitHub is part of "done": a refused push gets git's own `remote rejected` line with a reason, and a plain 403 only when the client asked for no report; every upstream request carries a `User-Agent`; the proxy rewrites LFS batch answers so signed URLs and headers never reach the agent, drops actions that point outside the upstream or the allowed hosts, and answers an object with a refused action with a per-object error and no actions; a refine or review task's proxy refuses the receive-pack advertisement, LFS uploads, LFS lock checks and every non-GET LFS action, and tests exercise those LFS branches; the server narrows every token it mints to one repo and the permissions the step needs; a refused push costs at most a 1 GiB upload to the sidecar (Q123); refusal messages are worded by status and by where the refusal came from, and the log keeps the upstream's reason without the body. The configuration reference has one line per code host for the hosts its LFS actions may call (GitHub.com: `github-cloud.githubusercontent.com`, `github-cloud.s3.amazonaws.com` and `lfs.github.com`; a GitHub Enterprise Server install lists its own storage host), and says that LFS objects of a cleaned-up task stay in the code host's storage (Q119, Q120). *Added 2026-11-18. Changed 2026-11-18 after spike 4.* | v1 | planned |
| F-116 | Egress baseline | No box can reach a private address range, the cloud metadata address or another box. It's a network policy on `kubernetes` and host rules on `docker`, and a test from a shell in the agent's container proves each one. The `host` executor can't enforce it, which is why its pools are labelled "not isolated" (ADR 0031, round 14). *Added 2026-11-18.* | v1 | planned |
| F-052 | Network rules | An environment limits which hosts its agents can reach, as an allowlist on top of the egress baseline (F-116). *Changed 2026-11-18: it builds on the baseline (Q26).* | later | planned |

Cleanup deletes refs, never LFS objects: a task's LFS objects stay in the code host's storage and count against its quota, and the docs say so (ADR 0039, Q120). *Changed 2026-11-18: also covers stopped boxes and blobs (Q42, Q76). Changed again 2026-11-18 after spike 4.* | v1 | planned |

## Reliability and scale

Rows F-043 to F-048 are each one guarantee from ADR 0011.

| ID | Feature | Done when | Priority | Status |
|---|---|---|---|---|
| F-043 | Nothing is lost | Killing the server at any moment and starting it again loses no ticket event, task change or agent event, and every running task carries on. | v1 | planned |
| F-044 | Drift gets fixed | With webhooks switched off, every change in the tracker and on GitHub still reaches ostra within 5 minutes *(working value)*. | v1 | planned |
| F-045 | Runners can drop out | A runner, or a box's sidecar, that's offline for up to 10 minutes *(working value)* reconnects, and its tasks carry on without losing an event. After longer than that, its tasks stop cleanly, writes from their old lease are refused, and they're ready to reopen on a fresh box. A lost box is one more case of reopening on a fresh one (F-033). Every event the server received before the grace ran out is stored exactly once, and an event that arrives after it is refused, not kept: the work it described is on the branch and the hidden ref (ADR 0034, Q111). The contract test runs a grace sweep and an ingest at the same moment and checks that no stored row has an epoch behind its task's. *Changed 2026-11-18: applies to a box's sidecar as well as to a runner (Q38). Changed again 2026-11-18 after spike 6: late events are refused and the ingest locks the task row (Q111).* | v1 | planned |
| F-046 | No duplicates | Replaying any webhook, or retrying any call to a tracker or code host, never creates a second PR, comment or status change. | v1 | planned |
| F-047 | Agent crashes don't kill tasks | Killing an agent mid-turn, or losing its box, marks its session as crashed and keeps the branches and the hidden ref, and one action reopens the task, on a fresh box when the old one is gone. *Changed 2026-11-18: covers a lost box too (Q38, Q53).* | v1 | planned |
| F-048 | Failure tests | Against the test workspaces, the test suite kills runners, drops webhooks and restarts the server mid-task, and every check passes. | v1 | planned |
| F-114 | Blob storage | Files go through a blob store adapter: session archives, images on drafts and attachments. A fresh install keeps them in Postgres, in chunks, with a cap of 64 MiB per blob *(working value)*, and needs no setting for it. An admin can switch to any S3-compatible store with its address and keys, which are in the configuration reference. Runners upload through the server, so they still need only its address. Copies go to the tracker as attachments where its adapter can, and on GitHub ostra links to the file (ADR 0043, Q76). *Added 2026-11-18.* | v1 | planned |
| F-117 | Scale-out | Every server process is stateless and runs as any number of `web`, `core` or `all` replicas, with Postgres doing the routing. A load test with simulated runners holds 1,000 tasks at once on three core replicas and one Postgres *(working values)*, at the event rates spike 1 recorded, with a steer reaching its runner in under 500 ms at p99. The load test passes before launch, as a gate for it (ADR 0016, Q18). The test also records Postgres CPU, runs its generator as several processes, includes a reconnect storm, and puts real browsers, not only Node clients, on the receiving end for a sample of the viewers, with partial text on for some tasks (ADR 0035). *Added 2026-11-18. Changed 2026-11-18 after spikes 6 and 7.* | v1 | planned |
