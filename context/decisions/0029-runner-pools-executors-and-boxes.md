# Runner pools, executors and boxes

**Status:** accepted (2026-11-18, from the delegated answers in `context/history/answers-2026-11-18.md`). Supersedes ADR 0012. Settles Q9, Q32, Q38, Q43, Q44, Q48, Q93, Q94, Q97 and Q98 (Q95 and Q96 are in ADR 0038), and round 14's problems 1–10. **Amended 2026-11-18 after spikes 1 and 9, and 2026-11-19 after spike 3:** the `host` executor contains a task's processes with a Windows job object or a Linux cgroup, a personal runner trades its device-code session for a runner-only key at once, the `docker` executor owns its boxes' subnets, `kubernetes` differs from `docker` on egress and needs Kubernetes 1.29, and the bridge has deadlines (Q151 to Q155). **Amended 2026-11-19 from the questions milestone 1 raised** (`context/history/answers-2026-11-19.md`): how `host` contains a task's processes on each system (Q126), which join tokens core accepts and when a joined runner waits for approval (Q130), and a runner's drain, resume and revoke (Q108, Q131). **Amended again 2026-11-19 for milestone 5's spec**, on the maintainer's delegation: a `host` pool's OS user on each system, what a runner reports, and the server's address under the egress baseline (Q242, Q231, Q239; "Milestone 5: the fleet in practice" below). **Amended 2026-11-21 by ADR 0068:** the box's browser runs in the agent's container on `docker` and `kubernetes` and is the machine's (or a pinned download) on `host`, and the init forwards a port on `docker`. This adds no allowed difference: the list below stands (ADR 0068, "The box's browser").

The server is the control plane and never runs an agent itself, as ADR 0012 said. A runner is the `ostra` CLI running `ostra runner` on a machine that someone hosts anywhere. It connects out to the server, so it works behind NAT.

**Runners join pools.**
- A runner pool is a named set of runners in one organization. Each project lists the pools it may use (Q9).
- A pool runner starts with the pool's join token in `OSTRA_JOIN_TOKEN`. On first contact it trades the token for its own identity, an Ed25519 key pair whose private half never leaves the runner. After that it uses short-lived access tokens (Q94, `research/runner-transport.md` §8).
- A personal runner signs in with a device code that its member approves in the browser. It runs only that member's tasks, on the `host` executor (Q44, Q94).
- **The device code's credential is narrowed at once.** better-auth's device flow hands out a full member session, good for about a week, and its `scope` narrows nothing (spike 9, `research/spike-auth-foundation.md`, surprise 5). So `ostra runner` uses that session once, to register: it presents the session, receives its own runner identity (the same Ed25519 key pair as a pool runner, whose private half never leaves the machine), and the server revokes the session straight away. The runner can then do what a runner does (connect, receive dispatches, fetch a task's leased credentials) and nothing a member can. The code that remains on disk is the runner key, not a login. The spike showed that the revoke call works. `ostra login` (F-103) is a different credential, a member's CLI session, and the runner never uses it.
- Each runner can be revoked on its own, in any state, and the revoke takes effect at once (below, "Drain, resume and revoke"). Rotating a join token doesn't disconnect runners that already joined.
- A runner reports its executor, capacity, labels and version (F-013).

**A join token is as sensitive as every secret of every project that may use its pool** (Q48). So:
- it's shown once, stored hashed, and expires after 30 days by default *(working value)*. An admin can set another lifetime, or none
- a pool can require an admin to approve each new runner
- every join is an audit entry and a notification to admins
- **any token of the pool that hasn't expired and isn't revoked lets a runner join** (Q130, amended 2026-11-19): the bootstrap token and the ones an admin makes in the panel alike. Milestone 1's core accepted the bootstrap one only, so the panel made tokens that registered nothing
- **the approval switch is enforced wherever a token is accepted** (Q130): a runner that joins a pool that requires approval stays `joining`, connected or not, and is offered no task until an admin approves it, or rejects it, which revokes it. Accepting more tokens without this check would have made the switch do nothing
- the audit entry of a join names the token. The notification to admins comes with notifications (F-036)

**Executors.** A runner gives each task its place to run through its executor. An executor is an `ExecutorAdapter`, which runs in the runner under Apache-2.0 (Q98, ADR 0025). v1 ships three, built in this order:
1. **`docker`:** a box of containers on a private network, with gVisor as an optional runtime.
2. **`host`:** a worktree on the machine, and no box. Personal runners use it. A pool may use it when an admin opts in, for machines that can't run containers for the job, such as Macs that build iOS apps. The panel labels it "not isolated". On a pool, the agent runs as a separate OS user (Q27).
3. **`kubernetes`:** a box as one pod. The cluster's own autoscaler supplies the elasticity.

**A box per task** (Q38).
- A box is the agent's container (the repos and the tools, no credentials), an ostra sidecar (the credentials, both proxies, the ACP driver, the event spool) and the environment's services.
- On `docker` they share a private network. On `kubernetes` they're one pod.
- The pool runner only creates and removes boxes. Each box's sidecar connects to the server itself, with a short-lived token for that one task, tied to the task's lease.
- A box serves one task and is never reused for another.
- The sidecar is the same `ostra` binary in an internal mode (Q80). On the `host` executor, the runner process does the sidecar's work. So the same task code runs on every executor.

**Dispatch.** A task goes to one of its project's pools, by labels and free capacity. A member may choose their own personal runner when they start a task. An organization's model provider is usable on personal runners only when an admin allows it for that provider (Q32, Q47, ADR 0030).

**Box sizes** (Q43). The organization names the sizes: small (2 vCPU, 4 GB), medium (4, 8) and large (8, 16) *(working values)*. A project picks its default. A pool caps its total and each project's share.

**Process containment on `host`.** A box ends every process of its task when its container ends. A worktree has no container, so processes a tool detached from the agent's tree could outlive a crash or a stop. Spike 1 saw that the runner's reap works from the agent's tree, and that a detached helper isn't reached by it. A difference like that is a runner-parity bug unless it's closed or recorded, so the `host` executor puts each task's processes in one containment unit and ends the unit when the task ends:
- **Windows:** a job object per task, set to kill its processes when it closes. *Settled 2026-11-19 (Q126):* the runner makes and holds the job itself, through `koffi`, an FFI library with prebuilt binaries that is loaded on Windows only (ADR 0007). The agent joins the job in the same tick as its spawn, and everything it starts is in the job from birth. The kernel ends the job's processes when the runner ends the job, and also when the runner itself dies, because the job closes with its last handle. In a run on Windows 11, this ended a helper that had detached itself and whose parent had exited, which the tree kill missed (`research/host-process-containment.md`). When the job can't be made, the executor falls back to the process tree and says so.
- **Linux:** a cgroup per task, killed as a unit, when the runner's own cgroup is delegated to it. When it isn't, the process tree and the marker sweep below.
- **macOS has neither** (`research/spike-how-should-the-runner-drive-opencode.md`, item 6). *Settled 2026-11-19 (Q126):* `host` on macOS ends the agent's process group and every descendant it saw, and then every process of the runner's own user that carries the task's marker. The marker is a random value the launch puts in the agent's environment, and a child keeps it unless it clears its environment. A process that both leaves the group and drops its environment isn't reached. That is the third allowed difference below. None of this has run on a Mac: the contract case runs on one before F-014 is `done`.
- **The runner reports its containment** (`container`, `job-object`, `cgroup` or `process-tree`), the server keeps it, and the panel says "a process the agent detaches isn't contained" on a runner that reports `process-tree`, whatever its system.
- **What no unit holds:** a process that something already running starts for the agent, such as `launchd`, an editor's server or a Docker daemon. It's outside a job object and a cgroup too. Only a box holds it (ADR 0031).
- **Until milestone 2's ticket 42 is in,** milestone 1's `host` executor on Windows ends the agent's whole process tree on stop and says in the panel that detached processes aren't contained.

**The allowed differences between executors.** `AGENTS.md` requires that every difference between runners is recorded in an ADR. These are the only ones:
1. **No services on `host`.** The `host` executor doesn't start an environment's services. The scheduler never sends it a task whose environment declares them (Q40, ADR 0038).
2. **No box sizes on `host`.** It counts slots only (Q43).
3. **Weaker process containment on `host` where the machine gives no kernel unit** (Q126, reworded 2026-11-19): always on macOS, on Linux when the runner has no cgroup of its own to write, and on Windows when the job object can't be made. The runner reports it and the panel shows it, as above.
4. **On `kubernetes`, the agent's container has direct internet access** (Q151). In a pod, every container shares one network namespace and one IP, and a NetworkPolicy selects pods, not containers. So the egress baseline (private ranges, the metadata address, other boxes) holds on both executors, but on `kubernetes` the agent can also reach any public host without going through the sidecar. On `docker` the agent's container sits on an internal network whose only exit is the sidecar, and that closes it (an `internal: true` network that no run has tried yet). No credential is exposed either way, because the agent holds none (ADR 0030), but a prompt-injected agent on `kubernetes` can send data out to a public host. v1 accepts and records this, and the panel says it plainly on a `kubernetes` pool: "the agent has direct internet access". Nothing in spike 3 shows a better pod shape, and a pod whose agent has its own network namespace has not been found. F-052 (allowlists, later) can come forward for `kubernetes` if it matters. A NetworkPolicy also has no effect on a cluster whose network plugin doesn't enforce it, and ostra's contract test tells an enforcing cluster from one that isn't (F-116).

**The `docker` executor owns its boxes' subnets** (Q154). Docker's default address pools hold at most 31 networks (15 of /16 and 16 of /20, from moby's source), and a box needs two, so a run of 50 boxes on one host would exhaust them. The runner carves each box's two networks out of a pool it manages, pins both inside it, and writes the egress rules once for the whole pool and not one rule per box. The pool is a setting with a working default that doesn't overlap Docker's own pools, and its line goes into the configuration reference when the executor reads it. The docs tell an admin to keep it clear of their own networks. One shared egress network with inter-container connectivity turned off is the alternative if pinning proves clumsy, and is untried. The fallback of one container per box with the runner as a separate OS user stays on the books: nothing in spike 3 triggers it. *Built 2026-11-22 (F-017): a box has one network of its own, its internal box network, and the boxes' sidecars share one egress network with inter-container connectivity off (the alternative above, built in milestone 1). So the runner pins only the box network: a /24 of `OSTRA_BOX_SUBNET_POOL` (`10.89.0.0/16` by default, spike 3's range), skipping every /24 another network on the host holds, and it refuses a box once the pool is full. The shared egress network takes its one subnet from Docker's pools, and the egress rules are written once, for it.* *Amended 2026-11-22 (F-116): the rules are written once for the pool too. `deploy/egress-baseline.sh` also rejects everything from `OSTRA_BOX_SUBNET_POOL` to the host itself (`INPUT`), with no accept, because a box network's gateway is the host's own address and Docker enforces `internal` on forwarded traffic only. The pool gets no forwarded (`DOCKER-USER`) rule, because an agent's traffic to its own sidecar crosses that chain on their bridge.*

**The `kubernetes` executor needs Kubernetes 1.29 or later** (Q155). The box's services run as native sidecar containers (`initContainers` with `restartPolicy: Always`), which are on by default since 1.29 and stable since 1.33. The configuration reference, the Helm chart (F-118) and the docs state it.

**The bridge has deadlines.** One connection between the sidecar and the init carries stdout, stderr and control, and a stalled reader pauses the socket, so a kill's reply could wait behind a full buffer. Every request on the bridge has a deadline, and stopping a task ends with removing the container when the init doesn't answer.

**Drain, resume and revoke** (Q108, Q131, amended 2026-11-19).
- **A drain is an admin's hold.** A draining runner takes no new tasks and its running tasks finish. It stays draining through disconnects and restarts, and comes back by an admin's Resume: to online, or to offline when it isn't connected. An admin can drain a runner that is online or offline. The server decides who is offered a task, and it offers to online runners only, so the hold survives whatever the runner's process forgets. The runner is told with the `drain` command, and with a `resume` command when the hold is lifted (ADR 0034).
- **A runner that shuts down by itself isn't draining.** For an upgrade or a restart it stops taking tasks by reporting no free slots, and it is online again when it reconnects, with the same identity. That needs no admin.
- **A revoke is final, and possible from any other state:** `joining` (a rejected join), `online`, `offline` and `draining`. An admin revokes any runner of the organization, and a member their own personal runner. A connected runner gets `evict` and a close with `4403`, and can't get a new access token. **Its leases end in the revoke's own transaction, with no grace:** the epochs go up, its tasks stop cleanly, and each is ready to reopen on another runner. The grace of F-045 is for a runner that may come back. A revoked one can't, and a grace would leave its last access token good for a task's credentials until it expired.
- A revoked runner that joins again makes a new key pair and is a new runner.

**Autoscaled pools.** A pool runner accepts a dispatch at once and reports "waiting for a node" while its box is pending. Otherwise the two-minute offer timeout (`research/runner-transport.md` §4) would fire while the cluster is still adding a node (round 14, problem 10).

**A `kubernetes` pool requires a registry.** A cluster can only pull images from one. For `docker` and `host` the registry stays optional (round 14, problem 4, ADR 0038).

**The Docker socket** (Q97). The `docker` executor needs the Docker socket, which is root on that host.
- Pool runners belong on dedicated hosts, and the docs recommend rootless Docker or the gVisor runtime.
- The default compose file mounts the socket into its runner. That's right for a one-machine install, and the docs say so.
- The `kubernetes` executor needs only its own namespace and a service account scoped to it.

**The egress baseline.** A box can't reach private address ranges, the cloud metadata address or another box (`research/elastic-sandboxes.md`, isolation rule 5). v1 ships it as a network policy on `kubernetes` and as host rules on `docker` (round 14, problem 11, F-116). Allowlists per environment (F-052) come later. ADR 0031 lists it with the other safety lines.

**ADR 0012's rule, reworded.** A runner holds no long-lived credential for code or models. Its identity key is long-lived, and grants only the right to connect and receive the tasks dispatched to it.

## Considered options

- **One runner container that runs many tasks in worktrees** (ADR 0012, ADR 0020). Rejected: a pool serves many projects, and their tasks would share one container with no boundary between them (`research/elastic-sandboxes.md`, isolation rule 6).
- **The runner inside each box** (round 9). Rejected on its own: something outside the box has to create it on an autoscaled pool.
- **The runner outside the box, doing all of the task's work** (round 14). Rejected on its own: a pool runner that crashed or upgraded would stop every task it held, and `host` would run different task code. The sidecar keeps both: one program, and the same task code everywhere.
- **A hosted sandbox vendor, E2B first** (`research/elastic-sandboxes.md`, recommendation 1). Rejected by the maintainer (Q36): people run runners where they want and join with a key. Hosted sandboxes may become community executors later (F-127).
- **Build `host` first** (Q93). Rejected: the box layout decides the proxies, snapshots and services, so `docker` comes first.
- **`host` only on laptops** (Q93). Rejected: a pool of Mac minis can only be served by `host`.
- **A one-time code per runner** (ADR 0012, F-013). Rejected: a join token per pool lets one key start any number of runners. The device code stays for personal runners.
- **A small helper program that puts the agent in a Windows job object** (Q126's first recommendation). Rejected: it needs a second language, a Windows build of ostra's own for two architectures and an unsigned binary, which ADR 0046 keeps out of v1, and the runner couldn't ask the job what is in it. `node:ffi` is the same idea as `koffi` with no dependency, and is experimental and absent from the Node versions the CLI supports (`research/host-process-containment.md`).
- **A drained runner that returns to service when it reconnects** (Q108's first recommendation). Rejected: a dropped connection or a reboot would cancel an admin's hold.
- **A revoked runner's tasks waiting out the grace** (Q131's first recommendation). Rejected: the runner can't come back, and the wait keeps its leases open for its last access token.
- **Join tokens that never expire.** Rejected as the default: a leaked token would let a stranger's runner receive a project's code and secrets. GitHub's runner registration tokens expire after an hour (`research/platform-auth-github.md` §1.7).

## Consequences

- Runner parity holds by construction: the same task code runs in every sidecar. The differences listed above (three on `host`, one on `kubernetes`) are the only allowed ones, and any other is a bug. The contract suite for executors includes a case that starts a detached helper and checks that stopping the task leaves nothing behind, on `docker`, `kubernetes` and `host` on Windows and Linux. *2026-11-19 (Q126):* and on macOS, where the helper keeps its environment and the marker sweep finds it. A second case, a helper that also clears its environment, is the recorded gap of a `process-tree` unit and must pass on the other three.
- A pool runner that crashes or upgrades doesn't interrupt its tasks, because each box talks to the server itself.
- New lifecycles, each a discriminated union. A runner is joining (possibly waiting for approval), then online ⇄ offline. An admin can drain it and resume it, and a revoke from any state is final (amended 2026-11-19, Q108, Q131). A box is creating, preparing, ready ⇄ idle, stopped and released, or failed (ADR 0039).
- Spike 3 (`what-is-inside-a-box`) proves the layout, and has not yet: its Windows rehearsal ran with no containers, passed the 33 checks it could run, failed none, and skipped 17 that need a Linux host with Docker, a cluster that enforces NetworkPolicy, gVisor, BuildKit with a registry (`research/spike-what-is-inside-a-box.md`). The credential handoff, the bridge, the key proxy's swap and a stop that leaves no process held in the rehearsal. A box is ready in under 10 s on Docker with the image present, and in under 60 s on a warm Kubernetes node. 50 boxes run on one host, and the sidecar stays under 100 MB *(working values)*. The sidecar's bar is checked against a Linux measurement of the driver alone first: it was 83 to 88 MB on Windows (spike 1). If it fails, the fallback is one container per box, with the runner as a separate OS user (Q27 as first written).
- The `kubernetes` executor builds snapshots with a rootless BuildKit pod, which spike 3 also checks.
- If expiry gets in the way of autoscaled pools, join tokens can be bound to a cluster's identity instead.
- Pools shared between organizations aren't possible. *Changed 2026-11-19: this said a hosted version might revisit that, and none is planned (ADR 0001).*
- **Milestone 1 runs its end-to-end demo on the `host` executor,** because the machine the plan is built on has no Docker. The runner is a personal one with a worktree, and it holds no credential: the key proxy and the git proxy run in the runner's own process, as the sidecar's work (ADR 0030). The `docker` executor is written in full, with unit tests, and its live test and spike 3 wait for a Linux machine with Docker. Until then F-017 stays `planned`.
- Ledger rows: F-013, F-014, F-015, F-017, F-067, F-069, F-091, F-092, F-093, F-095, F-116 and F-118. The fleet view (Q5) ships with them in milestone 5.

## Milestone 5: the fleet in practice

Added 2026-11-19 (Q231, Q239, Q242), for `specs/m5-the-fleet/spec.md`.

- **A `host` pool's separate OS user** (Q242). On Linux and macOS, the admin makes the agent's user and a sudoers rule that lets the runner's user start processes as that user and no other; the runner starts the agent, its setup script and its checks through `sudo -n -u <user> --` with an argument array, hands the worktree to that user, and keeps its own data folder, key and temp folder unreadable to it. `health()` checks both. **On Windows, a `host` pool runner refuses to start in v1,** with the reason: running a process as another Windows user needs that user's password or a service's privileges, and neither fits a runner a person starts. A personal runner on Windows is unchanged. This is a limit on where a `host` pool can run, not a difference in how a task behaves, so the list of allowed differences above stands. `OSTRA_DEV_HOST_POOL_SAME_USER=true` runs a `host` pool as the runner's own user for development and test only, refused otherwise, and the panel says "same user (development only)".
- **What a runner reports** (Q231). Every `hello` and `status` carries slots, and on `docker` and `kubernetes` the CPU and memory it offers, with its capabilities, labels, install and containment (ADR 0059). `capacity` stays the slot count, so a minor-3 runner still reads right.
- **The server's address under the egress baseline** (Q239). A box's sidecar must reach the ostra server, which is often at a private address. The baseline's one exception, on `docker` and on `kubernetes`, is the server's address and port (and DNS on `kubernetes`), plus `OSTRA_EGRESS_ALLOW` for a private endpoint an admin names, such as a model server. On `kubernetes` the agent can reach it too, as it can public hosts (the fourth difference above); it holds no token the server accepts. ADR 0060 has the policy's shape.
