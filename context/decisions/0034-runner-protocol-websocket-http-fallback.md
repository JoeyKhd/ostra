# The runner protocol: one session over WebSocket with an HTTP fallback, routed through Postgres

**Status:** accepted (2026-11-18, from the delegated answers in `context/history/answers-2026-11-18.md`). Records the outcome of the Q22 study (`research/runner-transport.md`), and settles the HTTP fallback, the version window and the dependencies that the answers took from it. Covers F-013, F-045 and F-061. It carries the transport and wording parts of ADR 0012, which ADR 0029 supersedes, and amends ADR 0022. **Amended 2026-11-18 after spikes 6 and 9** (`research/spike-runner-transport.md`, `research/spike-auth-foundation.md`): events that arrive after the grace are refused (Q111), the ingest transaction locks the task row, the HTTP carrier's extra calls are listed, the fallback triggers are reworded, and a personal runner's device session is traded for a runner key at once (Q115). **Amended 2026-11-19 from the questions milestone 1 raised** (`context/history/answers-2026-11-19.md`): the task token a box's sidecar connects with (Q129), what a revoke ends (Q131), the `resume` command (Q108), and where a task stands while its offer is out (Q132). **Amended again 2026-11-19 for milestone 5's spec**, on the maintainer's delegation: minor 4, and how a runner is pinned to its server's version (Q243, Q246; "Milestone 5: minor 4 and the pin" below). **Amended again 2026-11-19 after a live runner exited as revoked when the clocks disagreed:** a refused token says why, in minor 2, and only a revoked runner or a key the server doesn't know ends a runner ("Auth" below). **Amended 2026-11-20 after four runners with one identity took one machine's connection from each other:** one `ostra runner` per data folder, and a runner whose connection is replaced stops with exit code 4 ("One process per runner" below). **Amended 2026-11-21 by ADR 0068:** minor 7, and a second connection per watched preview (`/runner/v1/preview`) that carries its bytes off the session; replicas forward a preview's stream to the replica that holds it, the one place they talk to each other; over the HTTP carrier, the browser view at 2 frames a second and no tunnel (ADR 0068, "The preview connection").

The protocol is ostra's own: a session of numbered, acknowledged messages between the server and one peer, defined once as Zod schemas in the shared `protocol` package (ADR 0008). Messages are strict objects, discriminated on `type`, with branded IDs (`RunnerId`, `TaskId`, `SessionId`, `CommandId`). The server routes through Postgres. There's no broker and no Redis.

**Who connects.** A pool runner or a personal runner joins the server and receives dispatches. Inside a box, the sidecar connects to the server itself, with a short-lived token for that one task, tied to its lease (Q38, ADR 0029): the task token, below. Both speak this protocol. On the `host` executor the runner and the sidecar are one process.

**One session, two carriers:**
- **WebSocket**, the main carrier: one connection on port 443, through `ws`, with text frames, one JSON envelope per frame, and compression off. It's built in milestone 1.
- **HTTP**, the fallback: the same envelopes. `POST /runner/v1/up` takes a batch and returns acks. `GET /runner/v1/down?after=<seq>` holds for up to 25 s and returns commands, or 204. It's built with the fleet in milestone 5, and it's part of v1 (F-013). Spike 6 needed three more things, which belong to the carrier: `POST /runner/v1/hello` (the handshake that `hello` and `welcome` do on a WebSocket), the connection epoch on every request, with a `409` answer when a newer connection holds the runner, and a header that carries the runner's minor version (`x-ostra-minor`). The 25 s hold worked behind a proxy that buffers whole responses.
- **Bulk data** stays off the session: session archives and files go over chunked, resumable HTTPS with a digest, through the server, so a runner needs one address only (ADR 0043). Frames are capped at 1 MiB *(working value)*.
- Any replica serves any request on either carrier. State lives in Postgres, so the load balancer needs no sticky sessions.

**Up, from peer to server: events**
- The peer numbers every event of a session and keeps it in a disk spool until the server acks it.
- The server saves each batch in one transaction, idempotent on `(session_id, seq)`. In the same transaction it advances the ingest cursor and enqueues reactions (ADR 0037). It acks only after the commit, which is ADR 0011's "saved before ostra acts on it".
- A batch that doesn't start at the cursor plus one gets `ack {resendFrom}`, so a gap can't be committed. After any drop, the peer resends from its first unacked event.
- Partial text isn't an event. It travels as unsequenced live frames, at most every 250 ms, and isn't spooled (ADR 0035).
- The spool has a quota of 1 GiB per runner *(working value)*. When it's full, the peer stops reading the agent's output, the agent blocks on its own pipe, and events are never dropped.

**Down, from server to peer: commands**
- A command is a row in a Postgres outbox table, numbered per runner and written in the same transaction as the change that caused it. The panel sends commands this way too, so it never talks to the core service directly (ADR 0016).
- The number comes from a counter on the runner's row, taken under its lock, so numbers are gap-free and in commit order. A global `bigserial` doesn't give that.
- Commands are dispatch, steer, interrupt, stop, an approval's answer, drain and update hints. `resume` joins them with the fleet view (F-092): it lifts a drain on the runner's side, where `drain` set a flag the runner would otherwise keep until it restarts (Q108, ADR 0029). They carry references, never secrets. Keys and tokens are fetched by a separate call after the server checks the lease epoch.
- The peer applies each command once by its `id`, acks the highest contiguous number, and on reconnect says which it applied last. A command past its `notAfter` is rejected, never applied late. The peer judges `notAfter` by server time, so a laptop's clock doesn't matter.
- **A command whose ack never reached the server is sent again** (amended 2026-11-22, F-043). On the WebSocket, a hello that says the peer applied a command the server holds no ack for (the connection went with the ack, as when core is killed before the ack's transaction commits) doesn't ack it: the server sends it again, and those after it, and the peer answers each one it applied with the result it kept, never applying it twice. Acked by the hello, its result was lost: a dispatch's `accepted` with it, and the task waited out its offer while the runner worked it. A box's sidecar connection does the same. The HTTP carrier's down poll asks after the runner's own last applied command, so nothing is sent again there.
- **On HTTP, the runner sends again the results of an up batch the server never answered** (amended 2026-11-22, F-013). The down poll acks a command by seq alone, so a command's result reaches the server only in an up batch. A batch whose `POST /up` failed (cut, timed out, answered by something that isn't ostra) ended its connection and was dropped, and its results with it: the next poll had acked those commands with no result, and a dispatch's `accepted` was lost as on the WebSocket. Now the runner keeps the results of that batch, and of the frames queued behind it, and sends them first on its next connection's welcome, on either carrier. An ack by seq is never final for a result: the server records a result that comes after it, and its hooks act on it. A result that did arrive and goes again changes nothing (an offer is accepted once). The batch's events go again from their spools, and the status and the runner's own events on every welcome, as before. Nothing changes on the server, so an older runner works as it did.
- A dispatch is an offer. The peer answers `accepted` or `rejected`. An offer not accepted in 2 minutes *(working value)* goes back to the queue. **The task stays `queued` while its offer is open, and moves to `preparing` when the peer accepts** (Q132), so an offer that is refused or times out has nothing to undo. The offer still counts against the runner's free slots, and the task's page says which runner it was offered to. A pool runner in front of an autoscaling cluster must accept at once and report "waiting for a node", or the timeout fires while the cluster adds one.
- If a peer crashes between starting and finishing a steer, it reports `outcome-unknown`, and the panel shows that.

**Routing between replicas**
- A presence table records which replica holds which peer, with a connection epoch. A new connection evicts the old one, and the old replica closes its socket with `4409`.
- A command insert and a `NOTIFY` on one channel commit together. Every replica listens and ignores peers it doesn't hold. A sweep every 2 s *(working value)* catches any notification that was missed, so a lost notification costs up to 2 s and never a command.
- `NOTIFY` carries only commands, evictions and revocations: tens a second at 1,000 tasks. It never carries agent events. Committing a transaction that sends one takes a global lock, which limited a design with one notification per write to about 2.9K writes a second.
- Each replica holds one dedicated, direct `pg` connection for `LISTEN`, never through a pooler in transaction mode.
- A draining replica sends `goaway` in jittered waves. A connection older than 60 minutes *(working value)* is asked to reconnect, which spreads peers evenly after a scale-out.

**Liveness, leases and fencing (F-045).** All values are working values.

| Timer | Value | What happens |
|---|---|---|
| Server ping | every 20 s | Stays under nginx's 60 s idle close |
| Dead connection | no frame for 45 s | Either side closes, and the peer reconnects |
| Presence | one write per replica every 10 s | Constant load whatever the peer count |
| Panel shows offline | no presence for 45 s | |
| Task grace | 10 minutes without the peer | A timer stops the task cleanly, ready to reopen elsewhere |
| Self-fence | 9.5 minutes without the server | The peer stops its agents and keeps the workspace and branch |

Each dispatch raises the task's lease epoch, and the peer sends the epoch with every event, result and token request. After the task grace, the epoch it holds is stale: the server refuses its writes and won't mint it a token. So a laptop that sleeps through the grace period can't write afterwards. The server's refusal is the guarantee. The self-fence is a courtesy.

**Events that arrive after the grace are refused, not kept (Q111).** Spike 6 asked whether an event produced under a still-valid lease but delivered after the grace should be refused or kept in an inert quarantine table. Refused. The guarantee is: every event the server received before the grace ran out is stored exactly once, and after it the task stops cleanly and stale writes are refused. An event the agent produced during the cut and the peer could only deliver afterwards is lost from the log. What it did isn't lost: the work is on the task's branch and its hidden ref (ADR 0039), and the task reopens on a fresh box. A quarantine table would keep a transcript that nothing reads, and every reader of the log would have to learn to skip it. The spooled events of a refused peer are discarded once the server tells the peer its task was stopped. The build-order's wording for spike 6 is changed to this (`build-order.md`).

**The ingest transaction holds a share lock on the task row** (spike 6, gotcha 9). The grace sweep that stops a task and bumps its epoch, and a batch that is being stored, must not interleave, or a row could be written with an epoch behind its task's. F-045's contract test runs a grace sweep and an ingest at the same moment and checks that no stored row has an epoch behind its task's.

**Auth (Q48, Q94):**
- A personal runner signs in with a device code that the member approves in the browser (RFC 8628, through better-auth). The session that flow returns is a full member session, so the runner trades it for its own runner key at once and the server revokes the session (ADR 0029, Q115).
- A pool runner starts with its pool's join token and trades it for an identity: an Ed25519 key pair whose private half never leaves the runner.
- To connect, the runner posts a signed assertion and receives a 10-minute access token *(working value)*, which it sends at the WebSocket upgrade. The server caps a connection's age instead of re-checking the token. Revoking a runner sends `evict`, closes the socket with `4403`, and reconnecting fails. **A revoke also ends every lease the runner holds, in the same transaction and with no grace** (Q131, ADR 0029): the epochs go up, so its late writes are refused, and the spec, credentials and bulk endpoints refuse its access token from then on, though the token's own ten minutes may not be over.
- **A runner holds no long-lived credential for code or models.** Its identity key is long-lived, but it grants only the right to connect and receive what's dispatched to it. This replaces ADR 0012's "a runner holds no long-lived secrets".
- **A refused token says why, and only two refusals end a runner** (amended 2026-11-19: a personal runner exited as revoked, and told its member to delete its identity, when core refused its assertion because the two clocks disagreed by an hour). From minor 2 the token endpoint's error body carries a `reason`:
  - `clock-skew` (401), with the server's time as `serverTime`. The runner names the offset ("this machine's clock is 3600 s behind the server's"), keeps asking with its reconnect backoff, and connects once the clocks agree.
  - `unknown-key` (401): no runner has this ID, or its key doesn't verify the signature. It's one answer for both, so nothing about which runners exist leaks. The runner stops, and says the server doesn't know its key.
  - `revoked` (403). The runner stops.
  - `replayed` (401): the nonce was used before, as when a proxy resends a request. The runner signs a fresh assertion at once.
  - Only `revoked` and `unknown-key` end the runner (exit code 3), and only they come with the advice to delete its identity, the one case where a new identity is the fix. (A connection the server gave to another process of the same runner ends it too, with exit code 4: "One process per runner" below.) Core logs every refusal as `runner.token-refused` with the runner ID, the reason and, for the clocks, the skew, never the assertion or a token.
  - **The runner doesn't sign with the server's time.** The time in a refusal is unauthenticated. Correcting from it would let whatever answered the request (a proxy the machine trusts, a server reached over plain HTTP) get an assertion dated in the future, hold it back, and trade it for a token later, when the skew window exists so that a captured assertion is worthless two minutes after it was made. Retrying costs at most one backoff (60 s) once the clocks agree. `notAfter` already uses the server's time from `welcome`, which comes on an authenticated connection.
  - **Versions.** The runner sends its minor in `x-ostra-minor` on the token request. A request without it, from a runner before minor 2, gets minor 1's body, without `reason` or `serverTime`, since its schema is strict. From a server before minor 2, the runner reads a 403 as revoked, since that was its only 403, and retries a 401, which could be any of the other three. A proxy's 401 or 403 that isn't ostra's error body is a network failure, never a verdict on the runner.

**The task token (Q129, amended 2026-11-19).** What a box's sidecar connects with. Milestone 1 gave the sidecar the runner's own access token, in a file the runner rewrote every few minutes, so a compromised sidecar could speak for the whole runner, and a runner that stopped took its boxes' tokens with it.
- **What it is.** A token core makes for one lease. It names the organization, the task, the lease epoch, the box and the runner, under core's own signing key, with a prefix the log guard redacts.
- **How long it lasts.** Exactly as long as that lease is the task's current, active one. It has no clock and is never renewed. A stop, a release, the task grace, a new dispatch or a revoke ends the lease, and the token with it. Core reads the lease at every use, as it already does for every write.
- **What it may do.** Connect as that box's sidecar peer. Send that task's events, live text and command results. Receive that task's commands. Read that task's spec and credentials. Move that task's archives and files on the bulk path. Nothing of another task, and nothing a runner does.
- **How it arrives.** `POST /runner/v1/tasks/:taskId/token`, with the runner's access token and the lease epoch, answers only the runner that holds that lease, for a box on `docker` or `kubernetes`. The runner asks once, when it makes the box, and hands the token to the sidecar in a file that only the sidecar's container mounts. It is never in an environment variable or an argument, and never in the agent's container.
- **What the runner's token no longer gets.** On `docker` and `kubernetes`, a task's credentials go to its task token only. The runner still reads the task's spec, which holds no secret, to make the box.
- **`host` is unchanged.** The runner's process is the sidecar there, and uses its own token for its tasks.
- **Why no clock.** A token with its own expiry needs renewing, and a sidecar cut off for nine of the grace's ten minutes would come back with an expired token and lose a task the grace was there to save. A one-time code traded for the token would strand a sidecar that restarts while its runner is down, and ADR 0029 promises that a runner's restart doesn't interrupt its boxes.

**Versions (ADR 0022):**
- The URL carries the major, `/runner/v1/`. `hello` and `welcome` negotiate the minor.
- The server accepts a runner **one minor behind or ahead**, and a runner is **pinned to its server's version when it joins**: `ostra runner` reads `/runner/v1/info` and installs that version. A freshly installed runner is usually newer than its server, which ADR 0022 didn't cover.
- Each side keeps codecs for its own minor and the one before, and encodes down to the negotiated one, because ostra's schemas reject unknown fields. `hello` is the one message that tolerates them.
- A refused runner logs at error level with the fix, retries every 5 minutes, shows the reason in `ostra runner status`, and appears in the panel as outdated.

**Networks:**
- All traffic goes to `https://<server>/runner/v1/*` on 443, so one host is allow-listed.
- The runner honours `HTTPS_PROXY`, `NO_PROXY` and `NODE_EXTRA_CA_CERTS`. An answer that isn't an ostra envelope, such as a proxy's HTML page, is a network failure, and the runner says so.
- It falls back to HTTP when the upgrade gets a non-101 answer after TLS succeeded, when the socket dies within 10 s three times in a row, or when the upgrade succeeds but no `welcome` arrives within the 10 s handshake timeout. Once a connection has had its `welcome`, silence is a network failure: the runner reconnects over WebSocket, and doesn't fall back. (Spike 6: "two heartbeat periods with no frames" was replaced because a connection that has worked can go quiet for ordinary reasons.) It tries WebSocket again every 10 minutes. `--transport auto|websocket|http` overrides it.

## Considered options

- **Socket.IO.** Rejected: at-most-once by default, recovery lasts about two minutes in memory, its Postgres adapter has no recovery, and its fallback needs sticky sessions.
- **Connect-RPC streaming.** Rejected: bidirectional streams need HTTP/2 end to end, and its types come from protobuf, a second source of truth beside Zod.
- **NATS, Centrifugo or Rivet Actors.** Rejected: each adds a service and a second store to a Postgres-only install (ADR 0017), and an event saved there can't commit with a task change in Postgres. Centrifugo's own Postgres mode confirms the outbox design.
- **WebTransport.** Rejected: Node can't do it yet, and UDP is the first thing corporate networks block.
- **uWebSockets.js and `partysocket`.** Not needed. The first isn't on npm and covers only the server. The second buffers in memory without sequence numbers, which would compete with the spool.
- **SSE for the downlink.** Rejected for the fallback: a proxy that buffers holds the stream. A long poll returns a whole response, so buffering only adds latency. The POST-up, poll-down shape follows MCP's Streamable HTTP.
- **Polling only,** as GitHub Actions and Claude Code's self-hosted environments do. Kept as the fallback carrier, but a push path is needed for steers, which spike 6 holds to under 500 ms.
- **An advisory lock per runner,** as the ownership record. Rejected: the lock pool is shared and finite, and a presence row does the job.
- **Replica-to-replica forwarding and sticky routing.** Set aside: replicas would have to find and trust each other, and sticky routing doesn't help messages that start on the server.

## Consequences

- `ws` and `@types/ws` join the server and the runner, and `pg` is used directly for the listen connection. `https-proxy-agent` is not needed: spike 6's runner got through a CONNECT proxy with Node's own `https.Agent` and its `proxyEnv` option. That feature is documented as "active development", so the runner's minimum Node is 24.5 or later (22.21 or later on the 22 line), set in the `ostra` CLI's `engines` and in ADR 0046 (the repo root's `>=24.2` is lower), and the contract suite includes a proxy case that runs on each Node version the CLI supports. If a supported Node can't do it, `https-proxy-agent` is added then, with the maintainer's yes.
- The self-hosting docs say that `NODE_EXTRA_CA_CERTS` is read once, when the runner starts, so a changed certificate needs a restart.
- Spike 6 (`runner-transport`) gates this, on Node only, on Windows, macOS and Linux, and it is still open: its Windows run closed half of criteria 3 and 5 and most of criterion 2, and macOS, Linux and real nginx remain (`build-order.md`). Its bars are there: a connection or an automatic fallback through a CONNECT proxy, a TLS-inspecting proxy and nginx's defaults; every event stored once after `kill -9` and network cuts of 30 s, 5 min and 11 min, and after the 11 minutes the task stops cleanly and stale writes are refused; a steer in under 500 ms at p99 with two replicas; 2,000 connections on one replica; and 1,000 sessions on three replicas. If it fails, batch harder first, then weigh another WebSocket server. That fallback wasn't triggered, because no check failed, and isn't ruled out, because the 2,000-connection check hasn't run on Linux.
- A compatibility matrix of runner N-1, N and N+1 against server N runs in CI, over recorded fixtures.
- Credit-based backpressure keeps server memory flat: a window of 256 frames or 4 MiB, whichever is reached first, with frames of at most 1 MiB *(working values)*. The runner counts both (spike 6 found a runner that counted frames only, which would let up to 128 MiB be in flight). Reconnects use full jitter from 1 s to 60 s.
- F-045 and F-047 apply to a box's sidecar as well as to a runner. A lost box is one more case of reopening on a fresh one.
- The self-hosting docs say to pass the WebSocket upgrade through, and to raise the idle timeout on a load balancer that closes WebSockets on its own schedule.
- The glossary gains **lease** (with its epoch) and **command**.
- ADR 0022's "one minor behind" becomes one behind or ahead, and F-061 follows.
- It's hard to reverse once runners are installed in the field, which is why it's an ADR.

## Milestone 5: minor 4 and the pin

Added 2026-11-19 (Q243, Q246), for `specs/m5-the-fleet/spec.md`.

- **Minor 4** adds the `resume` command, a box's size and image in the dispatch, a snapshot build's push, `box.waiting` and `box.scheduled`, and what a runner offers and how it was installed in `hello` and `status`. A minor-3 runner keeps working: it gets no `resume` (a resumed minor-3 runner takes tasks once it restarts, and the panel says so), no size (it counts slots only) and no registry image (it builds and keeps its own snapshot). A `kubernetes` runner needs minor 4, since that executor is new in it. The HTTP carrier's endpoints are part of the major, not a minor.
- **How a runner is pinned** (Q243). "Pinned to its server's version when it joins" needs a mechanism, and the CLI is unpublished until milestone 7. At every start, `ostra runner` reads `/runner/v1/info`. A runner installed from npm whose version differs installs the server's version into `<dataDir>/versions/<version>` with scripts off, from the registry `info` names or `OSTRA_RUNNER_NPM_REGISTRY`, checks the package's integrity, and re-executes itself as that version, once. A runner from the image installs nothing: its tag is the pin, and the panel shows when it differs from the server's. A runner from source logs the difference. `OSTRA_RUNNER_PIN=false` turns it off. The window above still decides what the server accepts; the pin keeps a fresh install, or one the server has moved past, on the server's own version.
- **Considered:** pinning only at the first join. Rejected: a server upgrade would never reach a runner that was already joined until someone reinstalled it, and a start is when a reinstall costs nothing.

## One process per runner
Added 2026-11-20, after a live install: four `ostra runner` processes with one identity ran on one machine, left alive by restarts. Core gave the connection to each new one and evicted the one before (`replaced`, 4409); the evicted one slept a minute, reconnected and evicted the next. Every takeover restarted the task's agent, and the panel reloaded every few seconds.

- **One runner per data folder on a machine.** Before it signs in, `ostra runner` takes `<dataDir>/runner.lock`, a file made with O_EXCL that holds its pid, its host name and a nonce, and removes it when it stops. A second `ostra runner` on the folder exits with code 4 and names the pid that holds it. The lock is taken after the pin, so the version the pin starts takes it, and before the sign-in, so two first starts don't both register.
- **A lock a crash left behind is taken over** when its pid no longer runs, when it's this process's own pid (a restarted container, where the runner is pid 1 again), when another host name wrote it (a recreated container or a rescheduled pod, whose process this machine can't ask), or when the process with that pid isn't a Node program (a pid the system reused, read from `/proc` on Linux, `tasklist` on Windows and `ps` on macOS; a program it can't name counts as a runner). A stale lock is moved aside and compared with the one judged stale before it's replaced, so two runners starting at once on it don't both take it.
- **A replaced runner stops.** On `evict { reason: "replaced" }` or a 4409 close, a runner ends with a message saying another process connected as it, from another machine or a copy of its data folder, records `replaced` as its last refusal, and exits with code 4, which a service manager shouldn't restart on (systemd: `RestartPreventExitStatus=3 4`). ostra installs no service units of its own. Docker's restart policies restart on any code, so two containers with one identity still take turns, but at the speed of a container's restart, not every few seconds.
- **Its own reconnect race doesn't stop it.** A runner opens one connection at a time: `runSocket` finishes a socket before the loop opens the next, and an `evict` or 4409 that reaches a finished socket ends only that socket. So a half-open socket core evicts for the runner's new connection never reaches the loop. What can reach it is a hello of its own that core accepted late: core numbers connections by the order their hellos commit, not the order they opened, so a hello the runner gave up on (no welcome in time) can commit after the next connection's and evict it. The runner keeps the time of each hello it sent and got neither welcomed nor refused on, and a `replaced` within 5 minutes of one spends it and reconnects. Core settles a hello in seconds (it closes a socket without a hello in 10 s and an HTTP request not in within 30 s, and accepts it in one transaction), so the 5 minutes leave room for a proxy that forwards a request late.
- **A box's sidecar keeps reconnecting.** Its box has one sidecar, and its task's events have nowhere else to go.
- **The HTTP carrier tells a replaced connection apart** (amended 2026-11-21, protocol minor 8). A request from an older epoch, which a newer connection of the runner took over on either carrier, is answered `409` with the error `replaced`, as `evict` and 4409 say it on the WebSocket, and a runner on HTTP stops on it the same way, its own late hello excepted. `409 superseded` now means only a connection core closed (quiet past the dead time), and the runner says hello again on it. A minor-7 runner is answered `superseded` for both, as before, so two minor-7 runners with one identity on HTTP still take turns. Until then the two answers were one, and two runners on HTTP took turns (`HTTP_REPLACED_MINOR`, `httpEpochRefusal`). Core logs every eviction as `gateway.evicted`: also when both WebSocket connections are on one core process, which the hello's own path skipped when it ran before the replica's LISTEN, and with `carrier: "http"` for an HTTP connection.
- **Considered:** a heartbeat that keeps the lock file's time fresh, which would need no pid. Rejected for now: a laptop that sleeps stops the heartbeat and loses its lock while its runner is still alive. A local socket or named pipe as the lock: the OS frees it on a crash, but a Unix socket's path has a length limit a data folder can pass. Staying alive but disconnected on `replaced`, so no service manager restarts it: rejected, since idle processes holding the identity are what the incident left behind.
