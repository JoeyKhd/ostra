# Every tracker is an adapter; Linear works in two modes

**Status:** accepted (plan signed off 2026-11-17). Amended 2026-11-18: the decision stands, with a pointer to the Jira sign-in ADR, and the Linear app is registered by each organization, not each install (Q-20, Q102, ADR 0047). **Amended 2026-11-18 after spike 5** (`research/spike-linear-agent-mode.md`, updated after the first real-Linear run, and the spike's README): what the 5 seconds covers, Linear's retries, who a stop comes from, and the heartbeat's values (Q125). **Amended 2026-11-19 for milestone 6's spec,** on the maintainer's delegation: how agent mode is turned on, where the measurements of the real insert and proxy come from, and what the real run needs from a person (Q214 to Q220; the section "Milestone 6: agent mode in practice", with ADR 0057). Chosen on 2026-11-17 in grilling round 2. The maintainer: "make sure each PM tool is an adapter".

- **Each tracker is an adapter** behind one tracker interface. Things only some trackers have, such as Linear's native agent sessions, are declared capabilities (adapter parity in `AGENTS.md`).
- **Linear ships in v1, Jira in the first release after it.** A Jira test during planning makes sure the interface isn't shaped only for Linear (`research/trackers.md`). Jira signs in through a service account that the organization owns, plus one admin webhook, as ADR 0047 records.
- **Linear works in two modes, on one Linear app** that each organization registers itself:
  - **Always:** the plain API for picking up tickets, statuses, comments and PR links. It uses webhooks when Linear can reach the install, and checks Linear regularly when it can't.
  - **With a public HTTPS address:** native Linear agent mode. People hand a ticket to ostra inside Linear, see a live agent session on it, and can stop it or send follow-ups from there.
- **Private installs** work fully, just without agent mode. The docs show how to get a public address through a reverse proxy, Cloudflare Tunnel or Tailscale Funnel.

## Consequences

- Linear agent mode has to answer within 5 seconds, post its first update within 10 seconds, and post again at least every 30 minutes. That's the server's job, not the runner's. Spike 5 checked the server's side against a fake Linear (every webhook answered in at most 55 ms, every first thought posted in at most 91 ms, with no runner) and then against the real one on 2026-11-18 (the install and the 50 delegations ran; the stop and follow-up phase ran out of its wait window, so that bullet is not passed). Three precisions come from it:
  - **The 5 seconds covers the TLS proxy and the durable insert.** The handler's path is: verify the signature, claim the delivery ID and the signature in one insert, answer 200, then do the work. Nothing else sits in front of the 200. The insert has its own deadline, well inside the 5 seconds, and when it fails the handler answers a non-2xx so that Linear retries, instead of losing an event behind a 200. The host's clock stays within the SDK's 60-second signature window, and the handler records each webhook's transit time and warns when it is far from zero (the spike's machine ran 1.1 s behind Linear's). The spike measured the ack against an in-memory map, so the real insert and the real proxy are measured in milestone 6, when F-012 is built.
  - **A miss isn't free.** Linear retries a webhook after 1 minute, 1 hour and 6 hours, and the docs say the webhook "might be disabled" if the URL stays unresponsive. A slow insert could end with the app's webhook switched off.
  - **The 30 minutes is Linear's note, not a rule it states in full.** The docs say follow-up activities "can still be sent for up to 30 minutes before the session is considered stale", that a stale session is recoverable by sending another activity, and that Linear tracks the lifecycle "based on the last emitted activity". That the clock restarts on every activity is a reading, and the real run's one 35-minute turn is consistent with it, not proof.
- **A stop always comes from a signed-in user in Linear, never from an API key.** A stop is the "Send stop request" button, pressed by a person. A personal API key can't post an agent activity at all: `agentActivityCreate` with one is refused with a 403, "Using an unexpected authentication method (apiKey) for an operation", for a prompt and for a stop. So ostra's own activities are always posted with the app's own OAuth token, a stop can't be simulated or automated against real Linear with a key, and the test of a real stop needs a person pressing the button (a follow-up can be automated, as a reply in the session's thread by a key's user). A stop pressed in ostra's own panel is a different action: it stops the runner's turn and posts the final `response` with the app's token, and doesn't claim that a user stopped it in Linear. So for the tracker interface, a tracker's "stop" is an event ostra receives, not a call ostra makes (adapter parity, ADR 0025). Everything else about stop is tested against the fake. ostra handles a stop as Linear's docs say: the agent halts, takes no further action, and posts one final `response` or `error`. That the stop arrives as a `prompted` webhook whose activity carries `signal: "stop"` is the fake's guess: in the real run a `prompted` webhook did arrive after the button and the session then showed `complete`, but the harness didn't check the signal, so that stays unverified until a run does. A turn's state lives in Postgres, not in a process's memory, so a stop that reaches another replica than the one running the turn still stops it.
- **The heartbeat.** A silent turn gets an ephemeral thought every 20 minutes of silence, which leaves 10 minutes before the 30. The timer restarts on any post to that session, not only on its own, because in ostra the runner's stream posts too and a fixed 20-minute loop would add needless posts. A failed heartbeat retries for at most 5 minutes, so even a failing heartbeat lands by minute 25. The kind is ephemeral by default, so it leaves no trace in the thread. If Linear turns out not to count an ephemeral thought as activity, the kind switches to a plain thought (`heartbeat.kind`), which is permanent and visible. The real run's 35-minute turn stayed alive with one heartbeat and no stale episode, which is consistent with an ephemeral thought counting, from one run. The cost is small: one request per 20 minutes is 3 an hour per silent session, about 1,600 silent sessions per workspace against Linear's 5,000 an hour for an app user (derived from the docs' figure, a floor: plan multipliers raise it). A shorter heartbeat is cheap if a longer measurement asks for one.
- ostra works with Linear's own GitHub integration, not against it. The ticket ID goes in the branch name and PR title, so Linear links them by itself.

## Milestone 6: agent mode in practice

Added 2026-11-19 (Q214 to Q220), for milestone 6's spec, which ships F-012. Who counts as a member, where a delegation goes, what ostra posts, and outside tasks are ADR 0057.

- **Turning it on.** Agent mode is a second consent on the organization's existing Linear app: "Turn on agent mode" re-authorizes with `app:assignable` and `app:mentionable` added (`update_scopes_on_existing_token=true`), from an organization admin's session, with PKCE. The app was made with the `AgentSessionEvent` webhook type in milestone 2, so it isn't recreated. Then a project admin turns on "Start from Linear" on one board per team.
- **The fast lane as built.** The webhook route verifies, claims the delivery in Postgres, answers 200, and only then queues the work; the first thought is written in the same transaction as the task and sent from an outbox. The real insert and the real tunnel are in the measured path from milestone 6 on: ticket 38's harness times each delegation from its API call's response to the 200 on this machine's clock, which leaves the clock skew that made spike 5's end-to-end figure inconclusive out of it.
- **What the real run needs from people.** The `ostra-test` app has never been authorized, and its client-credentials grant is off (milestone 2's ticket 40), so no app token exists until the maintainer presses Authorize once. A stop can only be pressed by a person in Linear. So F-012's real bullets (the install, 50 delegations, a follow-up and a stop, 35 silent minutes) run against ostra itself only after those two acts, and until then every other condition is proved against the fake.
- **The results** of ticket 38's run are recorded here when it has run: whether the stop arrived as a `prompted` event with `signal: "stop"`, and whether one ephemeral heartbeat kept a 35-minute turn from going stale.
