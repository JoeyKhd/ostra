# Background work on pg-boss, behind one package

**Status:** accepted (2026-11-18, from the delegated answers in `context/history/answers-2026-11-18.md`). Settles Q24, and Q10, Q20 and Q78 where they touch the queue. It reverses the order in `research/durable-execution.md`: pg-boss first, DBOS Transact as the fallback. Covers F-043 to F-048 and F-106. It names the queue that ADR 0011 and ADR 0017 leave open. **Amended 2026-11-19 after spike 8** (`research/spike-durable-queue-choice.md`): pg-boss stays, a schedule that starts work is driven from ostra's own table (F-106), the heartbeat on pg-boss's forwarding queue plus a singleton slot is the stopgap for pg-boss's own schedules, the limit per key is a throttle, and the panel's start and the database's time zone have rules (Q156 to Q158).

pg-boss runs ostra's background work: webhooks, retries, timers, schedules and reconciliation. It's a new dependency (MIT). Every import of it sits in one package, `packages/jobs`.

**Three rules hold whichever library ships** (`research/durable-execution.md`):
1. **ostra's tables are the source of truth.** A task's discriminated union and its event log say where it stands. A job carries out one transition and checks the task's state again before it acts. If the queue were lost, the next reconciliation pass would rebuild the work from the tables.
2. **Jobs are short and carry only IDs.** Their keys are fixed by what they do, such as `task:<TaskId>:<transition>:<seq>` and `webhook:<provider>:<deliveryId>`. Sending a job twice returns the existing one: pg-boss answers `null` to a duplicate send, and only on an `exclusive` queue (a `singletonKey` on a standard queue made two jobs in spike 8), so `packages/jobs` makes every queue exclusive and looks the existing job up. After the first job completes its key is free again, so rule 1, a handler that checks the state before it acts, is what makes a second job harmless.
3. **A human wait is a task state,** never a job blocked for hours. "Needs you" is a state. An answer writes the decision and enqueues the continuation in the same transaction. A delayed job handles the timeout: it wakes, checks the state, and does nothing if the task has moved on.

**What runs on it:**
- Webhook processing, with the delivery row and its job saved in one transaction (F-043, F-046).
- Reconciliation against the tracker and the code host, one keyed schedule per connected board and repo (F-044).
- Timers: a session's maximum duration, stall detection, the task grace after a runner is lost (ADR 0034), and cleanup after 14 days (F-079).
- Schedules on automations (F-106, Q10): each is a row in ostra's own tables, ticked by one job a minute, and not a pg-boss cron (below).
- Retries with backoff for every call to a tracker or code host (ADR 0011).
- Insights, computed every few minutes (F-108), and the daily refresh of the model catalog and each provider's model list (ADR 0033).

**How it's used:**
- A job is enqueued inside the Prisma 7 transaction with `{ db: fromPrisma(tx) }`, which needs `@prisma/adapter-pg`. So a job exists only if its transaction commits. The panel enqueues without running workers, and only the core service runs them (ADR 0016).
- pg-boss supplies what ostra would otherwise build:
  - heartbeats (switched on per queue) that free a dead replica's jobs, with no executor IDs to manage. In spike 8 a killed replica's six jobs ran on the other replica 15.1 s later with 5 s passes, and a fake GitHub that counts idempotency keys saw 6 POSTs for 6 keys at each of three kill points. The minimum heartbeat is 10 s, and the recovery time rests on the passes and on a survivor with a free worker
  - dead-letter queues, and retention
  - schedules in the database, by cron or RRULE, with a key for several per queue. They send one job per tick while no replica dies holding the batch of occurrences that pg-boss forwards, and otherwise a tick up to 15 minutes late or sent twice (spike 8, below). pg-boss's docs word the guarantee as a throttle ("job throttling options are then used to make sure only 1 job is sent"), and an occurrence that came due while no instance ran is not sent at all unless `missed` is `once`. So ostra uses them only for passes that are idempotent: reconciliation (F-044), insights (F-108) and the model-catalog refresh
  - a limit per group across replicas (`groupConcurrency`), **which is a throttle and never a budget.** Spike 8 held a limit of 2 across three replicas for 1,000 jobs on 20 keys: the handlers never ran more than 2 in a group in any pass of any run, but snapshots of the committed job table showed up to 5 to 7 jobs `active` in a group (0.13% to 0.82% of snapshots, the longest episode 12 to 61 ms), because a claim can briefly pass the limit and pg-boss gives the extra jobs back before any handler runs. The docs say so ("Concurrent fetches can briefly claim past the limit"). Anything that counts `active` rows will see the extras. The limit is a worker option and isn't stored, so every replica must pass the same value, and `packages/jobs` sets it once per queue. Use it where two extra claims cost nothing: concurrent calls per credential to a tracker or code host, and per-board reconciliation. Never for anything that costs when exceeded
  - an MIT dashboard, `@pg-boss/dashboard`, where authentication is ostra's own
- ostra builds, on top of it:
  - **Request budgets per credential** (Q20). Each adapter's base class keeps a budget row per credential in Postgres, fed by the response headers. A call that would overspend becomes a job delayed until the reset. No queue counts requests per hour.
  - **Task admission and runner scheduling** (F-067), from ostra's own tables, read with `FOR UPDATE SKIP LOCKED`, counted inside the transaction that admits. A project's and a pool's share is a budget on runner capacity, so it never rests on the queue's limit. DBOS's shape is the one to copy: a lock on the scope, a count, and a claim of the room left, in one transaction.
  - **Schedules that start work** (F-106). An automation's cron expression is a column of its row. One pg-boss job a minute, the scheduler tick, finds the occurrences that are due. Each occurrence is a row in `automation_run`, with a unique key on the automation and the occurrence's time, inserted with `ON CONFLICT DO NOTHING` in the same transaction as its job, and the job's key is `automation:<AutomationId>:<occurrence ISO time>`. A replayed tick, a second scheduler or a backfill finds the row and does nothing. This is DBOS's tick ID rebuilt on ostra's tables, and rules 1 and 2 applied to schedules. A scheduler lease (a row, or `pg_try_advisory_xact_lock`) keeps replicas from repeating the work, and correctness doesn't rest on it. An occurrence that came due while the install was down fires once, for the latest one, when it is under 6 hours late *(working value)*, and older ones are skipped and noted in the audit log (Q156). A pause or a delete takes effect at the next tick. The resolution is one minute, and a start is a few seconds late: fires came 6.3 s (p50) to 8.4 s (latest) after the tick in spike 8's run. The design is not built. The check is spike 8's hunt, run against the tick: 200 automations, 4 ticks, and every replica but one killed the moment the tick's occurrences are being inserted or forwarded, aimed at the replica that holds the work, with each (automation, occurrence) pair started exactly once. A kill timed by the clock passed 3 of 3 and was wrong. *Note 2026-11-22: at pg-boss's defaults the tick itself came late (ticket 37's hunt: occurrences written 8 to 21 s after the minute at p50, 34 s at p95), since its cron pass runs every 30 s and the forwarding poll every 5 s. `packages/jobs` sets them to 2 s and 1 s (`CRON_PASS_SECONDS`, `CRON_FORWARD_POLL_SECONDS`): one pass an interval wins across replicas, and the forwarding insert is keyed by the occurrence's slot, so nothing is sent twice. A task started 4 s after its minute where the old intervals gave 20 s (`apps/core/src/automations/schedule-lateness.test.ts`).*
  - **Timers and stall detection.** A session's maximum duration is one delayed job under `session:<SessionId>:max-duration`, which wakes, checks the state and does nothing if the session has ended (rule 3), and is cancelled when the session ends. The task grace and the cleanup after 14 days are the same shape. Stall detection ("no agent event for 10 minutes") is not a timer, because a cancel and a send for every event would write to the queue at thousands of events a second at 1,000 sessions. It is a sweep: one keyed job a minute reads each running session's last event time from ostra's own tables, so 10 minutes becomes 10 to 11 (inferred; not run).
  - **Idempotency toward trackers and the code host** (F-046): record the key before the call, or check first whether it already happened.
  - **A "Background work" page** built on the dashboard's data and ostra's tables: queues, stuck jobs, retry and cancel.
- **The seam.** `packages/jobs` is the only package that imports pg-boss, and a lint rule enforces it (Q78). It holds typed job definitions with Zod-checked payloads, an `enqueueInTx(tx, ...)` function and schedule management. A swap to DBOS, or a fork, stays bounded. If the package count slows the build, `jobs` folds into `domain` behind the same lint rule.

## Considered options

- **DBOS Transact first,** as `research/durable-execution.md` recommended. Rejected as the first choice:
  - Under the three rules above, its durable workflows have nothing left to do: ostra's tables hold the state, jobs are short, and a human wait is a state.
  - What remains of it needs a sweeper for a dead replica, retention and an admin view, all of which pg-boss already has.
  - DBOS keeps those same pieces, along with automatic upgrades of running workflows, in its proprietary Conductor or its paid extension. It moved the Conductor client out of the open package in October 2026. Its open-source upgrade route pins an application version and branches with patches, and its drift toward open core would land on self-hosters.
  - It stays the fallback. Spike 8 ran it: it held the group limit with no overshoot in the committed state, and every (schedule, tick) pair fired exactly once, because its tick ID makes a double fire impossible. But its recovery is the weaker half. A killed replica's claimed work waits for its own executor ID to come back: with a new ID per process, 400 of 800 pairs stayed `PENDING` for good. So ostra would need a stable executor ID per replica, or its own sweeper (a replica table, a dead-replica check, and `DBOS.recoverWorkflows` for a dead executor and never a live one). It also needs its schema migrated once before three replicas launch (a deadlock otherwise), and a deleted schedule fires once more, because it rereads its schedules every 30 s.
- **graphile-worker.** Rejected: no rate limits and no concurrency per key above one, a static cron, and a crashed worker's jobs stay locked for four hours unless ostra builds its own heartbeat or buys Worker Pro.
- **Hatchet, Trigger.dev, Inngest, Restate and Temporal.** Rejected: each takes jobs over an API into a separate engine, so none can join ostra's transactions. Each also adds services, and two have licenses that don't fit a self-hosted install: Inngest's server is SSPL, and Restate's is BSL 1.1.
- **pgmq, Absurd and OpenWorkflow.** Rejected: each leaves more for ostra to build than pg-boss does.
- **Redis or a hosted queue.** Rejected: Postgres is the only store an install needs (ADR 0017).

## Consequences

- Multi-step work is an explicit state machine in ostra's tables, which ostra wants anyway, and waits for people are states.
- Installs upgrade on their own schedule (ADR 0022). A queue of small jobs that carry only IDs can't be stranded by an upgrade, which a versioned workflow can.
- pg-boss is maintained by one person, sponsored by Supabase and others, and its license is MIT "and always will be". The seam and the option to fork carry that risk.
- It needs Node 22.12 or later and Postgres 13 or later. Its optional `LISTEN/NOTIFY` doesn't work through a pooler in transaction mode, so an install behind one runs without it.
- Queue retention ships with pg-boss's own defaults, and its line goes in the configuration reference.
- **pg-boss is pinned, and the heartbeat on its forwarding queue is checked at boot.** pg-boss's cron pass inserts each due occurrence into an internal queue, `__pgboss__send-it`, which is created with no options: pg-boss's default expiry of 15 minutes and no heartbeat. A replica killed while it holds a batch of 50 occurrences leaves them `active` for 15 minutes, and the replay then sends again what was already sent (the batch's real jobs are sent in parallel, so some exist when the holder dies). Spike 8's default configuration failed this way in 3 of 3 runs that stranded a batch: 44 of 800 (schedule, tick) pairs fired 15.1 minutes late, and 106 occurrences fired a second time. The stopgap, for the schedules that remain on pg-boss's cron, is `updateQueue("__pgboss__send-it", { heartbeatSeconds: 10 })` after `start()`, plus a singleton key and `singletonSeconds` equal to the period on every `schedule()`. It passed 4 of 4 earlier runs (replay 13 to 19 s after the kill). It is a timing argument with a margin of about 10 s, over an internal queue that no docs page names, so an upgrade can undo it silently: the version is pinned, a boot check reads the heartbeat back, and a test fails when it isn't there. Occurrences inserted before the first replica's `updateQueue` carry no heartbeat.
- **A `web` replica that starts before any `core` has migrated** can't start its pg-boss producer: with `migrate: false`, pg-boss fails with "pg-boss is not installed". ADR 0016 lets `web` and `core` run as separate replicas, so a first boot, or a rolling deploy that brings `web` up first, hits it. The `web` role retries its start with backoff until the schema exists, and reports itself as starting on its health check in the meantime (Q157).
- **The database runs in UTC, and the server makes sure of it** (Q158). Prisma 7's `@prisma/adapter-pg` writes a `Date` into a `timestamptz` column as the date's UTC fields with no offset, which Postgres reads in the session's time zone: spike 8 saw the stored instant off by -5.5 hours in an `Asia/Kolkata` session. Reading the row back through Prisma returns the original, so the shift is invisible there and wrong for pg-boss, SQL and any other reader. The server sets `options=-c TimeZone=UTC` on every connection it opens, checks `SHOW timezone` at boot, and the configuration reference says the database runs in UTC.
- **`packages/jobs` has four gaps to close**: it sets no heartbeat on the forwarding queue and has no boot check, and its `schedule()` passes a key and `singletonKey` but no `singletonSeconds` (its two schedules today, `catalog.refresh` and `provider.refresh-models`, are idempotent, so the cost is a late or repeated refresh); its queue settings have no `groupConcurrency` and its send options no `group`, to be added with the first throttled job; there is no test for the panel's start against a database with no schema; and there is no port of the hunt as a test of the scheduler tick, which waits for the tick.
- Spike 8 (`durable-queue-choice`) gated it, and its result is in (Windows only, one loaded laptop, Postgres 18.6 with `fsync=off` and `LISTEN/NOTIFY` off): six of seven criteria pass and C4 fails, with no scenario skipped. The criteria:
  - A job enqueued inside a Prisma 7 transaction exists only if the transaction commits.
  - After `kill -9` on one of two replicas mid-job, the job resumes on the other, and a fake GitHub that counts idempotency keys sees no duplicate side effect.
  - A limit of 2 per key holds across three replicas for 1,000 jobs on 20 keys, with any brief overshoot recorded.
  - 200 schedules created at runtime each fire once per tick while replicas restart.
  - Delayed jobs survive a restart and can be cancelled, and the panel process enqueues without running workers.
  - It compiles under ostra's strict flags.
  - **Result:** the first three pass (a job enqueued through `fromPrisma(tx)` exists only if the transaction commits; the limit held for running work; the killed replica's jobs ran on the other with no duplicate), and so do delayed jobs, the panel's enqueue and the strict compile. 200 schedules on pg-boss's own cron fail, for the reason in the consequence above, and the same scenario passes on DBOS and on the fix. The first version of that scenario, whose kills were timed by the clock and never landed in a forwarding batch, passed three times and was wrong.
- **The revisit clause did not trigger:** pg-boss held a limit per key for running work and recovered a killed replica's jobs without a duplicate side effect. The failed scenario ran on DBOS, as it says, and the answer is to keep pg-boss and move schedules that start work into ostra's own table. Not run: Linux and macOS, Postgres 16 and 17, a pooler in transaction mode, `LISTEN/NOTIFY` on, a stalled-but-alive replica, 10 replicas or a loaded database for the fix's margin, and a rolling upgrade with two pg-boss versions on one schema (ADR 0022). Spike 8's biggest queue run was 1,200 jobs on one machine, so it doesn't stand in for the load test.
- The load test at 1,000 tasks (F-117) covers the queue, and the failure suite (F-048) kills a replica mid-job at spike 8's three kill points and runs its schedule hunt.
