# No credential enters the agent's container: the sidecar, the key proxy and the git proxy

**Status:** accepted (2026-11-18, from the delegated answers in `context/history/answers-2026-11-18.md`). Supersedes ADR 0014. Settles Q17, Q26, Q27, Q41 and Q47. **Amended 2026-11-18 after spikes 1 and 4** (`research/spike-how-should-the-runner-drive-opencode.md`, `research/spike-github-app-and-git-proxy.md`): every call is metered, the git proxy's contract is stated (the `User-Agent`, LFS and its host list, refusals, its address), and spike 3 gets OpenCode's loopback port to test.

No model key and no GitHub token is ever in the agent's container. They live in the box's sidecar (ADR 0029), and the agent reaches models and GitHub only through two proxies there (Q17).

**Where the real credentials live.**
- On the server, encrypted, through the built-in `SecretStoreAdapter`.
- They reach the sidecar per task over the runner protocol, tied to the task and its lease epoch.
- The sidecar keeps them in memory only. They're never in an environment variable, an argument or a file, the sidecar's own included (`research/credential-proxy.md`, "Interactions with OS users"). They're never logged.

**The key proxy** (Q26).
- The agent gets a base URL that points at the sidecar, and a fake key that is valid for one task. The fake key has at least 128 random bits and an expiry, and it's revoked when the session ends.
- The proxy checks the fake key, strips every client credential header, sets the real one, and opens its own TLS connection to the model provider.
- It passes the stream through byte for byte: no buffering, headers and body fields forwarded unchanged, keep-alive events kept, error bodies returned as received (`research/credential-proxy.md` §1).
- It handles both API formats the provider form offers (ADR 0033).
- It counts the tokens of each call from the usage fields in the stream, and logs IDs and counts only. Budgets and the spend cap per task rest on this count (Q105, ADR 0042). **It meters every call it carries, whatever the call offers:** spike 1 saw title and other calls that have no tools sit outside every turn's usage (554 of 38,741 tokens in its run, 1.4%), so a count taken from the agent's turns would miss them. Spike 1's 2% bar compares the proxy's count with the agent's usage for the same response bytes, and the independent check is the provider's own figure.
- It reports the provider's rate-limit answers, so the scheduler holds new dispatches until the retry time (Q20). It fails the task at once on an upstream 401 or 403.
- It needs no certificate authority and no TLS interception.
- The agent's environment is built from an allowlist, never inherited.

**The git proxy** (Q26, Q41).
- The agent's own `git` fetches and pushes through the sidecar, by a `url.<sidecar>.insteadOf` rule. `GITHUB_TOKEN` and `GH_TOKEN` are never in the agent's environment.
- The proxy adds a token for one repo, which the server mints from the organization's GitHub App. **The server narrows every token it mints to one repo and to the permissions the step needs** (spike 4, surprise 9): the box's clone and push, the check, the PR and the member lookup use three different scopes.
- It reads the command list of each `git-receive-pack` request. It refuses any ref except the task's branches and its hidden ref (ADR 0039), and any delete, before a byte reaches GitHub (`research/credential-proxy.md` §14). Spike 4 ran this on real GitHub: the default branch, a delete and another repo were all refused, and GitHub accepted a push to `refs/ostra/wip/<task>`.
- **A refused push is answered in git's own words.** The proxy replies with the receive-pack status report (`unpack ok`, then `ng <ref> <reason>` for each ref, in side-band when the client asked for it), so stock git exits 1 and prints `! [remote rejected] ... (ostra: <reason>)`. It sends a plain `403` only when the client asked for no report. The proxy reads and drops the push's body before it answers, so git reads the answer and doesn't meet a reset connection. That means a refused push still costs the box the full upload to its own sidecar, up to a cap of 1 GiB *(working value)*, beyond which the proxy cuts the connection. Whether it can answer before reading the body wasn't tried. "Before a byte reaches GitHub" is about the push, not the handshake: a read-write proxy forwards the ref advertisement upstream before it sees any command.
- **LFS goes through the proxy.** The proxy rewrites GitHub's LFS batch answer so signed URLs and their headers (an `Authorization` among them) never reach the agent: it keeps them under random nonces for at most an hour and gives git `<proxy>/_ostra/lfs/<nonce>`. It drops any action that points outside the upstream or the allowed LFS hosts, and an object with a refused action gets a per-object error and no actions, never an empty `actions`. git-lfs follows the `insteadOf` rule to the proxy with no extra setting. LFS objects are uploaded to the code host's storage, and ostra can't give that storage back when it cleans a task up (ADR 0039).
- **The hosts an LFS action may call are a setting of each code host (Q119).** The code host interface declares it and each adapter states its list, per the adapter-parity rule. GitHub.com's default is exactly `github-cloud.githubusercontent.com`, `github-cloud.s3.amazonaws.com` and `lfs.github.com`. The run saw exactly one name under `githubusercontent.com`, so the default has no `*.githubusercontent.com` wildcard. A GitHub Enterprise Server install lists its own storage host, or LFS fails closed with the proxy's error. The configuration reference has one line per code host. The check is by host name and not by the address the name resolves to, so a DNS answer that points an allowed name at a private address isn't caught. The box's egress baseline (F-116) is the second wall. A contract test keeps the list honest with names that must pass and look-alikes that must not.
- **Every upstream request carries a `User-Agent`.** `lfs.github.com` refuses a request with none, with a 403, and Node's `http.request` adds none. The proxy sets one on every request it makes, git smart-HTTP included. Any test double of a code host refuses a request without it, so a missing header fails in the harness and not on a real host.
- **The proxy's refusal messages say what was refused, and by whom.** The first version blamed "the task's credential" for every upstream 401, 403, 407 or redirect, and that was wrong when the missing `User-Agent` was the cause: it would send an operator to rotate a token that was never wrong. The message is worded by status and by where the refusal came from (the git endpoint, or an LFS action host), and the log carries the upstream's status and reason without the body.
- On refine and review tasks it accepts fetches only (Q66, Q71). That includes refusing the receive-pack advertisement, LFS uploads, LFS lock checks and every non-GET LFS action. The spike ran the push refusal and a clone only, so the LFS branches of the read-only mode are code that hasn't run, and F-090's tests cover them.
- **The proxy has no per-task secret in its URL, and hands out LFS URLs on the address the agent uses.** The proxy's own listen address is wrong inside a box, so the URLs it gives out use the address the agent reaches the sidecar by. And because there is no secret in the URL, the box's network must keep other boxes away from a sidecar's port (spike 3's "another box" check covers this port), or the URL carries the task's token.
- The agent may commit. After every turn, the box commits what's left and pushes the task's branches. Commits are authored by the GitHub App's bot identity, with a `Co-authored-by` trailer for the member whose prompt led to them (Q55, ADR 0040).

**ostra's MCP tools** also run in the sidecar, with a token for that one task. No ostra credential enters the agent's container either (round 13, problem 3).

**The boundary on each executor** (Q27).
- **`docker` and `kubernetes`:** a container. The sidecar holds the credentials and the agent's container never does. The agent may install packages in its own container without reaching a key.
- **`host` in a pool:** there's no box. The runner process does the sidecar's work, and the agent runs as a separate OS user from it.
- **A personal runner:** one user. The key proxy still keeps the key out of the agent's environment and files, but the member controls the machine and can read the key.

**Keys everywhere** (Q47). Every runner, a member's own laptop included, runs on model provider keys through the key proxy. No subscription login is used, stored or passed on anywhere. An organization's provider is usable on personal runners only when an admin switches that on for the provider. It's off by default.

**Accepted limits.**
- The agent can use its fake key while the task runs, but only through the proxy, only for model calls, and only until it's revoked. That allows spend, not theft, and the spend cap per task limits it.
- An environment's own variables and secrets stay visible to the code under test (`research/credential-proxy.md`, "Per-repo test secrets"). The panel says environments are for dev and test credentials (F-050). The docs recommend throwaway resources per task, such as a database with a random password.

## Considered options

- **Keys as environment variables of the agent** (ADR 0014). Rejected: the agent runs untrusted input with a shell, so anything in its environment can leak, through an install script that harvests variables or a prompt-injected `env | curl`.
- **A loopback key proxy inside the runner, the runner doing every fetch and push, and the agent as a different OS user** (Q26 and Q27 as first written, `research/credential-proxy.md`'s recommendation). Rejected for `docker` and `kubernetes`: with a box per task, a container boundary is available and stronger than Unix users. And a runner that runs `git push` on a workspace the agent controls runs the agent's hooks and config beside the token. The separate OS user stays the rule for `host` pools, and the whole design is spike 3's fallback.
- **A push from the sidecar's own clean clone.** Kept as spike 4's fallback, if LFS or large packs break through the proxy. LFS now works through the proxy on GitHub, once the two fixes above are in. The 500 MiB pack hasn't been tried on GitHub, so the fallback stays on the books until it is.
- **A central model gateway on the server.** Rejected: by the research's own estimate, about 35 MB/s each way through the server at 1,000 tasks, and a single point of failure (`research/credential-proxy.md` §1).
- **An off-the-shelf gateway, such as LiteLLM.** Rejected: a Python dependency holding every organization's keys, and supply-chain compromised twice in 2026 (`research/credential-proxy.md` §16).
- **Placeholder secrets swapped by a TLS-intercepting proxy.** Later, as an environment option. It needs a certificate authority per task and breaks clients that sign requests.
- **A member's subscription login on their own laptop** (ADR 0005, ADR 0014). Rejected: the maintainer chose keys, and the terms forbid a platform from routing subscription logins (`research/agent-harnesses.md` §1.4).

## Consequences

- ADR 0020's gap, that a GitHub token can't be limited to one branch, is closed: the git proxy enforces the task's refs. So refusing an unprotected default branch becomes a warning (F-060, ADR 0031).
- Adapter parity: an agent adapter must take a model base URL and a placeholder key, and declares that as a capability. OpenCode (F-019, v1) does. Claude Code, the second agent in milestone 7 (F-018), does through its gateway settings, on an endpoint that speaks Anthropic's Messages API, which the key proxy supports.
- Budgets are only as good as the count. An endpoint that reports no usage gets an estimate from token counts, and the panel says so.
- A laptop runner on an organization's provider holds a real key on a machine its owner controls. That's why an admin turns it on per provider.
- Spike 1 checks that the agent's environment holds only the fake key, and that the proxy's count is within 2% of what the endpoint reports. Spike 3 checks that no key or token can be read from a shell in the agent's container, through the environment, the process list, files or the network. It also calls OpenCode's loopback port from a shell in the agent's container with no password, and tries to read the password from the process list, `/proc/<pid>/environ` and `/proc/<pid>/cmdline`, because the agent's shell and OpenCode share a container and the password's secrecy is the only barrier to a self-approval through that port (spike 1, item 5). Spike 4 checks that the git proxy refuses a push to the default branch, a delete and a push to another repo, and records how LFS, a shallow clone and a 500 MB pack behave. On GitHub it passed all of these except the 500 MiB pack, the token in the agent's container, the check flip and the Linear link, which wait for a Linux machine with Docker, a second sandbox user, and Linear's GitHub app on the sandbox org (`build-order.md`).
- Short-lived provider credentials come later, as an auth strategy of the `ModelProviderAdapter` (F-130).
- Ledger rows: F-014, F-089 and F-090.
