# OpenCode first, over ostra's own ACP driver

**Status:** accepted (2026-11-18, from the delegated answers in `context/history/answers-2026-11-18.md`). Supersedes ADR 0004 and ADR 0024. Settles Q45, Q51, Q52 and Q103, and covers F-018, F-019 and F-024. ADR 0018 stays as the agent interface. Its "v1: Claude Code through ACP" section is replaced by this ADR. **Amended 2026-11-18 after spike 1, and 2026-11-19 after spike 10** (`research/spike-how-should-the-runner-drive-opencode.md`): OpenCode can steer mid-turn, so Send steers where the agent declares it; OpenCode sends no ACP plan, so the plan view is mapped from its todo tool; a deny re-prompts; and the default agent is not reopened. Spike 10 then ran the acceptance test and OpenCode passed: it stays the default (Q159). **Amended 2026-11-19 for milestone 7's spec:** Claude Code's adapter, its launch, its keys and where its binary comes from are ADR 0062; the redistribution check this ADR's consequences ask for is the maintainer's, and until it's done no published image holds Claude Code.

**Two agents before launch, behind one interface:**
- **OpenCode** is the default, and the only agent from milestone 1 (F-019).
- **Claude Code** ships before launch, in milestone 7, as the second agent (F-018 is v1). It runs on provider keys through the key proxy (ADR 0030), never on a subscription login (Q47). It needs a model provider whose endpoint speaks Anthropic's Messages API (ADR 0033), which the key proxy already supports. Its job in milestone 7 is to prove the agent interface with two real agents.
- **Codex** and the others come later, one adapter each (F-038).

OpenCode takes any model through a base URL, a key and a model ID, which is the rule for model providers (ADR 0033). One agent through milestones 1 to 6 keeps the test matrix small while the platform is built.

**The runner drives every agent with ostra's own driver:**
- The driver is built on the official `@agentclientprotocol/sdk` 2.x, over stdio, with one agent process per task, in the task's box (ADR 0029).
- Every agent-specific import lives in one runner package, behind `AgentAdapter` (ADR 0025). ostra maps ACP into its own typed event model (ADR 0018), and the panel sees only ostra's events.
- The driver advertises `elicitation.form`. Without it, OpenCode cancels its questions and tells the model to carry on without an answer (`research/rivet.md`, R13).
- OpenCode's version is pinned in the base image and its checksum is verified when the image is built. The package is `@opencode/cli`, the V2 line, installed at an exact version with install scripts off, with the SHA-256 of the platform binary checked. The default npm package `opencode-ai` is the 1.x line, which isn't offline-safe: it tried the npm registry and github.com during a turn in spike 1. The model catalog goes in as a file (`OPENCODE_MODELS_PATH`, with `OPENCODE_DISABLE_MODELS_FETCH=1`), which keeps ADR 0033's rule that the agent never fetches it. The switches that OpenCode's docs don't list (those two, `OPENCODE_DISABLE_AUTOUPDATE`, `OPENCODE_DISABLE_CLAUDE_CODE`, `OPENCODE_DISABLE_FREE_MODELS` and `OPENCODE_SERVER_PASSWORD`) are covered by the adapter's contract suite, so a bump that drops one fails a test. ostra writes its provider and permission config for each task. It starts the agent with an explicit environment that holds only a fake key and a base URL that points at the sidecar (ADR 0030), never the runner's own environment.
- The agent's own "always allow" is not used. "Approve for this task" is an ostra rule, and the agent is always answered "once" (ADR 0036).
- Reopening a task calls `session/load`. How the session reaches a fresh box is ADR 0039's subject. `session/load` replays the history as updates, and the runner marks those so they aren't stored as new events (ADR 0035). The runner also emits `session.config_changed` itself when the model or mode changes, instead of waiting for the agent to report it.
- OpenCode listens on a loopback HTTP port with a password, beside the stdio pipe. The driver's approvals travel on the pipe, never on that port. In the box design the agent's shell is in the same container as OpenCode, so the password's secrecy is the only thing that stops a self-approval through the port. Spike 3 tests that (ADR 0030).

## Steering

Steering mid-turn is a capability an agent declares (`steerMidTurn`, ADR 0025). The composer follows it (F-024):
- **An agent that declares it gets the message mid-turn. OpenCode does.** Spike 1 found that OpenCode 2.3.2 steers over plain ACP: `initialize` returns `_meta.steering.supported: true`, and the extension method `_session/steering` answers `injected`. The steer text reached the model in the same turn's next call. OpenCode's HTTP API steers too (`delivery: "steer"`). The OpenCode adapter declares `steerMidTurn` only when `initialize` says the flag is true, and it uses the ACP extension, not the HTTP API, so the driver keeps one channel to the agent.
- **An agent without it** runs one prompt at a time and returns an error for a second `session/prompt` while the first is active (spike 1, T9: rejected after 1 ms). Send **queues** the message for such an agent. Everyone sees it in the thread as "queued", and it's delivered when the turn ends.
- **Interrupt and send** is a separate, explicit action for every agent: it cancels the turn with `session/cancel` and sends the message as the next prompt.

Two facts the composer's hint states, because they surprise people:
- **A steer lands at the next model call, not at once.** A tool step that is running finishes first. In the spike, a steer sent during a 15 s tool step reached the model in the call after the step.
- **The extension is undocumented** on OpenCode's ACP page. So the contract suite runs a steer probe on every OpenCode bump, as it runs spike 1's T3, T5 and T11. If the probe fails, the adapter stops declaring the capability and Send falls back to queueing, with no change to ostra's events.

Decided on 2026-11-18, on the maintainer's delegation: Send steers when the agent supports it, because F-024 already said that for an agent that declares the capability. If members dislike a steer that waits for a tool step, the default flips to queueing per agent profile. Not tested: a real model's use of a steer, since the probe used a scripted stub. Milestone 3's steering test runs on the model in `model.env`.

The contract suite also runs a scripted fake ACP agent that declares what OpenCode lacks, which is native plan updates and reject-and-continue. A second scripted agent has no steering, so both paths of the composer stay tested. That keeps adapter parity testable in milestones 1 to 6 (`AGENTS.md`).

## What OpenCode lacks, and what ostra does about it

Spike 1's pass bar, read strictly, failed on three cases. The decisions:

- **Plans.** OpenCode 2.3.2 sends no ACP `plan` update, even with `experimental.todo` set. Its todo list arrives as a `todowrite` tool call. The OpenCode adapter maps that call to `plan.updated`, from `rawInput.todos` and `rawOutput.metadata.todos`, and the per-task config sets `experimental.todo`. So the plan view and F-063 work with OpenCode. The mapping lives inside the adapter, and nothing in ostra's events names OpenCode. An agent that sends ACP plans maps them to the same event.
- **Deny.** A deny over ACP (`reject_once`) ends OpenCode's turn, and it also rejects every other pending request in that session. So after a deny the runner re-prompts with a short message: the member's reason when they gave one, otherwise a fixed line saying the request was denied and the agent should carry on without it or suggest another way. That is the cancel-then-re-prompt path that spike 1 ran for waits. The other approvals open in that session close as cancelled (ADR 0036). Spike 1 did not run the re-prompt after a deny end to end, so the contract suite gets a case for it. OpenCode's HTTP reply with a message is not used: it would be a second adapter capability for one agent.
- **Process reap.** The runner reaps OpenCode's own process tree. What a tool detached from that tree is closed by the box, or on the `host` executor by a job object or a cgroup (ADR 0029).

**The default agent is not reopened.** Read strictly, the plan and the reject cases fail, and the rule under Consequences says a failed must-have goes to OpenCode's HTTP API and then reopens the default. It is not reopened because every other T5 check passed (tool calls with raw input and output, diffs, child-session metadata, usage with cost, compaction records, stop reasons), the HTTP API rescued the reject, and the plan has an answer on ostra's side that costs one mapping. Switching agents would trade three small gaps for the unknowns of an agent nobody has tested. Spike 10 (`is-opencode-good-enough`) then tested the bigger question, whether OpenCode's PRs are good, and OpenCode passed it. **The default stands (Q159).** All 30 runs (10 tickets, three each, on DeepSeek's flash model through OpenRouter) completed on OpenCode 2.3.2 through the spike's copy of this driver and key proxy: CI green and the hidden acceptance tests passed on 30 of 30, 6,840,135 tokens and $0.2040 in all. Two blind AI reviewers, Claude Opus and Claude Fable (the maintainer chose AI reviewers in place of a human), each rated all 30 pull requests alone, and put every run at "merge as it is" or "merge with small edits" (28 and 2, and 27 and 3, no reject), against a bar of 50%. They gave the same rating on 29 of the 30. **What the pass covers:** OpenCode, on one ordinary model, solving toy tickets on a 400-line calculator, with one author for the tickets, the hidden checks and the reference solutions, no tracker, box, git proxy or GitHub PR in the loop, a shell that ran as the maintainer's own account, and no human rater. Nothing failed, so the set can't tell the runs apart: read it as "OpenCode isn't obviously unfit", never as the share of real PRs a team will merge. The bar is reworded to what was measured, and the realistic claim becomes a gate after milestone 1's end-to-end demo (`build-order.md`, Q159). The reopening rule's conditions weren't met: spike 10 passed on its first model, and spike 2 moved sessions across OpenCode 2.3.0 to 2.3.2.

Spike 1's pass bar is reworded to match (`build-order.md`, spike 1): T5 passes with "a plan, or a todo list ostra maps"; T7 with "a reject ends the turn, and the agent can be re-prompted to continue"; T13 with "the runner's reap works from the agent's tree, and a box or a job object closes the rest". Even then B1 can't pass from a Windows run alone, because T1's packet capture and T3's `/proc` check run only on Linux. B1 is read from the Windows, Linux and macOS runs together.

## Considered options

- **Rivet Sandbox Agent** (ADR 0024). Rejected, on `research/rivet.md`:
  - Since v0.2.0 it passes raw ACP envelopes through, so its "universal schema" no longer exists and it adds no normalization over plain ACP.
  - It's built on ACP SDK 0.16 while the current one is 2.7, it has had one functional fix since March, and its issues are closed as "not planned" with fixes waiting.
  - Its transport dies on turns longer than five minutes. Its `DELETE` never kills the agent. Its restore is a text replay capped at 12,000 characters that never calls `session/load`.
  - Its telemetry is on by default (ADR 0021), it passes the runner's whole environment to the agent, and it downloads agents from "latest" without checking a hash.
  - What the maintainer liked about it stays: start as many runners as you want with one key, and the work goes faster. That comes from runner pools and join tokens (ADR 0029), which Rivet never provided.
- **Claude Code first** (ADR 0004). Rejected: Claude Code is proprietary, and its API format would tie the first agent to one provider, against "any base URL works" (Q106). It ships in milestone 7 instead.
- **An agent-against-agent bake-off in milestone 0** (Q46). Replaced by spike 10: OpenCode alone, on the model in `model.env`. The Omnara arm can't change a decision, and a Claude Code arm would tie the spike to one API family.
- **OpenCode's own server and SDK as the base.** Rejected: it's OpenCode only, which breaks adapter parity, and its API broke completely between versions 1 and 2. Spike 1 showed that it can steer and can answer a permission with a message, but ACP does the first, so it isn't needed. It stays the fallback inside the adapter if `_session/steering` goes away.
- **Screen-reading drivers** such as `coder/agentapi`. Rejected: no structured tool calls, diffs or permission objects, which is too lossy for ADR 0011.
- **The AI SDK's experimental agent harnesses.** Rejected: bridge harnesses need a port exposed on the sandbox, which conflicts with a runner that only dials out.
- **Six agents in v1** (`research/agent-roster.md`). Not adopted: one agent, then a second in milestone 7.

## Consequences

- ostra owns the driver. It's small, because the official SDK does the JSON-RPC, and it stays in one package. It's budgeted in milestone 1.
- Agent event schemas tolerate unknown event types, because the format belongs to the vendor (`AGENTS.md`).
- The base image pins OpenCode, and the runner image pins the ACP SDK (ADR 0046). A contract suite runs per agent version. On every bump, spike 1's cases T3, T5 and T11 run again, and so does spike 2's restore test (T12 in `research/rivet.md`), as its own CI job (`pnpm spike --only=stub,model,patch` in spike 2, which covers the move on directory boxes, the patch-version change and the rebuild template). OpenCode's `session export` and `session import` are `experimental` in its HTTP API and in no docs page spike 2 found (ADR 0039), which is why the per-bump run matters.
- ACP v2 is still a draft. A v2 driver changes only the adapter, never ostra's events.
- Claude Code's license is proprietary. Its redistribution terms are checked before it goes into the public base image (`research/rivet.md` §10, R16), and that check comes before milestone 7 ships it.
- Spike 1 (`how-should-the-runner-drive-opencode`) tested only this driver, and its finding is folded in above. The rule stands for what is still open: if a must-have fails on plain ACP, the failed capability is tried through OpenCode's HTTP API, and if that fails too, the choice of default agent is reopened. The same applies if the realistic gate misses its bar on two different models, or a later OpenCode version breaks the session's move to a fresh box (spike 2 showed it works on 2.3.0 to 2.3.2).
- Rivet's agent launch table is ported in milestone 1 as a small piece of logic, with attribution. It's listed in ADR 0015's Borrowed code section and in `NOTICE` (Q21).
- F-019 is v1 in milestone 1, and F-018 is v1 in milestone 7. F-038 (Codex) stays later.
