## 1. The question, and the answer

**Question.** Does the box hold on Docker and on Kubernetes? A box is the agent's container, an ostra sidecar, and the environment's services (`PASSBAR`). The spike tests Q26, Q27, Q38, Q95 and Q96, which ADR 0029, 0030, 0031, 0038 and 0046 wrote down (`README:20-22`).

**Answer.** Not answered yet. The bar stands at **0 of 5 bullets, with 0 FAIL**: 33 checks PASS, 0 FAIL and 17 are SKIPPED (`RUN`; counted from the report's rows). Every SKIPPED check needs Linux's `/proc`, an egress policy, a real box, an image build or a cluster, and this machine has none of them. What the run does show is narrower. On one machine, with no containers, and with the real OpenCode 2.3.2 as the agent (driven by a scripted stub model, plus one turn on a real endpoint), the box's protocol works from end to end. The credentials arrive from outside by a one-time handoff. The bridge carries a turn and a 21 s turn. A key planted in the agent's environment is found, and without it nothing is. A held approval stays pending when the checklist calls the control API without its token (HTTP 401); the self-approval path through OpenCode's own port wasn't tried. The key proxy swaps the fake key on a stub and on a real endpoint. Stopping the task leaves 0 processes, counted on Windows (Section 3, item 5). The deploy files parse and have the shape the design needs, but they were read, not run. Neither the fallback of ADR 0029 (one container per box, with the runner as a separate OS user) nor the layout is tested by this. Reading the files for this finding turned up eight places where a first real run is likely to fail or to overstate (Section 3, items 6 to 13). Four need a decision: Docker's address pools and the git proxy's URL before milestone 1 builds the `docker` executor and the git proxy, the snapshot's mount before milestone 3 builds snapshots, and the Kubernetes egress difference before milestone 5 builds the `kubernetes` executor (Section 4, items 2 to 5; milestones from `context/build-order.md:22,24,26`).

## 3. What surprised us, and the gotchas

**From the run.**

1. **The SKIPPED reasons name inputs, not the machine.** `[docker]` and `[kubernetes]` say "a host with Docker and the images…" because `--real` wasn't passed (`pass-bar.ts:30-34,54-60`). A reader could think the harness tried Docker and found it missing. It never looked. I checked the machine by hand (Method).
2. **`handoff` and `bridge` PASS only show that the ports were closed.** In the rehearsal the harness, sidecar and agent all sit on 127.0.0.1, so the address-based "from inside the box" refusal can't be tried. The file says so, and says the handoff and control ports then stand on the nonce, the closing after first use, and the bearer token (`box-fixture.ts:127-132`). `ECONNREFUSED` is what a closed port gives. The address check itself is unit-tested (`SPIKE/test/box-network.test.ts`; `SPIKE/src/sidecar/box-network.ts:108-118`), and I didn't rerun it.
3. **The agent's uid reads 0 on Windows.** `RUN log`, `bridge_connected`, says `agentUid: 0`. The init isn't root and Windows has no `process.getuid`, so it falls back to 0 (`SPIKE/src/init/main.ts:45-49`). The number looks like root and means nothing here.
4. **The endpoint check counted 1 call, and the log shows 2.** The check reads the key proxy's counter when the turn ends and found `1 calls, swapped 1, rejected 0` (`RUN` P1, `[endpoint]`). The log shows two `proxy.call` lines for that box, the second 0.8 s after the first and with 0 tokens (`RUN log`, `proxy.call` at 20:05:34.997 and 20:05:35.767). The README's run reported 2 of 2 (`README:183`). That fits a second call, such as a title call, that ends after the turn does (inferred from the timestamps: each line's `ms` puts both calls' starts near 20:05:31.8). The stub box's approval turn, by contrast, logs 3 `proxy.call` lines and the check saw 3 (`RUN log`, 20:05:03.628, 20:05:03.726 and 20:05:04.282). Spike 1 found the same thing in its own run, and ADR 0030 says the proxy meters every call (`context/decisions/0030-no-credential-enters-the-agents-container.md:17`). The check passes either way, because it asks for at least 1 swapped and 0 rejected (`box-run.ts:295`). It can't be used as a count.
5. **The stop check passes without the case that failed in spike 1.** The tree's grandchild is spawned `detached` by a server that stays alive (`box-scenarios.ts:17`). On Windows, the init's reap kills by `taskkill /T` and finds survivors by parent links (`SPIKE/src/lib/process-tree.ts:116-135,148-160`; `init/main.ts:120-127`). So a live parent keeps the link. Spike 1's finding was a helper whose parent shell exits within milliseconds, which stayed alive after a crash (`context/research/spike-how-should-the-runner-drive-opencode.md:166-168`). On Linux the init reaps by user ID, every process of uid 1000 whatever its parent (`init/main.ts:97-127,214-225`), which should catch an orphan. No run has tried that.

**From reading the files. None of these ran.**

6. **A snapshot's checkouts would be hidden by the box's task mount.** The snapshot Dockerfile puts each repo at `/task/workspace/<name>` (`SPIKE/src/snapshot/dockerfile.ts:41,55,69`), and the sidecar's `workspace` is `/task/workspace` (`SPIKE/src/lib/opencode.ts:73-75`). But the compose file mounts a tmpfs at `/task` (`compose.box.yaml:98-100`) and the pod mounts an emptyDir there (`box-pod.yaml:77,148`). Docker says of a mount over existing files that "the pre-existing files are obscured by the mount" ([Docker: tmpfs mounts](https://docs.docker.com/engine/storage/tmpfs/)), and an emptyDir is "empty scratch space" ([Kubernetes: volumes](https://kubernetes.io/docs/concepts/storage/volumes/)). So a box started from a snapshot would see an empty `/task`. No check starts a box from a snapshot, and the bar doesn't ask for one. ADR 0038's whole point, "a box starts in seconds" from the snapshot, needs this settled (Section 4, item 5).
7. **A run of 50 Docker boxes probably can't get 50 networks from Docker's default address pools.** The compose file pins `box-internal` to a templated /24 (`compose.box.yaml:130-136`), but `box-egress` has no `ipam` block (`compose.box.yaml:137-138`), so Docker picks its subnet. In moby's source the default local pools are 172.17.0.0/16, 172.18.0.0/16 and 172.19.0.0/16, then 172.20.0.0/14, 172.24.0.0/14 and 172.28.0.0/14 cut into /16 networks, then 192.168.0.0/16 cut into /20 networks ([moby `ipamutils/utils.go`](https://github.com/moby/moby/blob/master/daemon/libnetwork/ipamutils/utils.go), master, read today). That is 15 networks of /16 and 16 of /20, **31 at most**, and a box needs one. The 50-box run (`real-box.ts:401-442`) would probably fail at the box after the pools run out (the error text is unverified). The egress script has the same shape of problem: it takes one subnet and drops traffic from it to the private ranges (`SPIKE/deploy/docker/egress-baseline.sh:18,25,48-50`), so per-box egress networks each need a rule, or one wide rule over every pool. The bridge driver documents a `com.docker.network.bridge.enable_icc` option, "Enable or Disable inter-container connectivity" ([Docker: bridge networks](https://docs.docker.com/engine/network/drivers/bridge/)), which could let all sidecars share one egress network. I haven't tried it, and whether it also keeps sidecars apart through each other's published ports is unverified.
8. **The git proxy in this spike carries a per-box secret in its URL, and ADR 0030 says it has none.** The stub's route is `/<token>/<owner>/<repo>/…`, and a request with another token gets 404 (`SPIKE/src/sidecar/git-proxy.ts:98,141-145,219`). The sidecar makes the token with 16 random bytes and writes the URL into the agent's `~/.gitconfig` (`sidecar/main.ts:217,485-494`). The file's own comment: "Not a credential: the agent sees it in its git config" (`git-proxy.ts:77`). ADR 0030 says otherwise for the real proxy: no per-task secret in its URL, so the network must keep other boxes away, "or the URL carries the task's token" (`context/decisions/0030-no-credential-enters-the-agents-container.md:32`), and the bar's "another box's git proxy port" check leans on that (`PASSBAR`). With the token in place, a connection from another box would reach the port and still get a 404, so the `other-box-git` check (a TCP connect, `checklist.ts:364`) passes or fails on the network alone and no longer decides whether the push is possible. The spike and the ADR disagree. Spike 4 dropped the token its first sketch had, because it relied on the box's network (`context/research/spike-github-app-and-git-proxy.md:214`).
9. **In a pod, the agent has the sidecar's network, and the docs say so.** The spike's own NetworkPolicy file states it: a policy selects pods, so the agent has direct egress to the public internet in a pod, while on Docker its only exit is the sidecar (`SPIKE/deploy/k8s/egress-baseline.networkpolicy.yaml:12-19`; `README:217-223`). The docs agree: "Because they are applied at Pod level, NetworkPolicies apply equally to init containers, sidecar containers, and regular containers." They list as limits that pods "cannot currently block localhost access" or access from "their resident node", and say traffic to and from the pod's node "is always allowed" ([Kubernetes: network policies](https://kubernetes.io/docs/concepts/services-networking/network-policies/)). Pod containers also share an IP and port space and may use SystemV semaphores or POSIX shared memory between them ([Kubernetes: Pods](https://kubernetes.io/docs/concepts/workloads/pods/)). So on Kubernetes a prompt-injected agent can send data out to any public host without a credential. On Docker the design closes that (the agent sits on an `internal: true` network, `compose.box.yaml:7-9,131-133`), but no run has tried it, and item 12 says I couldn't confirm from the docs what such a network does. ADR 0029 allows only the `host` executor's differences and calls any other a bug, and `AGENTS.md` says a difference between executors "is a bug unless an ADR records it" (`context/decisions/0029-runner-pools-executors-and-boxes.md:42,73`; `AGENTS.md:28`). The difference is real, no ADR records it, and ADR 0030's "the agent reaches models and GitHub only through two proxies" can hold on Docker only (`0030…md:5`).
10. **The Kubernetes policy only works on a cluster that enforces it.** "Creating a NetworkPolicy resource without a controller that implements it will have no effect" (same page). The harness has no check that tells an enforcing cluster from one that isn't. Its destination checks pass on any unreachable address (item 12). By the API reference's own wording, the policy's `ingress: []` denies ingress from other pods: an empty list "does not allow any traffic", though the same field's text lets through traffic whose source is "the pod's local node" ([Kubernetes: NetworkPolicy API](https://kubernetes.io/docs/reference/kubernetes-api/policy-resources/network-policy-v1/)). And the `0.0.0.0/0 except …` carve-outs block other boxes only if pod IPs fall inside the excepted ranges. The docs say `ipBlock` is meant for "cluster-external IPs, since Pod IPs are ephemeral and unpredictable". The `ingress: []` on every box pod is the second wall that holds either way (`egress-baseline.networkpolicy.yaml:26-31,44-70`).
11. **The OpenCode password half of the bar can't be tested by this checklist, and may not hold on every host.** The `proc` check looks for the two markers it was given (`checklist.ts:191,230`). It can't look for a password it doesn't know, and the README says so (`README:224-226`). Spike 1 found that `opencode acp` holds its loopback password in memory, that the agent's own calls to the port got 401 on every try, and that it did not find how `acp` mode gets that password (`context/research/spike-how-should-the-runner-drive-opencode.md:160-164`). So the box can't search for it, and the spike can't plant one. Whether the agent's shell can read OpenCode's memory is a question about the host kernel. A same-user process passes the ptrace access check unless the target isn't dumpable, and `/proc/<pid>/mem` "is governed by a ptrace access mode PTRACE_MODE_ATTACH_FSCREDS check" ([ptrace(2)](https://man7.org/linux/man-pages/man2/ptrace.2.html); [proc_pid_mem(5)](https://man7.org/linux/man-pages/man5/proc_pid_mem.5.html)). With Yama's `ptrace_scope` at 1, the man page says, the target must be a descendant of the caller, and OpenCode is the ancestor of its shell tool, not a descendant. A host set looser than that has no such limit (inferred). A box doesn't set that value, and gVisor's behavior is unverified. Not tried.
12. **The network checks have no positive control, and a timeout counts as blocked.** `tryConnect` reports a timeout as "not connected", which the checklist reads as BLOCKED (`checklist.ts:131-152,357-359`). So an address that is down, mistyped or simply unreachable passes, and so does a cluster that enforces nothing but has no route to `192.168.0.1:80`. The default private target is that one address (`real-box.ts:253,352`). Nothing probes the box network's own gateway or the host, and I couldn't confirm from the docs what an `internal: true` network does there: it "lets you create an externally isolated network" and says no more ([Docker: networks](https://docs.docker.com/reference/compose-file/networks/)). The env check has a negative control (`box-run.ts:183-185`). The port and network checks have none.
13. **Smaller things the first real run will meet.**
    - **A bridge request has no timeout, and stop waits on one.** `request()` sets none (`SPIKE/src/bridge/bridge-server.ts:196-207`), and `stopTask` awaits `bridge.reapAll()` (`sidecar/main.ts:301-306`). One connection carries stdout, stderr and control. When one stream's buffer fills, the socket is paused (`bridge-server.ts:233-236`), and the reply to a kill would wait behind it. A hung init, or a stalled reader, would hang the stop. The product needs a deadline and a way to remove the container (inferred).
    - **The Kubernetes snapshot Job has no egress policy, and its build runs project code with secrets mounted.** The only NetworkPolicy is for `ostra-boxes` (`egress-baseline.networkpolicy.yaml:23-31`). The Job runs in `ostra-build`, with `Unconfined` seccomp and AppArmor and `--oci-worker-no-process-sandbox` (`buildkit-rootless.yaml:16,44-57`), and `namespace.yaml` holds no NetworkPolicy. BuildKit's rootless page says of that flag that it "is discouraged, as it cannot terminate processes that did not exit" ([BuildKit: rootless](https://github.com/moby/buildkit/blob/master/docs/rootless.md)). That page doesn't say the two `Unconfined` settings are needed on Kubernetes. It points to `examples/kubernetes`, so the manifest's claim is unverified from the docs.
    - **The build script pushes before anything scans.** Its default output is `type=image,…push=true`, and the harness scans only when it overrides that with an OCI tarball (`SPIKE/deploy/snapshot/build-rootless.sh:11-12,48`; `real-box.ts:466-470`). ADR 0038 says the build fails if the secret's value is in the image. A scan after the push leaves the leaked secret in the registry. The scan decompresses gzip blobs only (any other blob is searched as it is, so a zstd layer would be searched compressed) and looks for the literal value, skipping any under 6 characters (`SPIKE/src/snapshot/image-scan.ts:27,41`; `dockerfile.ts:96`). The OCI exporter's default compression is `gzip`, and `zstd` is allowed ([Docker: OCI exporter](https://docs.docker.com/build/exporters/oci-docker/)). Docker says a secret mount is "temporarily available inside the build container, for the duration of the build instruction" ([Docker: build secrets](https://docs.docker.com/build/building/secrets/)). A setup script can still write the value, or an encoded form of it, to a file, and the scan wouldn't see the encoded form.
    - **The measurements are upper bounds.** Ready time runs from `compose up` or `kubectl apply` to a status poll, and on Kubernetes each poll is a `kubectl exec` that starts Node in the sidecar, every 200 ms (`real-box.ts:224,317-336,389-392`; `box-run.ts:85`). The sidecar's memory is the process RSS from its own status in the one-box check (`box-run.ts:213-216`; `real-box.ts:541-542`), but container memory from `docker stats` or `kubectl top` (which needs a metrics server) in the 50-box run, and that is not the process RSS the bar's number was framed on (`real-box.ts:272-275,371-376,431-437`). The pod's sidecar is limited to 256Mi and the agent requests 4Gi (`box-pod.yaml:69-74,115-117`). 50 OpenCode processes at spike 1's 124 MB at rest come to 6.2 GB before any sidecar or Postgres (`spike-how-should-the-runner-drive-opencode.md:196`; arithmetic).
    - **A stale comment.** `agent-host.ts` says the bridge host is in `src/bridge/remote-host.ts`. There is no such file: the host is built at `bridge-server.ts:356-363` (`SPIKE/src/lib/agent-host.ts:7`). Milestone 1's issues 03, 09 and 22 point at the seam: 03 and 22 by the name `AgentHost` (`context/specs/m1-first-pr/issues/03-adapter-sdk-base-classes.md:17`; `…/22-docker-executor-images-compose.md:17`), 09 by the path `agent-host.ts` (`…/09-acp-driver-and-event-mapping.md:22`), and 22 also by the spike's directory (`…/22-docker-executor-images-compose.md:27`).

**What held up.**
- **The `AgentHost` seam.** The same ACP driver drove the real OpenCode 2.3.2 through the bridge, strictly validated and with backpressure, to `end_turn` and through a 21 s turn (`SPIKE/src/lib/agent-host.ts:40-49`; `bridge-server.ts:356-363`; `RUN` P2). The seam is what the executor's `startAgent` is meant to return (`context/specs/m1-first-pr/spec.md:177`).
- **The credential handoff.** The sidecar takes the credentials once, from outside, with a one-time nonce, and then closes the port. In the run, the `handoff` check found it closed (`ECONNREFUSED`). The nonce comparison is constant-time (`SPIKE/src/sidecar/handoff.ts:81-85,144-153`). The init opens the one bridge connection outward and holds only its own nonce, which root's environment keeps from the agent's user (`SPIKE/src/init/main.ts:1-13`). That last point is a claim about Linux the rehearsal can't test.
- **Pinned and verified.** The base image's OpenCode checksum matches the lockfile (Facts), and nothing is downloaded when a box starts (`Dockerfile.base:1-9`; ADR 0046).

## 4. What this changes in the plan

These are recommendations. No ledger row moves: a spike is throwaway code (`AGENTS.md`), and F-017, F-051, F-094, F-116 and F-120 stay `planned`.

1. **`context/build-order.md`, row 3 and the line above the table.** Row 3 says "none yet" for the finding and "Docker on Linux, and its finding" for what it waits on (line 203). Point the finding column at this file. Say that the run was on Windows, that 0 of 5 bullets are met with 0 FAIL, and what it waits on: a Linux host with Docker and both images, a cluster that enforces NetworkPolicy, `runsc`, `buildctl` with `rootlesskit`, and a registry. "Six spikes have a finding" (line 197) also goes up by one.
2. **ADR 0029, the Docker executor, and the bar's "50 boxes on one host".** Add that the executor owns its subnets. The default address pools stop at 31 networks, a box needs one for each network that isn't pinned, and the egress script takes one subnet (Section 3, item 7). Either pin both of a box's networks inside a pool the runner manages and document `default-address-pools`, or try one shared egress network with inter-container connectivity off. Keep the fallback (one container per box, the runner as a separate OS user) on the books: nothing in this run triggers it.
3. **ADR 0031 and ADR 0030: record the Kubernetes difference.** `AGENTS.md` says a difference between executors is a bug unless an ADR records it. Write down that in a pod the agent shares the sidecar's network, and the NetworkPolicy is the only wall, which leaves public egress open. Say that ADR 0030's "only through two proxies" is meant to hold on Docker (an `internal: true` network that no run has tried), and on Kubernetes holds only for credentials (Section 3, item 9). Then choose: accept it for v1 and bring F-052 (allowlists, now `later`) forward for `kubernetes`, or design a pod whose agent has its own network namespace. I recommend accepting and recording it for v1, because nothing in this run shows a better pod shape, and saying so plainly in the panel.
4. **ADR 0030, the git proxy's URL.** Decide the spike-versus-ADR split (Section 3, item 8). I recommend keeping a random path segment per box. It costs nothing, the agent can see it anyway, and it makes a push from another box fail even if a network rule doesn't hold. Reword the ADR to "no credential in the URL; a per-box path segment as a second wall", and keep the "other box" check as the first.
5. **ADR 0038 and F-051: the snapshot's place, and the order of scan and push.**
   - Decide where a snapshot's checkouts live relative to the box's writable task root, before milestone 3 (Section 3, item 6). A named volume that Docker fills from the image on first use, or a copy at box start, are the two shapes I'd try. I haven't tried either.
   - Add to F-051 and ADR 0038 that the scan runs on the built image before it is pushed, and that the registry never holds an unscanned image (Section 3, item 13).
   - Give the build namespace an egress policy of its own (registry and package hosts only).
   - Add to the spike's bar, or to F-051's "done when": a box starts from a snapshot and sees its repos.
6. **ADR 0030 and ADR 0032: the OpenCode password sentence.** ADR 0030 says spike 3 will try to read the password from the process list, `/proc/<pid>/environ` and `/proc/<pid>/cmdline` (`0030…md:64`), and ADR 0032 says spike 3 tests the password's secrecy against a self-approval through the port (`0032…md:19`). The first can't be done as written (Section 3, item 11). Reword it to what can be tested: a call with no password fails, and the password isn't in any process's `environ` or `cmdline` where it can be seen. First find out how `opencode acp` gets its password, which spike 1 left open. If it honors `OPENCODE_SERVER_PASSWORD` (unverified for `acp`), the init can set a marker as the password and the `proc` check can search for it, through `/proc/<pid>/mem` as well.
7. **F-116, and the checklist behind it.** F-116 says "a test from a shell in the agent's container proves each one". Add a positive control for each destination, and a check that tells an enforcing cluster from one that isn't: a control pod that must be refused. Treat a timeout as inconclusive and not as BLOCKED, or require a refusal for the policy-backed checks. Probe the box network's gateway.
8. **F-094, F-039 and the install docs: a minimum Kubernetes version.** The pod's Postgres is a native sidecar, so the `kubernetes` executor needs a cluster that has it: on by default since v1.29 and stable in v1.33 (Section 2, V1). State the version in the configuration reference.
9. **The bridge and stop path, for milestone 1's issue 22.** Give every bridge request a deadline, and give stop a last step that removes the container when the init doesn't answer (Section 3, item 13). Fix the stale pointer in `agent-host.ts` while the spike is open.
10. **The `yaml` dev dependency (ISC).** It is awaiting the maintainer's yes (`README:245`; `AGENTS.md`, "Ask before adding a dependency"). It's the spike's own, and the product has no use for it. Either approve it for the spike or let a small reader replace it.
11. **Nothing to change in ADR 0046's split of images, but its mechanism differs.** The spike writes the base and runner images only (the server image isn't in it), and the split matches the ADR (`0046…md:29,32`). The pinned checksum I checked matches: the base image's sha512 for the linux-x64 tarball equals the lockfile's (Facts). The mechanism is not the ADR's: the ADR says the image installs `@opencode/cli` at an exact version with install scripts off and checks the binary's SHA-256 (`0046…md:31`). The spike's base image downloads the platform package's tarball with `curl`, checks its sha512, and takes the binary's sha256 from that same build unless `OPENCODE_BIN_SHA256` is passed (`Dockerfile.base:16-32,65-72`). Neither image was built.
