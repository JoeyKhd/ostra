## Notes

- **Ticket 04 (2026-11-20)** built the agent contract suite's refine cases (`packages/adapter-sdk/src/testing/agent-team-cases.ts`), which run on the scripted fakes in `fake-agent.test.ts`: a push from a folder whose `origin` is fetch-only, as a refine task's git proxy is, is refused and no `git-receive-pack` reaches the upstream (`startGitUpstream` gains `fetchOnly`); `submit_draft` is listed for a refine task and absent for a code task (by the tool sets of protocol minor 5); the drafting fake's draft reaches the fake core's `/draft` by the protocol's schema, and a `limit-reached` refusal reaches the agent in the protocol's words. They live in a suite file, so they're named in the parity table (`parity.ts`), not cited here. The runner's read-only git proxy and the sidecar's tool are tickets 22 and 23; core's draft, ticket 15. Break-its: letting the fetch-only upstream take a push failed the read-only case; listing `submit_draft` for every kind failed the tools case; answering a draft as saved whatever the refusal switch said failed the drafting case.
- **Ticket 07 (2026-11-20)**, Linear's adapter: "Update ticket" writes the description through `issueUpdate(description)` (`updateTicket`), exactly as given, and refuses `acceptanceCriteria` as `invalid-input` before any call, since Linear has no field for them (`ticketFields.acceptanceCriteria: false`: core writes them into the description). A member's image goes through Linear's upload (`fileUpload`, a PUT of the bytes to the signed URL with only the headers Linear signed, then `attachmentCreate` with the asset URL), capped at 10 MiB (`MAX_ATTACHMENT_BYTES`); the fake Linear gained `fileUpload` and its upload target for this, and the file downloads back byte for byte. `defaultReadyStatus` drafts the board's "ready" status (the first `unstarted` one by position: "Todo" on `OST`). Sub-tickets are sub-issues (F-077). The rows stay `partial`: the draft, its editor and the "Update ticket" and "Mark ready" writes are core's and the panel's (tickets 15, 27, 34).
- **Ticket 09 (2026-11-20)**, OpenCode's adapter: `PrepareLaunchInput` gains `kind`, `allowPrototyping` and `tools` (additive, `@ostra/adapter-sdk`), and OpenCode's config maps them. A refine task's edits are denied after every ask unless its profile allows prototyping (the built-in Refine profile doesn't); the shell stays allowed, since the box contains it (ADR 0031), and `external_directory` stays denied last. ostra's tools the task's sets don't name are denied (`ostra_submit_draft` and the others), which OpenCode 2.3.2 takes as "not offered": they leave the model's tool list. OpenCode reports a shell command that exits non-zero as `completed`, with the exit in `rawOutput.metadata.exit`; the adapter now reads it as a failed call, so a push the fetch-only remote refused shows in the event log as a failed shell call. Ticket 04's team cases all run on the pinned OpenCode with the stub model, on both API formats (the fixture's `team` probes, `stub-scenarios.ts`), and the parity table names them for OpenCode. The rows stay `partial`: the refine task's start, its read-only git proxy and the runner's launch are tickets 15, 22 and 23.
- **Ticket 15 (2026-11-20)** built refine drafts in core: the built-in Refine and Review profiles (`ensureBuiltInKindProfilesInTx`, seeded with each new organization and by `profiles.seed-built-in` for every existing one at core's start; they can't be archived, and they're each project's refine and review defaults); a refine task on a ticket (`startTicketTask` with `kind: "refine"`, which writes nothing to the ticket) with the refine prompt and the `draft` and `memory` tools; `POST /runner/v1/tasks/:taskId/draft` (`apps/core/src/runner-http/draft.ts`, the task token's task, `wrong-kind`, `invalid`, `limit-reached`); the turn's end (`handInDraftInTx` in `recordWorkSaved`); `editDraft`, `addDraftImage`, `applyDraft` with `draft.apply` (`apps/core/src/refine/apply.ts`) and `markTicketReady` through the ticket outbox's new `move` target `ready`. The cases run the shipped Linear adapter against the fake Linear, and the Jira fake.
- **Why `partial`:** the git proxy's read-only mode and the sidecar's `submit_draft` are the runner's (ticket 22), the draft's screen and its API are tickets 27 and 34, and "Create ticket" for a prompt refine task (F-097's path with the draft) isn't built yet. The profile's edit is milestone 3's `saveAgentProfile`, which refuses only the generic built-in one; its case belongs to ticket 27's API tests.
- **Ticket 22 (2026-11-20)**, the runner. A refine or review task's git proxy runs in milestone 1's read-only mode (`pushesWork` in `apps/runner/src/task-host/task-run.ts`): the agent's push of the task's branch and of its hidden ref are both refused at the proxy, and the upstream sees no request of either. After a turn the runner commits nothing and pushes nothing, not the branch and not the hidden ref (Q221); `session.saved` names no head, and the session archive still goes up, so a reopen restores the conversation. The sidecar's MCP server serves exactly the spec's tool sets (`tools`), and `submit_draft` forwards the protocol's draft to core's `/runner/v1/tasks/:taskId/draft` with the link's token (`teamLink`, `server-link.ts`), answering in the protocol's words, refusals included; core unreachable, it says nothing was saved. The same cases run on `host` and on `docker` as a box's sidecar drives it (`DockerExecutor` through the real bridge, the proxy and the tools in the sidecar). The spec carries no "allows prototyping" field yet, so the runner's launch leaves `allowPrototyping` out (`false`: the built-in Refine profile's). With core's endpoint (ticket 15) the draft row is `proved`: the tool's input and core's endpoint parse the same protocol schema. The read-only row stays `partial` until the proxy runs on a real box network on Linux with Docker (F-017's live run, spec section 9.1).
