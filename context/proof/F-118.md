Notes (2026-11-20, milestone 5's ticket 23): the charts are `deploy/helm/ostra-server` and `deploy/helm/ostra-runner`. Their values are Zod schemas (`packages/deploy-checks/src/helm/values.ts`), generated to each chart's `values.schema.json` (draft-07, strict objects), so Helm refuses an install that lacks a required value or mistypes a key (seen in the render runs). `pnpm check:helm` runs the checks that need no Helm everywhere; where `helm` is on the PATH it also runs `helm lint --strict` and `helm template` of both charts with every file in `examples/` (one with only the required values), checks the rendered manifests read with `@kubernetes/client-node`'s `loadAllYaml` (`rendered.ts`: no cluster role, a Role and RoleBinding in the box and build namespaces only with `NEEDED_ACCESS` and no write on network policies, the baseline and build policies equal to `baselineEgressPolicy` and `buildEgressPolicy`, the runner's join token from the admin's secret, one shared server secret with the three keys made once and kept, web and core with their replicas, the ingress's idle timeout), refuses both charts on Kubernetes 1.28, and compares each render with the one kept in `context/specs/m5-the-fleet/demo/helm/<chart>/`, which the CI tests read. It ran here with Helm v4.3.2 (`check-helm.log`). The `ostra-runner` deployment's `--executor kubernetes` start is ticket 20's runner.

Every row stays `partial` until ticket 35's `live-kind` job installs both charts on kind with only their required values (the server against a Postgres container, the runner joining with the chart's secret) and keeps its log here.
