## Notes

- **Rows 5 and 6 are partial** (milestone 4's ticket 06): the index builder and the block's renderer, as pure code. That only a read moves a note's last use is ticket 15's `memory.used` ingest; that the block reaches the agent, ticket 07's.
- 2026-11-19, ticket 02 (m4): three rows are `partial`, for the adapter contract on the fakes. `AgentCapabilities.memory` (`mcp` or `index-only`), `PrepareLaunchInput.memory` (`{ block, tools }`) and `composeLaunchInstructions` (the profile's instructions, the repos side by side, the block); the scripted fakes call `memory_search`, `memory_read` and `memory_propose` on the MCP server their config names, a third fake is `index-only`, and `startFakeMemoryCore` (`@ostra/adapter-sdk/testing`) answers the sidecar's memory endpoints by the protocol's minor-3 schemas behind a stand-in for the sidecar's MCP server. The contract suite runs the same cases on every agent (`packages/adapter-sdk/src/testing/agent-memory-cases.ts`); the rows cite the fakes' own tests. OpenCode (ticket 07), core's endpoints and spec (ticket 15) and the sidecar's MCP server (ticket 20) prove the rest. The native-memory row stays `missing`: the base class states the rule and both fakes and OpenCode say they have none, and its contract case comes with the Claude Code adapter, the first agent with native memory.
- 2026-11-19, ticket 07 (m4): OpenCode passes the suite's memory cases on both stubs (the block and no repo touched, the three tools listed and round-tripping through the fake core, two repos side by side), and has its own cases above. Its instructions file holds the profile's instructions, its skills, the repos and then the block, and is named before the repos' own `AGENTS.md`; ostra's MCP server is written with `codemode: false`, so OpenCode lists `ostra_memory_search`, `ostra_memory_read` and `ostra_memory_propose` by name. The live run on the development model called `memory_search` and `memory_propose` when asked (the evidence file). Rows 1 and 2 stay `partial` for core's spec (ticket 15) and the sidecar's real MCP server (ticket 20). OpenCode documents no memory feature of its own, so the native-memory row still waits for the Claude Code adapter.
- 2026-11-19, ticket 15 (m4): core builds the spec's `memory` section at each session's spec (`buildMemoryBlock` over the project's and the organization's active notes), with the tools only for an agent that declares `mcp` on a minor-3 runner, and folds the block, rendered without the tools, into a minor-2 runner's instructions. The sidecar's three endpoints (`apps/core/src/memory/endpoints.ts`) check the task token's task and lease, or a `host` lease's runner, and answer within the task's organization and project. `memory.used` is stored at ingest, and only `read` and `search` move a note's last use: row 5 is `proved`. Rows 1 to 3 stay `partial` until the sidecar's MCP server (ticket 20) carries the tools to a real agent through core.
- 2026-11-19, ticket 20 (m4): the runner's side. `prepareLaunch` gets the spec's `memory` block and `tools`; the runner reports the spec's `alwaysNoteIds` and `indexNoteIds` as two `memory.used` events once a session, before its first turn, to a minor-3 peer only. The sidecar's MCP server (`apps/runner/src/sidecar/mcp-tools.ts`) offers `memory_search`, `memory_read` and `memory_propose` beside `set_pull_request_text` when the spec's `tools` is true, parses each input with the protocol's schemas, and forwards it with the link's token (`MemoryLink` in `server-link.ts`: the runner's on `host`, the box's task token in a sidecar); a read is `memory.used` with `via: "search"` when the turn's search found the note, `read` otherwise. With core's section and endpoints (ticket 15), OpenCode (ticket 07) and the sidecar's server in place, rows 1 to 3 are `proved`: the spec carries the block, the runner hands it and the tools to the agent, and the tools reach core's endpoints with a token for that one task. Row 4 stays `partial` until the task page lists the notes (ticket 38); the runner's `memory.used` events are the data it reads.
- 2026-11-19, ticket 29 (m4): `tasks.memory` lists each session's `MemoryUse` rows (note, scope, how, when) and the task's proposals; the task page's list is ticket 38.
