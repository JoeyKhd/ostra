## Notes

- **Ticket 02 (2026-11-20)** built the contract and the fake Linear's agent sessions: the rows marked `partial` cite the fake's own tests, which show the rules the heartbeat and the stop path are built against (staleness after 30 silent minutes, recovered by the next activity; a personal key's activity refused 403; a stop as a `prompted` event with `signal: "stop"`). They prove the fake, not ostra's turn: ticket 13 (core's agent mode) and ticket 38 (the harness) prove the rest against it.
- **The live run is not done.** It needs the maintainer's authorize click (ticket 40). The plan, from spike 5's four real-Linear bullets: on `ostra-test` (team OST), re-authorize the existing app with `app:assignable` and `app:mentionable` and `update_scopes_on_existing_token=true`; delegate 50 tickets to the app and record each `created` webhook's ack and first activity; press "Send stop request" on one session and send a follow-up on another, from a signed-in person; leave one session silent for 35 minutes with the heartbeat on, and check it never shows stale. Its log goes in `context/specs/m6-whole-team/demo/` and is cited here as `live:`.
- **Ticket 07 (2026-11-20)**, Linear's adapter: `parseAgentSessionEvent` reads `created` (a delegation, or a mention with its comment) and `prompted` (a follow-up, or `signal: "stop"`) loosely, tolerating fields it doesn't know; `postAgentActivity` posts each kind through `agentActivityCreate` with Linear's content shape and `ephemeral` (a thought or an action only), once per key: its client-made ID is a UUID derived from the session and the key (`activityIdFor`), looked up among the session's activities before the post and again when Linear refuses it, so a retry after a lost answer posts nothing more; a personal key's post is `unauthorized` after one call; `setAgentSessionLink` sets `externalUrls`; `getUser` reads `user(id)`; `authorizeUrl` asks for the agent scopes with `update_scopes_on_existing_token=true`, and the fake's install gains them. Linear's API has no field that reads a token's scopes back, so the granted scopes are the token answer's (`LinearTokenSet.scopes`), and `missingAgentScopes` says which agent scopes they lack. `postThreadReply` (ported from spike 5) posts a follow-up as a thread reply for ticket 38's harness. The tracker suite's session cases run on Linear's adapter with `milestone6: true`. Rows stay `partial`: the task, the fast lane and the turn are core's (ticket 13), and the live run waits for ticket 40.
- **Ticket 13 (2026-11-20)** built agent mode in core. The inbox sends a session's event to `linear.agent-event` in the claim's own transaction (`apps/core/src/webhooks/inbox.ts`). `apps/core/src/linear/agent-mode/events.ts` makes the session, starts the task through ticket 14's `startFromTrackerInTx` (a matched member's own start, or an outside task), writes the first thought with them, and posts it at once. A stop goes through milestone 2's stop path (the task stopped, a `stop` command for the lease's runner in the outbox) with one final response. A follow-up from a matched member is their message with the intent `linear-follow-up`, sent after the turn. `outbox.ts` posts with the app's token only (a connection holding a person's key posts nothing) and moves the heartbeat on with every post; `linear.heartbeat` sweeps once a minute. A task's moves, its PRs and the panel's stop tell the session through the domain's copy, in their own transactions (`packages/domain/src/linear/agent-session-moments.ts`). "Turn on agent mode" is `createLinearAuthorizeUrl(..., { agentMode: true })` and `authorizeLinear`, which refuses a token without the scopes; "Start from Linear" is `setBoardAgentMode`.
- **What these tests run against:** the fake Linear server (ticket 02) and Postgres, through the shipped `LinearAdapter` (ticket 07) as core builds it, so the fake answers each call as Linear would (a personal key's post refused, a repeated activity ID the same activity). The rows stay `partial` for the API and the screens (tickets 26 and 33) and the live run.
- **A difference from the ticket:** a claim whose insert fails answers 503 (milestone 2's inbox), not 500. The case checks for any non-2xx, which is what makes Linear retry.
- **The break-its were run one at a time, each failed its case, and each was restored.** The two the ticket names: `linear.agent-event` enqueued outside and before the claim's insert, and the heartbeat's due time not moved by a post.
- **Ticket 26 (2026-11-20)** added agent mode's API: `linear.enableAgentMode` (an organization admin's, from their own session: Linear's consent URL with agent mode's scopes, `actor=app` and PKCE, or on at once for a token that holds them; refused for a polling connection), `linear.setBoardAgentMode` (a project admin's, one board per team, the refusal naming the project that holds it), and `linear.status`'s `agentMode` (its scopes, reach, next renewal, boards, session counts and the last ten sessions, who started each by the tracker's name and whether they matched). The live run is still the maintainer's (ticket 40).
