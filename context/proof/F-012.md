## Notes

- **Ticket 02 (2026-11-20)** built the contract and the fake Linear's agent sessions: the rows marked `partial` cite the fake's own tests, which show the rules the heartbeat and the stop path are built against (staleness after 30 silent minutes, recovered by the next activity; a personal key's activity refused 403; a stop as a `prompted` event with `signal: "stop"`). They prove the fake, not ostra's turn: ticket 13 (core's agent mode) and ticket 38 (the harness) prove the rest against it.
- **The live run is not done.** It needs the maintainer's authorize click (ticket 40). The plan, from spike 5's four real-Linear bullets: on `ostra-test` (team OST), re-authorize the existing app with `app:assignable` and `app:mentionable` and `update_scopes_on_existing_token=true`; delegate 50 tickets to the app and record each `created` webhook's ack and first activity; press "Send stop request" on one session and send a follow-up on another, from a signed-in person; leave one session silent for 35 minutes with the heartbeat on, and check it never shows stale. Its log goes in `context/specs/m6-whole-team/demo/` and is cited here as `live:`.
- **Ticket 07 (2026-11-20)**, Linear's adapter: `parseAgentSessionEvent` reads `created` (a delegation, or a mention with its comment) and `prompted` (a follow-up, or `signal: "stop"`) loosely, tolerating fields it doesn't know; `postAgentActivity` posts each kind through `agentActivityCreate` with Linear's content shape and `ephemeral` (a thought or an action only), once per key: its client-made ID is a UUID derived from the session and the key (`activityIdFor`), looked up among the session's activities before the post and again when Linear refuses it, so a retry after a lost answer posts nothing more; a personal key's post is `unauthorized` after one call; `setAgentSessionLink` sets `externalUrls`; `getUser` reads `user(id)`; `authorizeUrl` asks for the agent scopes with `update_scopes_on_existing_token=true`, and the fake's install gains them. Linear's API has no field that reads a token's scopes back, so the granted scopes are the token answer's (`LinearTokenSet.scopes`), and `missingAgentScopes` says which agent scopes they lack. `postThreadReply` (ported from spike 5) posts a follow-up as a thread reply for ticket 38's harness. The tracker suite's session cases run on Linear's adapter with `milestone6: true`. Rows stay `partial`: the task, the fast lane and the turn are core's (ticket 13), and the live run waits for ticket 40.
- **Ticket 13 (2026-11-20)** built agent mode in core. The inbox sends a session's event to `linear.agent-event` in the claim's own transaction (`apps/core/src/webhooks/inbox.ts`). `apps/core/src/linear/agent-mode/events.ts` makes the session, starts the task through ticket 14's `startFromTrackerInTx` (a matched member's own start, or an outside task), writes the first thought with them, and posts it at once. A stop goes through milestone 2's stop path (the task stopped, a `stop` command for the lease's runner in the outbox) with one final response. A follow-up from a matched member is their message with the intent `linear-follow-up`, sent after the turn. `outbox.ts` posts with the app's token only (a connection holding a person's key posts nothing) and moves the heartbeat on with every post; `linear.heartbeat` sweeps once a minute. A task's moves, its PRs and the panel's stop tell the session through the domain's copy, in their own transactions (`packages/domain/src/linear/agent-session-moments.ts`). "Turn on agent mode" is `createLinearAuthorizeUrl(..., { agentMode: true })` and `authorizeLinear`, which refuses a token without the scopes; "Start from Linear" is `setBoardAgentMode`.
- **What these tests run against:** the fake Linear server (ticket 02) and Postgres, through the shipped `LinearAdapter` (ticket 07) as core builds it, so the fake answers each call as Linear would (a personal key's post refused, a repeated activity ID the same activity). The rows stay `partial` for the API and the screens (tickets 26 and 33) and the live run.
- **A difference from the ticket:** a claim whose insert fails answers 503 (milestone 2's inbox), not 500. The case checks for any non-2xx, which is what makes Linear retry.
- **The break-its were run one at a time, each failed its case, and each was restored.** The two the ticket names: `linear.agent-event` enqueued outside and before the claim's insert, and the heartbeat's due time not moved by a post.
- **Ticket 26 (2026-11-20)** added agent mode's API: `linear.enableAgentMode` (an organization admin's, from their own session: Linear's consent URL with agent mode's scopes, `actor=app` and PKCE, or on at once for a token that holds them; refused for a polling connection), `linear.setBoardAgentMode` (a project admin's, one board per team, the refusal naming the project that holds it), and `linear.status`'s `agentMode` (its scopes, reach, next renewal, boards, session counts and the last ten sessions, who started each by the tracker's name and whether they matched). The live run is still the maintainer's (ticket 40).
- **Ticket 33 (2026-11-20)** built the panel's agent mode on "Connect Linear" (`apps/web/src/components/linear/agent-mode.tsx`): its state, the public address's check, the app user, the granted scopes, the token's renewal, "Turn on agent mode" (`linear.enableAgentMode`: to Linear's consent page, or on at once when the token already holds the scopes), each board's "Start from Linear" (also on the project's Boards page) and the last session events; and the Needs approval screens (F-040). `apps/web/e2e/20-agent-mode.spec.ts` runs it on the stack's fake Linear as the connection, with the token as the consent leaves it: the consent page itself is linear.app's, which the stack doesn't reach, and the panel's OAuth endpoints aren't configurable, so the redirect to it is unexercised here. Live plan (ticket 40, unchanged): the maintainer presses "Turn on agent mode" on the dev install and authorizes on linear.app; the page then shows `On` with both scopes, and step 10 of the demo delegates tickets from Linear. F-012 stays `building` until that run.
- **Ticket 38 (2026-11-20), the harness:** `e2e/m6-linear-agent-mode/`, `pnpm e2e:linear-agent-mode` (`docs/development.md`). Spike 5's `real-run.ts`, `thread-reply.ts` and its scenarios' judges, ported to run against ostra itself: core's inbox, the claim, the queue, the outbox and the heartbeat, on Postgres, behind the tunnel. Its phases (`src/phases.ts`), judges (`src/judge.ts`, the spike's `evaluate.ts`) and ostra's side (`src/ostra-side.ts`) are shared by the live run and its rehearsal.
- **Without the token it skips cleanly**, as this machine shows today: `pnpm e2e:linear-agent-mode` printed `skipped: no app token` and ended 0 on 2026-11-20, since `~/.config/ostra-dev/linear.env` has no `LINEAR_REFRESH_TOKEN` (ticket 40's step 1 is the maintainer's Authorize click). The skip test runs it as a process and sees nothing asked of Linear.
- **The rehearsal (CI):** every phase through the same code against core as its own process and the fake Linear server. It passed: the install (the app's own user, not the admin, with the agent scopes); 50 delegations, 250 ms apart, each acked in under 0.03 s and each first thought posted 0.4 s (p50) to 4.4 s (max) after the 200, no runner online, every session active, then one bulk reject ending each with one final response; a follow-up as a thread reply by the key's user (on a session a mention started: a delegation's session hangs from no comment, so it has no thread); a stop pressed by a script, with `signal: stop`, the task stopped and one final response; and 35 minutes of Linear's clock (the fake's at 10 times the wall clock, core's heartbeat at a minute) with the session never stale, a heartbeat and nothing else posted, ending complete. One check doesn't run there, by design: with no runner the follow-up's task waits queued, and a queued task takes no message (`not-reopenable`), so "it reached the task" is reported not run. The live run signs a runner in before bullet 3 and gives the follow-up's and the stop's tickets a turn that runs on the stub model.
- **Why the row stays `partial`:** the rehearsal proves the harness and ostra's side on the fake; only the live run proves the bullets on Linear. **The plan for the live run**, once the maintainer has pressed Authorize and saved `LINEAR_REFRESH_TOKEN`: add `LINEAR_APP_CONNECTION_ID` (the ID at the end of the app's webhook URL) to `linear.env`, point the tunnel in `tunnel.env` at the harness's core (8831), load `github.env` and `github-test.env`, and run `pnpm e2e:linear-agent-mode --record` on a checkout whose `.ostra-dev/` may be emptied. It refreshes the token and writes the rotated one back first; checks the install with `viewer.app` and the admin's key; delegates 50 tickets in `OST` with no runner online and rejects them all at once; signs a runner in, sends the follow-up as a thread reply and asks the maintainer to press "Send stop request" on the ticket it names (waiting 30 minutes, reported not run without a press, never passed); watches a 35-minute silent turn on the stub model, polling each minute and every 10 s from minute 28; and keeps the log (IDs, counts, times) in `context/specs/m6-whole-team/demo/linear-agent-mode.log`, to be cited here as `live:` with the results in ADR 0013's amendment. It has never run against Linear.
- **Found by the rehearsal:** a follow-up from Linear on a task still queued (no runner free yet) is dropped: `sendMemberMessageInTx` reopens it, the reopen answers `not-reopenable`, and core logs `linear.follow-up-refused` and posts nothing to the session, so the person in Linear sees no answer. Not changed here (ticket 13's path); noted for the maintainer.
- **Ticket 41 (2026-11-20), the session's link:** core now links a Linear agent session to its task's page. `sendActivity` (`apps/core/src/linear/agent-mode/outbox.ts`) calls `setAgentSessionLink` with the session's first post, where the tracker declares `agentSessionLink`, before marking it sent: a link Linear may still take is retried with the post (which its key keeps from posting twice); a refusal is logged and the posts go on. A session with no task (no board takes its team) is never linked.
