Notes (2026-11-19, milestone 5's ticket 02): the executor contract gains the capability `registry` (`required`, `optional`, `none`), `create`'s `image` (by digest, with its pull credential) and `buildSnapshot`'s `push` and `digest`. No row is proved yet: the pushes and pulls themselves are tickets 09 (`docker`), 07 and 21 (`kubernetes`). The suite's case "F-120: a box from a registry image is pulled by digest with its credential, which is in no container's environment, files or process list; with no registry an image is refused" is what each of them passes: it failed when the tiny executor's fleet variant pulled by tag, when the pull token was written into the box's files, and when `refuseUnfitBox` let an image through on `registry: "none"`. Until ticket 09, `docker` refuses a build asked to push (`packages/adapters/adapter-executor-docker/src/docker-snapshot-box.test.ts` > "F-120: until docker pushes (ticket 09), a build asked to push to a registry is refused, and nothing is built"). The suite's cases live in `packages/adapter-sdk/src/testing/executor-suite.ts`, which isn't a test file, so they are named here rather than cited: `defineExecutorContractSuite` runs them in CI from `packages/adapter-sdk/src/contract-suites.test.ts` (the tiny executor and its fleet variant), `packages/adapters/adapter-executor-host/src/host-executor.contract.test.ts` and `packages/adapters/adapter-executor-docker/src/docker-executor.contract.test.ts`.

Notes (2026-11-19, milestone 5's ticket 06): the fake OCI registry (`packages/adapter-sdk/src/testing/net/fake-oci-registry.ts`, Basic or bearer auth, a push-only and a pull-only credential) is the registry tickets 09, 17, 21 and 28 test against; it proves no row by itself. Notes (2026-11-19, milestone 5's ticket 09): `docker` pushes and pulls. A build with `push` tags the scanned image with the registry's name and pushes it through the Engine API with the push credential in the call's `X-Registry-Auth` header (never `docker login`, so nothing lands in `~/.docker/config.json`), only after the scan found nothing (ADR 0038), and answers the registry's manifest digest. A box with an image pulls `ref@digest` with the pull credential the same way, before anything of the box is made, and its agent's container runs exactly that digest. The executor contract suite's case "F-120: a box from a registry image is pulled by digest with its credential, which is in no container's environment, files or process list; with no registry an image is refused" runs on `docker` (the fake Engine has no processes, so its process list is the live suite's). The second row stays `partial` for `kubernetes` (tickets 07, 21) and for the live case "F-120: an image pushed to registry:2 with the push credential is pulled by digest on a second Engine, and no credential is left in a file" in `packages/adapters/adapter-executor-docker/src/docker.live.test.ts`, run by ticket 35's Linux job. The third row stays `partial` until a real Docker host builds and keeps one (milestone 3's live `snapshot.live.test.ts`, ticket 35). The break-it for the third row: the test asserts `engine.pulls` is empty.

Notes (2026-11-20, milestone 5's ticket 17): core's side. `setRegistry` (`packages/domain/src/use-cases/registry.ts`) stores the push and pull credentials in the secret store (the row holds references), writes `registry.set` and queues `registry.check` for the setting's version in one transaction; only an admin may. `registry.check` is core's own calls to the distribution API (`apps/core/src/registry/probe.ts`): `/v2/`, the token flow, an upload started and cancelled for the push scope, and an existing snapshot's manifest (or the tag list) for the pull scope; nothing is pushed, and the result is kept with its time. With a registry set, a build goes to a `kubernetes` runner of the project's pools with `builder: "buildkit"`, else a `docker` runner at minor 4, and the command carries `push.ref`; `snapshot.built` marks it ready with `pushedAt` and the registry's name. A `kubernetes` pool without one builds nothing, and its tasks wait with `needs-registry`. `POST /runner/v1/snapshots/:id/push-credential` answers the builder only while it builds; `POST /runner/v1/tasks/:taskId/pull-credential` the runner holding the task's current lease at that epoch, and none with `node` auth. Each issuance is one `registry.credential-issued` entry. A dispatch to a runner that pulls from the registry names the project's ready snapshot by digest. The first row stays `partial` until the panel sets it (tickets 28 and 33); the others until the live runs of ticket 35.

Notes (2026-11-20, milestone 5's ticket 28): the panel's API has the registry, for organization admins: `registry.get` (the address, the prefix, the auth kind, whether each credential is set, the last check with its time, the pools whose runners need a registry, and the organization's snapshots in it by digest), `registry.set` (a credential left out keeps the stored one), `registry.clear` (`clearRegistry`: the row and its credentials go, the snapshots stop naming it, the images stay in the registry) and `registry.check`, which queues `registry.check` for the settings' version (the row's `updatedAt`, which `setRegistry` now sets to the version its own check is queued for) and returns at once. The environment's snapshot section gives the ready snapshot's registry reference by digest, its builder and its runner. The row stays `partial` until the panel's Registry page sets it (ticket 33) and a real registry (GHCR, ECR or Harbor) is set in ticket 35's or the demo's run.
