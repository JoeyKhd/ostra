Notes:
- Ticket 26 (core's scheduling) proves its half of the second and fourth rows: each trigger makes one build a minute at most, sent as a `snapshot-build` command to an online `docker` runner of the project's pools, whose setup secrets (and only those) come from `POST /runner/v1/snapshots/:id/credentials` for that runner alone; a `secret-found` failure marks the scan failed and leaves the previous ready snapshot in use. The image build, the mount and the scan are ticket 14's, and their live run waits for the Linux machine, so both rows stay `partial`. The environment's change and Rebuild are enqueued by the API (ticket 40): an environment's save, a service's change and Rebuild each queue one `snapshot.schedule`; `environments.snapshot.get` reads the state back ("F-051: the snapshot's state reads back: none, queued waiting for a docker runner, building, ready on its runner, and the last failure's reason" in `packages/api/src/routers/environment-services.test.ts`).
- Also proved for ticket 26, beyond the "done when": the spec names the ready snapshot only to the runner that keeps it and no runner is passed over for lacking it ("F-051: the spec names the ready snapshot only to the runner that holds it, and no runner is passed over for lacking it"), a `host` runner's spec names the project's dependency cache ("F-051: a host runner's spec names the project's dependency cache"), a build waits queued for a `docker` runner and one refused or lost goes back to the queue, and another organization's snapshots are untouched, all in `apps/core/src/snapshots/snapshots.test.ts`.
- Ticket 48, 2026-11-19: the panel's Snapshot group on the environment page (state, when and on which runner it was built, why, the scan, the digest, the last failure's reason, Rebuild; on `host` only, `Worktree and dependency cache`). Its words are tested in `apps/web/src/components/projects/environment-services-words.test.ts` ("F-051: the snapshot panel says why a build ran, who rebuilt it, and why one failed"), and the page is compared with its target in `context/specs/m3-step-in/evidence/environment-services-built.png`. No row of the "done when" is about the panel, so the rows are unchanged.
- Ticket 14, 2026-11-19: the `docker` half, against the fake Engine API and a fake BuildKit (the Dockerfile, the secrets as BuildKit mounts for their repo's step only, the scan of every layer raw and in base64 with its negative control, the image deleted on `secret-found`, the build kept by its label and digest; a box from the snapshot made before its sidecar so the image fills the new task volume, the sidecar moving the checkouts in, fetching and running the incremental setup, or falling back), and on the pool runner (the `snapshot-build` command accepted at once and built in turn, its result a `runner-event` frame sent again on each new connection for an hour, the box started from the kept image by its digest). No registry: the image stays in the runner's own Docker and is never pushed (F-120 is milestone 5), so "before it is pushed" holds as "before it is used". The live build, scan and box (`packages/adapters/adapter-executor-docker/src/snapshot/snapshot.live.test.ts`, gated on a Docker host and the built images) wait for the Linux machine, so these rows stay `partial`.

Notes (2026-11-19, milestone 5's ticket 08): on `kubernetes` the build's pod runs in the build namespace (`OSTRA_K8S_BUILD_NAMESPACE`), never beside the boxes, and the executor builds nothing there unless a NetworkPolicy restricts the builds' egress (`buildEgressPolicy` is the one the runner chart renders: DNS, the registry, the code and package hosts).
