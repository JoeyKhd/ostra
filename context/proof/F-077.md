## Notes

- **Ticket 07 (2026-11-20)**, Linear's adapter: `createTicket` with a `parent` makes a sub-issue (`issueCreate` with `parentId`), refused as `not-found` with nothing created when the parent is on another board; `getTicketContext` reads each child with `open` from its state type, so a done child is closed. The test builds a three-level tree and reads it the way core's walk does (ticket 12), one `getTicketContext` per ticket, each one `issue` query. The ticket asked for "at most one query per level": the interface reads a ticket's context one ticket at a time (ticket 02 kept milestone 2's shape), so it's one query per ticket read; core's walk decides how many it reads. Both rows stay `partial`: the start of one task per leaf and the parent's page are core's and the panel's (tickets 12, 25, 32). The tracker suite's sub-issue case runs on Linear's adapter too (`linear-adapter.test.ts`, `milestone6: true`).
- **Ticket 12 (2026-11-20)**, core: `startSubIssues` (`packages/domain/src/starts/sub-issues.ts`, core's tracker lookup in `apps/core/src/starts/sub-issues.ts`) reads the parent's tree through `getTicketContext` to `OSTRA_SUB_ISSUES_DEPTH` levels, upserts a child not cached yet, keeps the open leaves on the project's boards and starts each through `startTask` (the one-active-task index) with `parentTicketId`, in its own transaction. Over `OSTRA_SUB_ISSUES_MAX` it starts nothing and gives the count. `startTask` refuses a code start on a ticket whose open children are cached (`has-sub-issues`), so no path (a member's, a rule's, a schedule's or a bulk start's) gives a parent a code task; a refine start refines the parent. Tested on the fake Linear server through Linear's adapter and on the Jira fake's sub-tasks.
- The parent's progress comment (`packages/domain/src/tickets/parent-progress.ts`, the writer's parent branch in `apps/core/src/tracker/writer.ts`): one `comment` row per parent, ever (its key is the parent's), and an edit per child's change, rendered from the children's states and PRs when the writer applies it; the writer's coalescing skips an edit a newer one supersedes.
- A child's prompt gains the parent's acceptance criteria from its accepted refine draft (applied or marked ready), as a new block of the ticket template (`parentCriteria`, F-064).
- The second row stays `partial` until the parent's page lists its children (tickets 25 and 32).
- A deviation from ticket 12's text: the leaves start directly, each in its own transaction, not as a `BulkStart` (`bulkStartId` is always `null`): the migration has no column for a bulk start's parent, which each leaf's `parentTicketId` needs. A replayed request starts nothing twice (each leaf's task is found).
