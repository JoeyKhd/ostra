## Notes

- **Ticket 04 (2026-11-20)** built the agent contract suite's automatic-turn case (`packages/adapter-sdk/src/testing/agent-team-cases.ts`), ported from spike 10: the asking fake asks one ACP elicitation mid-turn; answered with the fixed neutral reply it carries on and ends its turn `end_turn` with the reply in its message; declined, the control, it ends the turn `cancelled`, as OpenCode's question tool did. It runs on the four scripted fakes in `fake-agent.test.ts`, and is named in the parity table (`parity.ts`), not cited, being in a suite file. The runner sending the reply in an automatic turn is ticket 23's, and the rounds and caps ticket 18's. The spec's new `elicitation` capability is the existing `elicitationForm`, which says the same thing (an agent that asks through ACP elicitations), so no second capability was added. Break-its: the fake carrying on after a decline failed the control; the fake ignoring the answer failed the neutral-reply case.
- **Ticket 06 (2026-11-20)** built the pure rounds (`packages/domain/src/review-loop/rounds.ts`): `roundAllowed` with each kind's cap and the 4 automatic turns together, `countRound`, and the reset on a person's action, which a "changes requested" round is; the round's lifecycle (started, held by the budget, capped); the findings round's prompt, blocking findings as data and nits listed after them; and the budget gate's origins `changes-requested` and `linear-follow-up` (ticket 05's commit). The rows stay `partial` until ticket 18 runs the rounds through the gate and the spend cap and raises needs you at a cap.
- **Ticket 18 (2026-11-20)** built the rounds in core: `round.start` (`apps/core/src/review-loop/rounds.ts`, the domain's `startRound` in `packages/domain/src/review-loop/start-round.ts`), in the task's lock: the caps since a person last acted (`OSTRA_CI_ROUNDS`, `OSTRA_REVIEW_ROUNDS`, `OSTRA_AUTOMATIC_TURNS`), then the budget gate as an automatic round (a closed gate holds it as `HeldTurn` and the round `held`; `budget.release` starts the held rounds oldest first, counting each then), then the task's spend cap, then the turn: a `steer` with `automatic: true` on the warm box when the session is idle and its runner speaks minor 5, else a fresh session, whose dispatch goes only to a minor-5 runner, with `automatic` on the dispatch and the spec. A cap reached moves the task to needs you (`round_cap`) for its driver, worded with the cap, and writes `round.capped` in the thread. A person's message, reopen, question answer, plan answer or approval answer zeroes the counters (`recordPersonActionInTx`). Row 5, the neutral reply, is the runner's (ticket 23).
- **Ticket 09 (2026-11-20)**, OpenCode's adapter: OpenCode's `question` tool reaches ostra as one ACP elicitation (`elicitationForm: true`, the capability the spec calls `elicitation`). On the pinned binary with the stub model, the fixed neutral reply in every field lets the turn carry on with it, and a decline ends the turn `cancelled`, as spike 10 found. The suite's two cases run on OpenCode on both API formats. The row stays `partial`: the runner's answer in an automatic turn, and its record, are ticket 23's.
- **Ticket 23 (2026-11-20)**, the runner. A turn is automatic when the spec's `automatic` says so for the session's first turn (a box's sidecar reads it from the spec, since its own dispatch carries none), or when every message that makes it up is a steer with `automatic: true`; one person's message makes the turn theirs, and so does a person's message steered into a running automatic turn. In an automatic turn, the agent's question gets `NEUTRAL_REPLY` at once, as an answer in every text field (a select's first option) and never a decline, and the runner emits `question.auto_answered` with the question's ID and the reply, not `question.asked`; the question's text is never logged. An approval in an automatic turn still follows the profile's rules and waits for a person. The cases run on `host` and on `docker` as a box's sidecar drives it. With OpenCode's own case (ticket 09) the row is `proved`; the demo's steps 6 and 12 show it live (ticket 39).
- **Ticket 28 (2026-11-20)**: `tasks.rounds` lists a task's rounds with their cause (a CI round's failing checks with their log files' names, a findings round's findings, a "changes requested" round's reviewer), their state, a capped round's reason (its kind's rounds or the automatic turns, from `round.capped`; else the spend cap) and a held round's budget. `packages/api/src/routers/review.test.ts` > "F-101: after a CI round and a findings round, each shows its cause, its state, and a capped one why" is its case; break-its: passing checks listed as causes, and every capped round called the spend cap's, each failed it. It's the panel's view of the rows above, not a condition of its own.
- **Ticket 35 (2026-11-20)**, the panel: the review screen (`apps/web/src/components/tasks/review/review-screen.tsx`, `/tasks/{id}/review`) reuses milestone 3's Changes tab with an AI review's findings on their lines ("Fix this", "Remember this"), and shows the ticket's criteria, the reviewers and the PR; the task page gains the stage line, "automatic turns N of 4", a card per round, the cap's needs-you with "Keep working" (milestone 3's `keepWorking`, which now answers a `round_cap` too) and the Rounds group; the Checks tab gains the code host's CI; a project gains Settings > Review. The Playwright cases (`apps/web/e2e/19-review.spec.ts`) seed the rows core's loop leaves after a CI round and a findings round (`seed-review-world.ts`, the reviewing fake's nit among them), since the e2e stack runs no agent; the loop itself is core's tests'.
- **Ticket 41 (2026-11-20):** the Status row names the stage the loop is at (`In review · CI running`, `· fixing CI`, `· waiting for a reviewer`): `statusWithSubState` in `apps/web/src/components/tasks/review/task-rounds.tsx`.
- **Review follow-up (2026-11-21, the maintainer's "all yes"; ADR 0058 amended)**, row 6: an AI review run again on a new head, because the last run never posted (a person pushed while it read the old head, ticket 17's `failReviewOnHeadMoveInTx`), is one of the task's review rounds. `startReviewInTx` (`packages/domain/src/review-loop/review.ts`) checks it against `OSTRA_REVIEW_ROUNDS` (`reviewRerunAllowed`, `rounds.ts`) before it makes the run: allowed, the counter rises (`countReviewRerun`; it isn't an automatic turn, since the coding agent takes none); at the cap, no run and no dispatch, the code task needs its driver with `round_cap`, the same item as every capped loop, worded by `reviewRerunCapSummary`. Core's `review.start` job reads the install's limits (`settings.team.roundLimits`). The first review of a loop, and a review of a round's fix (its last run posted), are no reruns.
