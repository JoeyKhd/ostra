## Notes

- 2026-11-19, ticket 02 (m4): ADR 0035's canary control, which milestone 1's suite lacked: a file outside the task's workspace, a scripted shell call (`cat`) that reads it, and the event log showing the call with its command and folder and its output. It runs in the agent contract suite for every agent with a `canary` probe (the three fakes now). The row stays `partial`: the audit log itself and the event log view are tickets 10 and 25.
- 2026-11-19, ticket 10 (m4): every audit write goes through `recordAudit` (`packages/domain/src/audit/record-audit.ts`), which keeps the actor's name, and every action is on the closed list in `packages/domain/src/audit/actions.ts`, which the type of `AuditInput.action` enforces. Each case of `every-action.test.ts` runs its procedure twice: once as it is, then on a database whose every transaction rolls back at its end, which must leave no entry. The cases cover a task's start, stop and takeover, an approval, the organization's name and a member's role, pools, join tokens, a runner's revoke, a project, model providers and agent profiles; `task.credentials-issued` is asserted by core's dispatch test through the credentials endpoint. The row stays `partial`: a budget's change (tickets 12, 27), a memory note's (tickets 16, 29), the invitation, membership, reset and project-access actions (tickets 22, 23) and `mcp-secret.issued` (ticket 20) are on the list, and each of those tickets adds its case to `every-action.test.ts`.
- 2026-11-19, ticket 25 (m4): `audit.list`, the CSV export (`/api/audit/export`, `serveAuditExport`, the list's query and access check, streamed in pages) and `tasks.eventLog`. *Admins can view and filter it* stays `partial` until the panel's page (ticket 34) shows it.
- 2026-11-19, ticket 34 (m4): the audit log (`/organization/audit`, and a project's in its settings) and the task's Event log tab, in the browser (`apps/web/e2e/12-audit.spec.ts`) on seeded entries written through `recordAudit`.
- 2026-11-20, review findings in `packages/api`: `audit.list` returns `entityLabel` (the live record's key or name, else a label in the entry's data, else the ID) and takes `actorKind` for the Actor filter's Runners and System; the CSV has the target's columns and is named `audit-<organization-slug>-<yyyy-mm-dd>.csv`. The panel showing the label and offering Runners and System is `apps/web`'s.
- 2026-11-20, ticket 41 (m4): the budgets' and the memory notes' entries joined the cases (`budget.set`, `budget.cleared`, `memory.note-created`, `memory.note-edited`, `memory.note-archived`), and the credentials' entry is checked for its runner (`apps/core/src/dispatch/dispatch.test.ts`).
- 2026-11-20, m4 gaps (after milestone 4's final check): the web view now draws what the API's `entityLabel` names. The Entity column shows the kind's word (`pool`, `provider`, `note`, `profile`; other kinds as stored) then the label, mono for a ticket key and pool, runner and provider names and sans for the rest, and an entity with no label its short ID; the panel reads `Task CALC-161`, linked by the kinds the log stores (`runner-pool`, `model-provider`, `agent-profile`, `memory-note`, which the old links missed), with `Entries about this pool`; the entity chip reads the label. The Actor menu lists removed members with ` (removed)`, then `Runners` and `System`, which filter by `actorKind`. Component and unit tests, seven break-its.
