## Notes

- **Ticket 03 (2026-11-20)** built the code host's side: `listCiResults` (other apps' check runs and statuses), `getCiLog` (a log's tail at most the cap, from the end, never in an error) and the `check_run`, `check_suite` and `status` webhook hints, with their cases in the contract suite on the fake code host. The cited test proves the shared tail cut every adapter uses; the reopening, the rounds and the caps are tickets 16, 18 and 23.
- **Ticket 08 (2026-11-20)**, GitHub's adapter: `listCiResults` pages `GET /commits/{sha}/check-runs` (every app's runs, each with its app's slug) and reads `GET /commits/{sha}/status`. `getCiLog` reads a GitHub Actions run's job log through `GET /actions/jobs/{id}/logs` (the App's `actions: read`), following its redirect to the signed download with no token and a `Range` of the last bytes, cut to the cap. Another app's run is its `output.summary` and `output.text`; a status is its description and target URL; a log GitHub expired is `{ found: false, reason: "expired" }`. The `check_run`, `check_suite` and `status` deliveries are `ci` hints with the head SHA. `appHealth` is `degraded`, naming them, when the App doesn't subscribe to them (an App made before milestone 6, until ticket 40's step 2). The code host suite's CI cases run on GitHub's adapter against the fake GitHub (`milestone6Fixture` in `github-adapter.test.ts`); its break-its: dropping the statuses failed the CI-results case, and ignoring `check_suite` failed the webhook case. Live on `test1` (`github-adapter-m6-live.txt`): a real CI run's check runs were listed, and a GitHub Actions job's 10,004-byte log was read as its last 2,048 bytes, which end the whole log. The row stays `partial`: reopening the task with the failing checks, and the rounds, are core's (tickets 16 and 18).
- **Ticket 16 (2026-11-20)** built CI on the task's PRs in core: `ci.evaluate` (`apps/core/src/review-loop/ci.ts`, the domain's `evaluateCi` in `packages/domain/src/review-loop/evaluate-ci.ts`), keyed by the task repo and the head, enqueued by a `check_run`, `check_suite` or `status` hint (ostra's own App's runs are no hint), a PR's opening or new head, and the PR reconcile; the verdict without ostra's own App's check runs, kept per head in `CiRun`, with `ci.updated` in the thread on a change; the "no CI" deadline and the wait limit as two delayed evaluations; a failed verdict's log tails (at most `OSTRA_CI_LOG_CHECKS`, `OSTRA_CI_LOG_TAIL_KIB` each) as blobs of the task, never logged; and the code task's sub-state following the combined verdict over its open PRs. Proved on the fake code host with the review loop's capabilities on. Row 1 stays `partial`: the runner writing the logs under `.ostra/ci/` is ticket 23's, the GitHub adapter's CI ticket 08's, and the live run ticket 39's.
- **Ticket 18 (2026-11-20)** built the CI round: `round.start` (`apps/core/src/review-loop/rounds.ts`, the domain's `startRound`), its caps, the budget gate and the spend cap. A CI round with log files goes to a fresh box, whose spec carries them as `ci` files and `automatic: true`, and whose dispatch goes only to a runner at minor 5.
- **Ticket 23 (2026-11-20)**, the runner. A CI round's log tails come as the spec's `ci` context files (`<blobId>.log`, plain text) and are written under `.ostra/ci/` in the folder the agent's session opens on, where the round's prompt names them (`writeCiFiles`, `apps/runner/src/task-host/ticket-files.ts`): at most 5, each fetched through the bulk path and checked against its size and digest, any other type skipped. Every repo's git excludes `.ostra/`, so a log never lands in the branch or the hidden ref, and a log's text never reaches a log line. On `host` and on `docker` as a box's sidecar drives it. The row stays `partial` for the live run (the demo's steps 5 and 12, ticket 39).
