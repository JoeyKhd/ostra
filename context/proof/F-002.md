**Not built yet: milestone 4** (the row's "Building" note: "the first admin only; invitations, resets and more members are milestone 4").

- *Sign-up is invite-only* is partial: sign-up is closed (proved), on every install: the open sign-up settings were removed on 2026-11-19, and an upgraded install that still sets `OSTRA_OPEN_SIGNUP_ACCOUNTS=true` starts and still refuses a stranger (`docs/configuration.md`, "Removed settings"). But an admin can't yet invite with a link, copy it, mail it or remove a member from the panel. What would prove it: a router and an e2e test of the invite flow, and of removing a member.
- *An invitation is bound to an address* is missing: ostra's own sign-up-by-invitation code doesn't exist yet. What would prove it: a test that a stranger who knows an invited address, without the link's ID, can't sign up, and that the ID alone is what's recognised.
- *It works once and expires after 7 days* is partial: better-auth's invitation, as ostra configures it, expires after 7 days and an admin (not a member) revokes it (proved). "Works once" needs the invitee's sign-up, milestone 4.
- *The link is a bearer secret* is missing: no docs page for invitations yet, and no email (F-002's email half is with the mail settings). What would prove it: a docs test like `scripts/deploy-docs.test.ts`, and a test that with email set up a mismatched or unverified address is refused.
- *Without email, the instance admin, and only the instance admin, creates a reset link* is missing: no route makes a reset link yet. What would prove it: a router test that an organization admin is refused and the instance admin gets a link valid for 24 hours. (better-auth's `resetPasswordTokenExpiresIn` is set to 24 hours already.)

*Using a reset link signs out the account's other sessions* is proved with a reset token stored the way better-auth stores the one it makes, then used through better-auth's own `reset-password` route; who may make one is the condition above.

- 2026-11-19, tickets 22 and 23 (m4): invitations, sign-up by the link, verification and resets through better-auth's HTTP handler (`packages/api/src/auth/invitations.test.ts`), and removal (`packages/api/src/routers/members.test.ts`). *The link is a bearer secret* stays `partial`: its email half is proved, and the docs page that says to send the link privately is ticket 32's (the panel's words) and 41's. Two refusals are checked twice on purpose: the sign-up hook and the acceptance both compare the address, and both lookups of a member's scope want an active membership, so each break-it broke both together.

## Notes

- 2026-11-19, ticket 32 (m4): the panel's Members page, the invite sheet, `/invite/[id]`, `/reset` and `/reset/new`, proved through the browser on the e2e stack (`apps/web/e2e/10-members.spec.ts`) with no email set up, so the admin copies the link and the instance admin makes the reset link. Two fixes rode with it: the instance admin's link now opens `/reset/new?token=` like a mailed one (ticket 22 had returned better-auth's redirect, which can't tell a used link from an expired one), and the reset link's sink is one store per process, since Next loads `account-hooks.ts` once per route bundle (the panel's "Create reset link" failed without it). `email.on` and `accounts.resetPreview` are the two public reads the pages before sign-in use.
- 2026-11-20, ticket 41 (m4): the live demo found a removed member's panel showing "No organization" and "Couldn't load this" on every list. `me.get` now says `noMembership: "removed"` (or `"none"` before an invitation is confirmed), and the panel's layout shows "You're no longer a member of any organization", with Sign out, instead of the shell (`apps/web/src/components/auth/no-membership.tsx`); the instance admin keeps the Instance and Account pages.
- 2026-11-20, review findings in `packages/api`: better-auth's organization and admin plugins' routes are refused over HTTP (`isServerOnlyAuthPath` in `create-auth.ts`), since they never read a membership's state nor write an audit entry, and a removal takes the organization out of the member's login sessions. The forged leading `X-Forwarded-For` value no longer opens a new rate-limit window (`clientAddressOf` takes the proxy's last hop).
