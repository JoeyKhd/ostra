## Notes

- **Ticket 11 (2026-11-20)** built the bulk start (`packages/domain/src/starts/bulk.ts`, core's `bulk.start-item` worker): one `BulkStart` and its items in one transaction, idempotent by the member's request key, at most `OSTRA_BULK_START_MAX` (50), and each item through the one start (`startTask`) in its own transaction, with an outcome per ticket (`started`, `skipped` with `has-task`, `no-access`, `not-on-a-board` or `has-sub-issues`, or `failed` with the refusal's code). Every task it starts goes through the real dispatch's gates and waits queued with the reason (`apps/core/src/testing/start-gates.ts`).
- The first row stays `partial` until the Inbox's selection and the dry run's "Start all" button reach `startMany` (tickets 25 and 32); the use case and its worker are proved here.
- A dry run's "Start all" starts what the rule would: the rule's kind, its profile unless the member chose one, and its pool labels; each task keeps the rule's ID (`automationId`) and the member as its starter (`origin: member`).
- **Ticket 24 (2026-11-20):** `automations.startAll` is a project admin's "Start all": the saved automation's dry run, started as one bulk start with `source: dry_run` and the rule's ID, idempotent by the press's request key.
- **Ticket 25 (2026-11-20)** gave the Inbox its API: `inbox.startMany` (the selected tickets as one bulk start, `source: inbox`) and `inbox.bulkStart` (its items, each one's outcome and task). The outcomes reach the panel on the tab's one stream (ADR 0035: one subscription per tab): each decided item sends the project's change notice, and the panel reads `inbox.bulkStart` again, so no second subscription is opened. The first row stays `partial` until the Inbox's selection and the dry run's button are on the screen (ticket 32).
- **Ticket 32 (2026-11-20)** put both on the screen: the Inbox's tick column, selection bar and bulk-start panel (`apps/web/src/components/inbox/bulk-start.tsx`) send the ticked tickets to `inbox.startMany` as one bulk start and read each one's outcome back from `inbox.bulkStart`; ticket 31's editor presses `automations.startAll`. A ticked parent's code start goes to `tickets.startSubIssues` (a parent never runs code, so `startMany` would skip it). Proved end to end in `apps/web/e2e/19-inbox-bulk.spec.ts` and `18-automations.spec.ts`, against core's `bulk.start-item` worker; the first row is `proved`.
- **Ticket 41 (2026-11-20), the ticks across a refresh:** the Inbox kept its ticks in a map but its Shift range's anchor as a row index and its panel in tick order, so after the 10 s refresh reordered the rows (a changed ticket moves to the top), a range ticked other tickets and the panel's order drifted from the list. `apps/web/src/components/inbox/inbox-selection.ts` keeps each tick and the anchor by ticket ID, lists the ticked tickets in the list's current order with the refreshed copies (a ticket that gained a task previews as skipped), and keeps a tick on a ticket the refresh no longer lists.
