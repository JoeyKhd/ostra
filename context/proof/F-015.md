Notes (2026-11-19, milestone 1's ticket 41): the box's sidecar against a fake peer, with real ingest, grace and stop reactions; a real box waits for a Linux machine with Docker (F-017).

Notes (2026-11-19, milestone 5's ticket 02): `writeTaskTokenFile` (`packages/adapter-sdk/src/executor/task-token.ts`) is the task token's one handoff for `docker` and `kubernetes`: a folder of the sidecar's own, readable by its user only, never an environment variable or an argument. The executor contract suite's cases "F-015: the task token is readable at the sidecar's mount only, never in an environment, an argument or another file; an executor with no sidecar refuses one" and "F-015: release removes every object the box made, its token and pull secrets included" (in `packages/adapter-sdk/src/testing/executor-suite.ts`, run from `packages/adapter-sdk/src/contract-suites.test.ts`) pass on the tiny executor's fleet variant; they failed when the token was copied into the box's files, when an executor with no sidecar took one, and when release left the box's folder. `docker` gives them its fixture in ticket 09 and `kubernetes` in ticket 07.

Notes (2026-11-19, milestone 5's ticket 07): on `kubernetes` the task token is in the box's secret, mounted as a file into the sidecar's container only (`items: [token]`); the bridge's nonce, beside it in the secret, reaches the agent's container as one variable from its own key, and the pull credential is a `dockerconfigjson` secret only the kubelet reads. The pod's surface (every container's command, arguments, variables resolved from their secrets, and secret files) holds the token at the sidecar's mount alone. The executor contract suite's cases for the token and for release pass on a pod in `packages/adapters/adapter-executor-kubernetes/src/kubernetes-executor.contract.test.ts`. A runner restart that leaves the pod and its sidecar running is ticket 20's.

Notes (2026-11-19, milestone 5's ticket 09): on `docker`, the executor's pool runner half (`DockerExecutor`'s `pool`) makes the token folder with `writeTaskTokenFile`'s rules and mounts it read-only into the sidecar's container only; the suite's cases "F-015: the task token is readable at the sidecar's mount only, never in an environment, an argument or another file; an executor with no sidecar refuses one" and "F-015: release removes every object the box made, its token and pull secrets included" now run on `docker` against the fake Engine. A real box whose sidecar stays up while the runner is replaced is the live case "F-015: a box keeps running, its sidecar untouched, while the runner that made it is replaced" in `packages/adapters/adapter-executor-docker/src/docker.live.test.ts` (ticket 35); its sidecar's connection to core is the demo's (ticket 37).

Notes (2026-11-20, milestone 5's ticket 10): a `host` pool runs every process of a task (the git that makes its worktree, its setup script, its checks, the agent) through `sudo -n -u <user> --` with the command as an argument array and the environment by name only (`--preserve-env`, the sudoers rule's `SETENV`), hands each task's folder to the agent's group, and checks at start that the sudoers rule works for that user and no other and that the user can't read the runner's key; it refuses to start on Windows, without the user, and on the development switch in production, and on the switch elsewhere it runs as the runner's own user and `health()` says "same user (development only)". The tests run the real executor with `sudo` replaced by a stand-in that checks and logs each call (`packages/adapters/adapter-executor-host/src/testing/fake-sudo.ts`), since this machine has no second user. The row stays `partial`: the agent really being another user, a shell that can't read the runner's key or a folder the runner kept, is `packages/adapters/adapter-executor-host/src/host-executor.live.test.ts`, run by ticket 35's Linux and macOS jobs, and the panel's "not isolated" line for a pool is ticket 31's. One agent user serves all of a pool's tasks on a machine, so a running task's agent can read another running task's worktree there; Q293 asks whether that's enough.

Notes (2026-11-20, milestone 5's ticket 20): on `kubernetes`, in the fake cluster's process mode, the box's sidecar is the real `ostra sidecar`: it reads the task token from its secret's mounted file and connects to the server on it, and the runner's data folder holds the box's IDs only, never the token. The runner then stops and a new one starts: the pod and its sidecar run on, the sidecar's connection isn't replaced, and the new runner adopts the pod from its records (`<dataDir>/kubernetes-boxes/`) and the namespace's box pods. A release deletes the pod and its secrets, and the runner lists what's left by the box's label (nothing). Real boxes on Linux with Docker and on kind remain ticket 35's.
