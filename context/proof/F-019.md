## Notes

- **The agent:** OpenCode runs in these tests as the real, pinned binary (`@opencode/cli` 2.3.2, its SHA-256 checked before start) against a stub model, over ostra's ACP driver, which is built on the official ACP SDK (`@agentclientprotocol/sdk`, `packages/adapter-sdk/src/agent/acp/driver.ts`). The runner test runs the agent registry the runner ships (`defaultAgents()`), the host executor, the key and git proxies and a git upstream; the live demo ran it against a real endpoint and GitHub (PR #31).
- **Rows 2 and 6, partial: the base image.** `deploy/Dockerfile.base` installs `@opencode/cli@2.3.2` with `--ignore-scripts` and checks the platform binary's SHA-256 against `pinnedChecksums`, but it has never been built: this machine is Windows with no Docker (F-017, `context/specs/m1-first-pr/demo.md`, "What's still missing"). On the host executor the adapter itself refuses a binary whose SHA-256 differs, which the tests prove, and writes the provider, permission and catalog files per task. What would prove the rest: `docker build -f deploy/Dockerfile.base` on Linux, once with the pinned binary (it builds, and `opencode --version` in the image says 2.3.2) and once with a changed checksum (the build fails).
- **Row 3, partial:** what is built for agents works with OpenCode and is proved here or in its own row: live activity (F-023: `packages/task-view/src/every-agent.test.ts` folds a real OpenCode turn), stop (F-025, the live demo stopped OpenCode mid-turn), steering, and the plan through `todowrite`; native plan and reject-and-continue are declared absent. The ledger's later agent features aren't built yet, so "every feature" can't be shown; each one's own proof should run it on OpenCode or show the capability declared absent.
- **Row 5, partial: the deny.** The plan half is proved on the real binary. The re-prompt after a deny isn't built: milestone 1's runner answers every permission request itself with "allow once" (`onPermission` in `apps/runner/src/task-host/task-run.ts`), and nothing re-prompts after a deny. The contract suite's deny case is skipped for OpenCode: ostra's config allows every action in the worktree, so OpenCode never asks. It waits for member approvals (F-026). What would prove it: a task-host test where a member denies an OpenCode request, the turn ends `cancelled`, and the runner sends the re-prompt, after which the agent goes on.
- **Row 7:** the suite (`defineAgentContractSuite`) runs in CI against the pinned OpenCode in both API formats and against the fake in both profiles; its case titles live in `packages/adapter-sdk/src/testing/agent-suite.ts`, which isn't a test file, so the ledger cites the F-019 cases written in the test files and a log of one full run of the suite. A version bump changes the pin in `binary.ts`, and the steer probe then runs against the new binary on the next run. Six suite cases are skipped for OpenCode because no prompt can make it do that thing against a stub (a permission request, a question, the environment and endpoint probes, an unknown update, a leftover process); its environment is checked by the adapter's unit tests and by the live demo instead.
- **Row 3, adapter parity (milestone 7, ticket 03):** the agent contract suite now runs by adapter (`runAgentSuite` in `packages/adapter-sdk/src/testing/run-agent-suite.ts`) on OpenCode in both API formats and on the four scripted fakes, with milestone 7's cases (`agent-parity-cases.ts`): an unknown notification after `initialize` tolerated (on a fake that sends one), every model call at the key proxy with the task's key and nothing through the machine's proxy, the proxy's count equal to the agent's own turn usage (OpenCode's prompt answer carries it), the launch's environment exactly the adapter's allowlist with a canary of the runner's own reaching neither the launch nor the process, a repo's config hidden for the task with its hook never run and restored byte for byte (on the fakes without `projectConfigOverride`), "allow for this task" holding across a relaunch with nothing of it in the repo, ticket text that starts with `/` never sent first, and a checksum mismatch refusing the launch. The parity table (`packages/adapter-sdk/src/testing/parity.ts`) names, for every row of the m7 spec's section 6 and for each adapter, the case that proves it or the capability it lacks with its fallback; `checkParity` fails on a missing row, a case that doesn't exist, a fallback for a capability the adapter declares, or a capability with no case that runs its way. It stays partial for four rows only: milestone 6's refine and review, start from Linear, automatic turns and onboarding, which `pendingParity` lists as waiting for milestone 6's tickets 04, 09, 13, 18, 21, 22, 23 and 38, being built. A row that names a runner or core test (the git proxy, the sidecar's MCP tools, the runner's limits) is the same for every agent, and runs on the scripted fake.
