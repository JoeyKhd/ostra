## Notes

- **Ticket 04 (2026-11-20)** built the agent side. Row 3 is `partial`: `stageCommitPaths` (`packages/adapter-sdk/src/executor/commit-paths.ts`) stages only a task's `commitPaths` (an onboarding task's `["AGENTS.md"]`) in a real git repo, and leaves the agent's other changes in the workspace, uncommitted, counted for `commit.filtered`. The runner's commit using it is ticket 23, and the PR it opens is ticket 21's. Row 2's agent half is in the agent contract suite (`agent-team-cases.ts`): the proposing fake's `propose_environment` reaches the fake core's `/environment-proposal` by the protocol's schema, and a `secret-found` refusal reaches the agent by kind, never by value; the suite's commit case runs `stageCommitPaths` after a real turn of the fake. Suite cases run in `fake-agent.test.ts` but live in a suite file, so they're named here and in the parity table (`parity.ts`), not cited. Break-its: answering a proposal as saved whatever the refusal switch said failed the proposal case on every fake with MCP.
- **Ticket 09 (2026-11-20)**: ticket 04's onboarding cases run on the pinned OpenCode with the stub model, on both API formats: `propose_environment` round-trips through the fake core (a `secret-found` refusal reaches the agent by kind), and OpenCode's own writes outside `commitPaths` stay uncommitted after the runner's filter. Nothing in the adapter does the filter; the parity table names both cases for OpenCode.
- **Ticket 21 (2026-11-20)**, core: `startOnboarding` (`packages/domain/src/onboarding/onboarding.ts`) for a project admin, one open per project (under the project's row lock): a code task with origin `onboarding` and `onboarding: true`, from the onboarding prompt on the saved environment (its setup script, shown with the first repo, and its checks), or the draft detected from each repo's files when none is saved. It reads each repo's `AGENTS.md` at its default branch so the prompt names only the repos without one. `buildTaskSpec` leaves the snapshot out (no image, no host cache), serves `["environment", "pr-text"]` and commits only `["AGENTS.md"]`; on a `host` box the prompt gains `ONBOARDING_HOST_LINE`. `POST /runner/v1/tasks/:taskId/environment-proposal` (`apps/core/src/runner-http/environment-proposal.ts`) takes an onboarding task's proposal only, scans its scripts, checks, services and notes with milestone 4's scan and the organization's secret values, supersedes the open one, writes `environment.proposed` and a needs-you item (`environment_proposal`). `decideEnvironmentProposal` saves an accepted (or edited) proposal through `saveEnvironment` with the environment's entries kept (a secret by its reference), upserts its checks and services by name, and records `environment.proposal-accepted` with the version (`environment.saved` entries counted). Row 2 stays `partial`: the agent running the setup, the services and the checks in its box is the runner's (ticket 23) and the live run is ticket 39's. Row 3 stays `partial` until ticket 23's runner commit opens the `AGENTS.md` PR.
- **Ticket 23 (2026-11-20)**, the runner and the host executor (which `docker` and `kubernetes` run too). After every turn, with the spec's `commitPaths`, each repo's commit stages only the allowed paths' changes (`#commitAllowed`): the rest stay in the working tree, uncommitted. When the branch's own commits since its base (the agent's) touch any other path, the tip is rebuilt as one commit on the base: a mixed reset to the merge base keeps every change in the tree, and only the allowed ones are committed again, with the runner's message. A repo with nothing allowed changed isn't ahead, so it isn't pushed. The executor reports what was kept (the branch against its base) and left (at most 50, with the count) per repo, and the runner emits `commit.filtered` for each repo that left something out. On `host` and on `docker` as a box's sidecar drives it. `propose_environment` on the sidecar's MCP server forwards to core's `/environment-proposal` (ticket 22's commit, `mcp-team-tools.test.ts`). **A limit** (closed 2026-11-21, below): the agent can still push its own commits to the task's branch through the git proxy, which an onboarding task's runner overwrites with the filtered tip when the repo is ahead; when nothing allowed changed, the runner pushes nothing, and such a push of the agent's would stay on the branch, with no PR, since the repo isn't ahead. Row 3 stays `partial`: "only where it's missing" rests on core's prompt naming only the repos without one (ticket 21), not on the filter, which takes an edit of an existing `AGENTS.md` too; and the PR from a real onboarding run is ticket 39's demo (step 11). Row 2 stays `partial` for the box from the base image with its services, which needs Linux with Docker (spec section 9.1).

- **Review follow-up (2026-11-21, the maintainer's "all yes"; ADR 0038 amended)**: ticket 23's limit is closed, row 4. With the spec's `commitPaths`, the git proxy holds each push on disk and checks it before a byte goes upstream (`apps/runner/src/sidecar/git-proxy/path-check.ts`): every commit the pack carries against each of its parents, and a ref moved to a commit the code host already has. One changed path outside `commitPaths` refuses the whole push as `path-not-allowed`, whose words git prints to the agent; a push the check can't read (its objects missing, past 32 MiB, an object whose content doesn't hash to its ID) is refused as `paths-unchecked`. The check runs git in a scratch repo of the proxy's own, never in the agent's checkout, with the checkout's objects as an alternate for thin bases and parents, and hashes every commit and tree it reads again. The hidden ref's save keeps only `commitPaths` too (`saveWorkInProgressIn`), so the runner's own pushes pass; a reopened onboarding task gets back only those paths' unfinished changes. The proxy is the task host's, so every executor runs it; the runner cases run on `host` and on `docker` as a box's sidecar drives it, as for row 3.
