## Notes

- **Ticket 08 (2026-11-20)**, GitHub's adapter: `listRequestedReviewers` reads `GET /pulls/{n}/requested_reviewers` (people by ID and login, teams by slug). `readCodeOwners` reads the first of `.github/CODEOWNERS`, `CODEOWNERS` and `docs/CODEOWNERS` at the ref, in the order GitHub looks, or `null`. A `pull_request` delivery whose action is `review_requested` or `review_request_removed` is the `pull_request_reviewers` hint. The code host suite's reviewer, CODEOWNERS and webhook cases run on GitHub's adapter against the fake GitHub. Live on `test1` (`github-adapter-m6-live.txt`): CODEOWNERS was read at a branch from `.github/CODEOWNERS`, with none on `main`, and a PR's requested reviewers were read. The live PR had none: asking a person to review would notify them, and the App can't list the org's teams, so a non-empty list is proved on the fake only. The row stays `partial`: the match to members and the "needs you" are core's (ticket 19), and the screen is tickets 28 and 35.
- **Ticket 19 (2026-11-20)**, core: `reviewers.refresh` (keyed by the task repo, a 10-second window) runs on a `review_requested` or `review_request_removed` hint, a PR's opening or push, and the PR reconcile. It reads the requested users and teams and, when the PR changes paths, `CODEOWNERS` at the PR's base for those paths (`compare` from the base to the head; a rename counts both paths). Each user is matched to an active member by `User.githubUserId`; a CODEOWNERS login by the requested user of that login, else the linked account's `githubLogin`; an unlinked CODEOWNERS login has no GitHub ID to key by, so its row's `githubUserId` is `login:<login>` (`codeOwnerLoginKey`). Teams are rows of their own (`source: team`, slug in small letters, the `org/` prefix dropped), never expanded. A row whose user reviewed stays when GitHub drops the request on review. `reviewers.updated` is written only when the set changes. A code task entering "waiting for a reviewer" (`moveTaskInTx`) writes the `waiting_for_reviewer` item (audience `reviewer`, moment `review_requested`); leaving it dismisses the item. The fan-out reaches the matched reviewers who can open the project, else the driver. Milestone 4's `review.evaluate` keeps each user's latest review state and answers the reviewer's own notification for a review since the item; the item is answered once every matched reviewer's is closed. The panel's one rule (`openNeedsYouWhere`) shows a reviewer item to each matched reviewer without a closed notification of it, and to the driver when nobody matched. ostra requests nobody on GitHub. Rows 1, 2 and 4 are the review screen's (tickets 28, 35).
- **Ticket 28 (2026-11-20)**, the API (`packages/api/src/routers/review.ts`): `review.screen` gives, per PR of a code task, its diff (milestone 3's stored compare by head, through `taskDiffs`) with its files and a file tree counting each file's open findings, its findings of every review run with their round, state and placement, its CI run at the head, and its reviewers (the linked member, or the login or team); the ticket with the applied refine draft's criteria (`acceptedCriteriaOfTicketInTx`, which the review prompt reads too) or the ticket's own text; and the round line (the sub-state, each kind's rounds of the install's limit, the automatic turns). `review.fixThis` saves the finding as the member's draft line comment through milestone 3's `saveDiffComment`, on the head the review ran on; pressed twice it's one draft, and a finding off the diff (in the review's body) is refused. It counts as a person acting (`recordPersonActionInTx`). The first row stays `partial` until the screen draws it (ticket 35). "Approving and merging stay on GitHub" stays `missing` here: no procedure of ticket 28 approves or merges, and the code host adapter refuses any review event but `COMMENT` (F-100); ticket 39's demo shows it live.
