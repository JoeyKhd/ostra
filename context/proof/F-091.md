Notes (2026-11-19, milestone 1's ticket 42): the notification to admins comes with F-036. The key pair and the short-lived access tokens are exercised by the same tests (each runner registers a fresh Ed25519 key and connects with an access token traded for a signed assertion), and by the live run in `context/specs/m1-first-pr/issues/42-join-tokens-and-approval.md`.

**Bug fixed while challenging it (2026-11-19): joins that raced with one name each made a runner.** `registerPoolRunner` read the pool for a runner of the join's name, then made one, with no index or lock between the two: three joins sent at once with one name made three runners in the pool, all `201`. A join now takes its pool's row (`FOR NO KEY UPDATE`) before it reads, so joins into one pool go in turn and the second of two with one name is refused with `409`. The race test holds the join token's row, which a join writes last, so every join reads the pool before any commits, and then lets go.

Notes (2026-11-19, milestone 5's ticket 03): the two runner notices, `runner_joined` and `runner_awaiting_approval`, are moments for the organization's admins. `renderRunnerNotice` gives the panel's words and both parts of the mail; the notification contract suite runs each kind on the panel channel, both email channels (SMTP and Resend) and the tracker channel (on the fake Linear and the Jira fake), which refuses them. The row stays `partial` until core sends the notice in the join's transaction (ticket 12).

Notes (2026-11-19, milestone 5's ticket 12): pools and join tokens are the domain's (`createPool`, `updatePool`, `createJoinToken`, `revokeJoinToken`, `registerPoolRunner` in `packages/domain/src/use-cases/pool-admin.ts`), and core's register endpoint joins through `registerPoolRunner`: any live token of the pool, read by core's clock; a refusal names `expired`, `revoked` or unknown in its message and writes nothing but a log line with the token's ID, at most once a minute per token. The join's audit entry is `runner.joined`, naming the token, with its `runner.join-notice` job in the same transaction. That job sends `runner_joined` to the admins and, when the pool requires approval, `runner_awaiting_approval`, which is their open item until the approval or the reject answers it (a needs-you item belongs to a task, and a joining runner has none). The token row stays `partial`: the panel's answer that shows it once is ticket 25's. The lifetime and revoke row stays `partial` for the same reason.

Notes (2026-11-20, milestone 5's ticket 25): the panel's API is on the domain's use cases now. `pools.create` makes the pool and its first join token in one transaction (with the projects it's for, each at the end of its list) and answers the token once; `joinTokens.create`, `joinTokens.revoke` and `joinTokens.list` are the token's own procedures, and milestone 2's `pools.createJoinToken`, `pools.revokeJoinToken` and `pools.joinTokens` call the same code until the panel moves (ticket 30). No list, page, error, audit entry or log line carries a token or its hash. `runners.approve` and `runners.reject` answer a runner that isn't joining any more with its state and `changed: false`. The first row stays `partial` until a project's ordered list can be set (ticket 27).

Notes (2026-11-20, milestone 5's ticket 19): the runner's half of the start. `apps/core/src/gateway/runner-pool-start.test.ts` runs the real `ostra runner` (its sign-in, its `host` executor on the development same-user switch, its connection) with `OSTRA_JOIN_TOKEN` against core's register endpoint and gateway. In a pool that requires approval, minor 4's `welcome` carries the pool and `awaitingApproval`; the runner keeps it in `status.json`, and `ostra runner status` says "waiting for an admin to approve this runner in <pool>". `approveRunner` sends a connected minor-4 runner `resume`, which clears it; the row goes `online`. An expired, revoked or unknown token prints its reason and exits 1, with nothing made. Row 2 is proved with this: the token from the environment, traded at first contact for the runner's own key (only the public half is sent), and the access tokens after that, all by the real runner.
