## Notes

- **Row 1 is partial.** The tests run `ostra runner` from the CLI's own entry point (`apps/runner/src/main.ts`, the file the package's `bin` names) and check that the runner image's entry point is that file. Neither the npm package nor the image exists yet: `@ostra/runner` is `private` and unpublished, and the image has never been built (no Docker on the milestone 1 machine). What proves it: `npm install -g` of the published package running `ostra runner` against a server, and `docker run ostra/runner` on a Linux machine with Docker joining a pool.
- **Row 4 is missing:** the HTTP fallback isn't built (milestone 5, the ledger's note). What proves it: a test that blocks the WebSocket upgrade at a proxy and watches the runner reach core over HTTP within 30 seconds.
- **The browser.** `runner-cli.test.ts` approves the code through better-auth's own device routes, the ones the panel's `/device` page calls. The page itself approving it is the live screenshot from milestone 1's demo (`09-device-approve.png`), and the Playwright spec `apps/web/e2e/03-first-run.spec.ts` ("Connect a runner: ..."), which `check:proof` can't cite yet because its file skips at phone width.
- **"Can do nothing else a member can."** The test shows the session better-auth issued is deleted, resolves to no session, and isn't in the runner's data folder or output. What the runner keeps is its own key: the access token it earns at core resolves to no session in better-auth, which every panel route checks, as a bearer or as a cookie, and core takes it for the runner's WebSocket, which delivers the runner's commands.

## Bug fixed while challenging it (2026-11-19)

- **One device session made a runner for every register that raced with it.** `register` checked the session outside its transaction, created the runner, and then deleted the session with a `deleteMany` that succeeds on no row. Registers sent at once with the same session all found it valid, and each made a runner: three registers, three runners, all `201`. The session now goes first, in the register's transaction, and only the register that deleted it goes on: a racing one waits on the row, finds it gone, and answers `401` with nothing made (`registerPersonalRunner` in `packages/domain/src/use-cases/register-personal-runner.ts`, `revokeInTx` in `apps/core/src/gateway/device-sessions.ts`). The race test holds the session's row itself, so every register queues on it, and then lets go.
