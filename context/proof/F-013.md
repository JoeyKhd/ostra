## Notes

- **Row 1 is partial.** The tests run `ostra runner` from the CLI's own entry point (`apps/runner/src/main.ts`, the file the package's `bin` names) and check that the runner image's entry point is that file. Neither the npm package nor the image exists yet: `@ostra/runner` is `private` and unpublished, and the image has never been built (no Docker on the milestone 1 machine). What proves it: `npm install -g` of the published package running `ostra runner` against a server, and `docker run ostra/runner` on a Linux machine with Docker joining a pool.
- **Row 4 is proved** (milestone 5's ticket 18, 2026-11-20): core's carrier (ticket 11) tested against a fake peer over HTTP, and the real runner connection (`startConnection` from `apps/runner`) falling back to it by itself, against the real gateway and ingest, through ticket 06's proxies: the CONNECT proxy with and without Basic auth (stays on the WebSocket), the TLS-inspecting proxy that blocks upgrades and the one that answers 101 and holds the frames, nginx's defaults (emulated, spike 6's), and a front that kills or silences the upgraded socket. Each trigger is timed from the runner's start against 30 s, on the runner's real timers (10 s for the missing welcome and the quick deaths). Real nginx and the runner image add to it in ticket 35's Linux job; neither is needed for the row (spec section 9.1).
- **The browser.** `runner-cli.test.ts` approves the code through better-auth's own device routes, the ones the panel's `/device` page calls. The page itself approving it is the live screenshot from milestone 1's demo (`09-device-approve.png`), and the Playwright spec `apps/web/e2e/03-first-run.spec.ts` ("Connect a runner: ..."), which `check:proof` can't cite yet because its file skips at phone width.
- **"Can do nothing else a member can."** The test shows the session better-auth issued is deleted, resolves to no session, and isn't in the runner's data folder or output. What the runner keeps is its own key: the access token it earns at core resolves to no session in better-auth, which every panel route checks, as a bearer or as a cookie, and core takes it for the runner's WebSocket, which delivers the runner's commands.

- **A refusal that can pass never ends the runner** (ADR 0034, "Auth"). On 2026-11-19 a personal runner connected for hours exited with code 3, as revoked, and told its member to delete its identity, when core refused its new token because the two clocks were an hour apart; it wasn't revoked, and restarting it connected at once. Core now names why it refuses a token, and the runner retries the clocks, a replayed nonce and an older server's reason-less 401. The clock row above replays the incident: core's clock jumps an hour, core counts the peer dead, and the runner says by how much, keeps asking and comes back. The two refusals that do end it are tested too, though no sentence above is about them: `runner-cli.test.ts` > "F-013: a revoked runner stops with the refused exit code and the advice to sign in again" (broken by reading the `revoked` reason as retryable: the runner never exited) and > "F-013: a key core doesn't know ends the runner with its own message, not as revoked" (broken by the old mapping: it said revoked), with `peer.test.ts` and `cli.test.ts` cases for each, and `gateway.test.ts` > "F-013: say why, and core logs each with the runner ID and the reason only: ..." (broken by dropping core's log line, and by answering an unknown runner apart from a bad signature).

- **One process per runner** (ADR 0034, "One process per runner"). On 2026-11-20 four `ostra runner` processes with one identity, left alive by restarts, ran on the maintainer's machine. Each new connection evicted the one before, the evicted one came back a minute later and evicted the next, each takeover restarted the task's agent, and the panel reloaded every few seconds. The reconnect row above holds the two race tests: a runner's own connections never stop it. What stops it, or keeps it from starting, is tested here, though no sentence above is about it:
  - `apps/core/src/gateway/runner-cli.test.ts` > "F-013: a second ostra runner on the same data folder refuses to start with exit code 4, naming the first one's pid, which keeps its connection; after a crash the next one starts", the real CLI against real core. Broken by giving each process a lock path of its own in `startRunner` (`apps/runner/src/cli/cli.ts`): the second runner started, took the connection, and the test timed out waiting for it to exit.
  - `apps/core/src/gateway/runner-cli.test.ts` > "F-013: a runner whose connection another process took stops with exit code 4 and says why, and doesn't take it back", a copy of the data folder as the other machine. Broken by sending a replaced runner back to its old sleep-and-reconnect in `peer.ts`: the first runner never exited, and the test timed out.
  - `apps/runner/src/connection/peer.test.ts` > "F-013: a runner whose connection the server gives to another process stops, says why, and doesn't reconnect", for an `evict` frame and for a bare 4409 close. Broken the same way: `done` never settled. The same break failed the late-hello test, and a box's sidecar keeps reconnecting (> "F-013: a box's sidecar that's replaced keeps reconnecting: its task's events have nowhere else to go").
  - `apps/runner/src/identity/runner-lock.test.ts`: > "F-013: a second runner on a data folder another runner holds is refused, with the holder's pid, and its lock is untouched" (broken by counting a running holder as stale: four of the file's tests failed), > "F-013: the lock a crashed runner left is taken over, and the next runner after that is refused" and > "F-013: a lock is stale when its pid ended, is this process's own (a restarted container), or another machine wrote it" (broken by letting a pid that ended hold the lock: both failed), > "F-013: two runners starting at once on a crashed runner's lock: one takes it, the other is refused" (broken by replacing a stale lock without checking it was still the one judged stale: both runners took it), with the holders as real processes taking the lock through the real module.
  - `apps/runner/src/cli/cli.test.ts` > "F-013: refuses to start while another runner on this machine holds its data folder, with exit code 4 and that runner's pid, and starts once it's gone": no token is asked for and no runner starts. Broken by taking the lock in another folder: it signed in and exited 0.

## Bug fixed while challenging it (2026-11-19)

- **One device session made a runner for every register that raced with it.** `register` checked the session outside its transaction, created the runner, and then deleted the session with a `deleteMany` that succeeds on no row. Registers sent at once with the same session all found it valid, and each made a runner: three registers, three runners, all `201`. The session now goes first, in the register's transaction, and only the register that deleted it goes on: a racing one waits on the row, finds it gone, and answers `401` with nothing made (`registerPersonalRunner` in `packages/domain/src/use-cases/register-personal-runner.ts`, `revokeInTx` in `apps/core/src/gateway/device-sessions.ts`). The race test holds the session's row itself, so every register queues on it, and then lets go.

Notes (2026-11-19, milestone 5's ticket 06): spike 6's networks, ported to `packages/adapter-sdk/src/testing/net/net-proxies.ts` with per-run certificates made in memory (`certs.ts`): the CONNECT proxy with and without Basic auth, the TLS-inspecting proxy in its three modes, switchable at run time, the nginx emulation and the held or reset cut. They prove no row by themselves: the runner's fallback through them is ticket 18. Their tests (`net-proxies.test.ts`) show a WebSocket upgrade through each behaving as the spike recorded, and failed when the hold mode passed frames, the reset cut did nothing, the proxy skipped its auth and nginx passed the upgrade.

Notes (2026-11-20, milestone 5's ticket 19): row 1 is proved by the npm CLI, which meets its "or" (spec section 9.1). `pnpm --filter @ostra/runner pack:cli` (`apps/runner/src/pack/pack-cli.ts`) bundles `ostra` with esbuild into one file with no dependencies, writes a package.json with the `ostra` bin and `engines.node` `>=24.5`, and packs it with npm; the test installs that tarball with `npm install --offline` into a fresh prefix, runs the bin as npm's shim does (`--version`), and starts `ostra runner` with a join token against the fake server, which registers it at its version; `ostra runner status` then says it's from npm. The runner image's build and start stay ticket 35's. The package's name is `ostra` until the maintainer registers one (ADR 0046); `OSTRA_CLI_PACKAGE` names another. Row 6 now also cites the real runner's start against core's gateway: its `hello` and `status` carry its executor, capabilities, slots, labels and install (minor 4), which core keeps on its row.
