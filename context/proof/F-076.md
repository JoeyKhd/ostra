## Notes

- **The first condition is partial**, for two of its parts. Proved here: the checklist's six steps in their order, each ticked only once its thing exists and `next` always the first one not done (the walk, through the real routers on embedded Postgres, with only GitHub and the model endpoint faked); and in the browser, on the production build, every step done in the panel (`01-shell` to `03-first-run`, the runner being the real `ostra runner` approved with a device code), the checklist's own buttons leading to each step's page, the first task started from a prompt, and Home dropping the checklist once it is done. Not proved:
  - **"After `docker compose up`"**: this machine has no Docker, and no test runs the checklist on `deploy/compose.yaml`. The e2e stack starts the panel and core from the production build the way `pnpm dev` does (milestone 1's demo), not from the images. What would prove it: the same specs run against `docker compose up` on `deploy/compose.yaml` (F-001), in CI on Linux.
    - **Built, not yet run (ticket 22, 2026-11-20).** `apps/web/e2e/compose-e2e.sh` runs `01-shell`, `02-setup` and `03-first-run` against a fresh `docker compose up` of the install guide's compose file and images, with the fake GitHub and the stub model beside it (`e2e/fakes.ts`, `e2e/compose.e2e.yaml`); the `docs-commands` job of `proof.yml` runs it after the guide's commands, and uploads `compose-e2e.log`. The outside-stack mode was checked on this machine against a stack started apart (`OSTRA_E2E_PANEL_URL`, `OSTRA_E2E_CORE_URL`): the specs signed in, changed the default password, connected the fake GitHub's App, created a project and approved a runner's device code, and failed exactly where they fail on their own stack. The compose half needs Linux with Docker; its log goes in `context/specs/m7-launch/demo/` and is cited here once the job has run.
    - **The three specs fail on `main` today, on either stack**, for changes after they were written: the checklist puts Linear fourth, live with "Skip for now", where `01-shell` expects "milestone 2" and `02-setup` and `03-first-run` expect it last (F-076's order; ticket 24 settles it); `02-setup`'s "Allow on personal runners" switch is no longer on the provider's page; and `03-first-run`'s `getByRole("status")` after Approve matches two elements. The job's run proves this condition only once they pass again.

What would prove it: milestone 2's live Linear step (F-005, `context/brand/app-targets/m2/home-first-run.md`), skippable, with a test that setup completes without it and that connecting Linear ticks it.
