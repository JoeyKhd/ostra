- Ticket 11's other break-its, each restored: the rule's labels left out of `requiredLabelsInTx` (the kind, profile and labels test failed at the admission gate), and `dryRunAutomation` without its `matched-before` lookup (the dry run's test failed).
- **Ticket 24 (2026-11-20)** added the automations API (`packages/api/src/routers/automations.ts`): `list`, `get`, `dryRun` and `history` for any member who can open the project; `create`, `update`, `pause`, `resume`, `delete` and `startAll` for a project admin, each through the domain's use cases and their audit entries. A rule's input is strict, so a `repoId` is refused before anything is read. Its profile must be one every member who can open the project may use (built-in, open to everyone, or listed with each of them on it). Its pool labels are checked against the project's pools: a label no runner of them carries is returned as `labelsNoRunnerHas` (the editor's "its tasks would wait" line), not refused, as the screen target says. The dry run adds each row's title, the task a `has-task` skip names, and `has-sub-issues` for a code start on a parent (F-077), so `startAll` starts exactly its `would-start` rows. The first row stays `partial` only for the tracker's own project (ticket 06's note).
