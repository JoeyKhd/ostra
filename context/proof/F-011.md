## Notes

- **Ticket 06 (2026-11-20)** built `intakeFilterSchema` and `matchesFilter` (`packages/domain/src/automations/intake-filter.ts`), pure over milestone 2's cached ticket, each field with a near miss, and the rule's lifecycle (pause at the hourly limit, resume, delete). The first row stays `partial` until ticket 11's ingest starts the task once per ticket per rule under replays and two replicas; the rule's kind, profile and pool labels (`AutomationSettings` in `m6-signatures.ts`) and the dry run are tickets 11 and 24's.
- The cached ticket has no column for the tracker's own project yet: `FilterTicket.trackerProjectId` is `null` until ticket 11's ingest fills it, and a filter on a tracker project then matches nothing (its near miss is tested).
- **Ticket 11 (2026-11-20)** built intake rules on milestone 2's real ingest (`packages/domain/src/automations/intake.ts`, `intake-enqueue.ts`, the ingest's `enqueueIntakeMatchesInTx` in the webhook's and the poll's transactions), tested on the Jira fake through core's webhook handler and `pollBoard`, with `intake.match` on two pg-boss workers over two database clients. The first row stays `partial` for one part of its sentence: the cache has no column for the tracker's own project, so a filter on it matches nothing (ticket 06's note). Adding the column is a migration a later ticket owns; the Jira fake also assigns nobody, so an assignee's near miss is ticket 06's pure case.
- The hourly limit pauses the rule and writes an `automation_paused` notification for each of the project's admins, not a needs-you item: a needs-you item belongs to a task (`NeedsYouItem.taskId` is required) and a paused rule has none.
- Ticket 11's other break-its, each restored: the rule's labels left out of `requiredLabelsInTx` (the kind, profile and labels test failed at the admission gate), and `dryRunAutomation` without its `matched-before` lookup (the dry run's test failed).
- **Ticket 24 (2026-11-20)** added the automations API (`packages/api/src/routers/automations.ts`): `list`, `get`, `dryRun` and `history` for any member who can open the project; `create`, `update`, `pause`, `resume`, `delete` and `startAll` for a project admin, each through the domain's use cases and their audit entries. A rule's input is strict, so a `repoId` is refused before anything is read. Its profile must be one every member who can open the project may use (built-in, open to everyone, or listed with each of them on it). Its pool labels are checked against the project's pools: a label no runner of them carries is returned as `labelsNoRunnerHas` (the editor's "its tasks would wait" line), not refused, as the screen target says. The dry run adds each row's title, the task a `has-task` skip names, and `has-sub-issues` for a code start on a parent (F-077), so `startAll` starts exactly its `would-start` rows. The first row stays `partial` only for the tracker's own project (ticket 06's note).
