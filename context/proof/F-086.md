**Partial: the first condition.** Proved: an organization admin, and only one, creates a project with one repo the organization's GitHub App installation lists, its one environment (drafted from the repo), the built-in OpenCode profile as the default for each task kind (refine, code, review), and the organization's default runner pool; boards are none. Not built yet, so not proved: several repos, boards from Linear, and choosing the pools (milestone 1's "Building" note: they come later; milestone 2 adds the boards). What would prove them: the same router test with two repos, a Linear board, and a pool list, once `projects.create` takes them.

**A bug the second condition found (2026-11-19).** `command`, `blob` and `blob_upload` have a nullable `projectId` and link to their task by the composite key `(taskId, projectId)`. Postgres checks a composite foreign key only when all its columns are set (MATCH SIMPLE), so a row with a `taskId` and no `projectId` named any task, or one that doesn't exist, unchecked. The migration `20261119233000_task_records_carry_project` adds a check to each: a row that names a task names its project.

Notes (2026-11-20, milestone 5's ticket 27): a project's pools are an ordered list with a share each, set by its admins and the organization's through `projects.setPools` and read through `projects.runners`; a pool of another organization or one listed twice is refused and nothing changes. The first row stays `partial` until the project's Runners settings show the list (ticket 32).

Notes (2026-11-20, milestone 5's ticket 32): a project's Runners tab shows its pools in order with each share, the boxes it holds in each against the share, its default size and the line on personal runners; its admins reorder the pools by drag or keyboard, set a share, add and remove a pool, through `projects.setPools`. The first row stays `partial` for several repos and boards from Linear (above), not for the pools.
