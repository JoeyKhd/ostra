## Notes

- 2026-11-19, ticket 03 (m4): four rows are `partial`, for the adapter contract and the fake code host only. `CodeHostAdapter` gains `listReviews`, `publishCheckRun` and `updateCheckRun` (idempotent by head and name), the `pull_request_review` webhook and the capability `reviews`; the code host contract suite checks them on the tiny host (the suite's cases live in `packages/adapter-sdk/src/testing/code-host-suite.ts`, so the rows cite the fake's own tests). The fake's branch protection has both of ADR 0040's modes, `in_progress-blocks` and `only-failing-blocks`. The check itself (the evaluator, publishing on each PR, moving both ways) is core's ticket 18, GitHub's side is ticket 08, and which mode GitHub is comes from the live run on `test1` (ticket 41).
- 2026-11-19, ticket 06 (m4): the evaluator, ported from spike 4 with drivers as members and approvers through verified links, and the check's lifecycle per head, as pure code in `packages/domain`. Row 6's lifecycle test has no break-it of its own: ticket 18's webhook test is the one to cite there.
- 2026-11-19, ticket 08 (m4): GitHub's side. `listReviews` reads every page of `GET /pulls/{n}/reviews` (the author's ID and login, `isBot` from the author's type, the state lower-cased, the commit and the time); `publishCheckRun` lists the head's runs of this App by name before it creates one, and `updateCheckRun` PATCHes it, each with a token for the one repo and `checks: write`; `parseWebhook` reads `pull_request_review` (`synchronize` was already read). GitHub passes the code host suite's milestone 4 cases against the fake GitHub, which now holds reviews and check runs, and the live run on `test1` published one check run on a PR's head through two publishes, updated it to success, and read the App's own comment review as a bot's (the evidence file). A reviewer user's approval and its webhooks wait for ticket 42; which branch-protection mode GitHub is waits for ticket 41's run with branch protection set.
- 2026-11-19, ticket 18 (m4): core's side. `review.evaluate` (`apps/core/src/reactions/review-check.ts` over `evaluateReviewCheck` in `packages/domain/src/review/review-check.ts`) lists the PR's reviews, maps each reviewer through the verified links to the organization's active members, takes the drivers from `TaskCoAuthor`, runs the evaluator, keeps the result in `ReviewCheck` per head, and only when it changed publishes or updates the check run and writes `review.check_updated`. It's enqueued (keyed by PR and head, 10 s later, grouped by connection) by a `pull_request_review`, a `pull_request` `opened`/`reopened`/`synchronize`, a PR ostra opens, a link or unlink, a new co-author from an `@ostra` comment, and the PR reconcile. A waiting check is `in_progress` through one switch (`REVIEW_CHECK_WAITING`); rows 3 and 7 stay partial until ticket 41's live run on `test1` with branch protection says which mode GitHub is. Proved against core's fake code host, which now holds reviews and check runs (`FakeReviewsAndChecks`).
- 2026-11-19, ticket 30 (m4): `tasks.get` carries each PR's check: its newest head's state (`waiting` or `passed`), reason and approver, and every head's, per repo.
- 2026-11-20, ticket 39 (m4): the task header shows each PR's `ostra/independent-review` state in words ("Waiting for an independent reviewer", "Only drivers approved", "Approved by Sam"), from `tasks.get`'s `reviewCheck` (`apps/web/e2e/16-repos.spec.ts`). The `in_progress` row stays `partial` until the real-repo run (ticket 42).
