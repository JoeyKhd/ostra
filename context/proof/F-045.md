Notes (2026-11-19, milestone 1's ticket 41): the box's sidecar against a fake peer, with real ingest, grace and stop reactions; a real box waits for a Linux machine with Docker (F-017).

Notes (2026-11-19, the flaky-test pass):

- The race test used to set the moment with timers (twelve ingests 3 ms apart, the grace at 15 ms), and asked for at least one refusal, so it failed under load whenever the grace took the lock after every ingest. It now pins the moment: a blocker holds the task's row until five ingests and the grace all wait on it (each sent only once the one before is waiting, read from `pg_stat_activity`), then lets them go together. Postgres grants a row to its waiters in no promised order (a run under load showed two ingests overtake the grace), so the checks hold for every order: the rows of the old epoch are exactly the ones the grace saw, once each; every batch was acked at or behind the fence or refused; and a batch sent after the grace is refused and stores nothing.
- Pinning the order showed a race in the product: ingest read the session's cursor before it took the task's lock, so a batch that waited behind another batch of its session saw the old cursor and asked again for an event already stored (`resendFrom`). Ingest now reads the cursor again under the lock (the second test, where one batch waits while the lock's holder saves the event before it), and so does the skip of an event the database refuses even as a placeholder, which could otherwise have moved the cursor back.
- Both tests passed 30 of 30 runs in a row on Windows 11 while the whole repo's tests ran at concurrency 16 (`pnpm turbo run test --concurrency 16 --force`), and the whole-repo runs passed 8 of 8 alongside (2026-11-19).
- The contract test of the sentence is this integration test of ingest against Postgres; no contract suite covers ingest.
- Row 4 stays partial: the tests show that what arrived before the grace is stored once and what came after is refused, not that the work is on the branch and the hidden ref.
