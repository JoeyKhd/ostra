## Notes

- Ticket 23, 2026-11-19: core's half, against the fake code host. The runner running the checks after a turn is ticket 32; the panel's Checks tab is tickets 39 and 47; the environment's check editor is ticket 48. The rows stay `partial` until those land and a live run on `ostra-test` shows the PR body and the draft (ticket 50).
- 2026-11-19, ticket 09 (m3): `partial`. The adapter makes a PR a draft and ready again, idempotently (live on `test1`). The live run found that GitHub's draft mutations need `contents: write` besides `pull_requests: write`; the adapter mints both, and the fake refuses without them, as GitHub does. Running the checks and making the PR a draft on a failure are tickets 23 and 32.
- Ticket 40, 2026-11-19: `environments.checks.list`, `.save`, `.reorder` and `.delete` (project admins edit; a new check goes last, after any new order). The editor is ticket 48.
- 2026-11-19, ticket 32 (m3): the runner's half of the second row. After a turn with changes it commits, runs the checks that apply to the repos the turn changed (Q188) through the executor, each with its timeout and all within the spec's total, uploads each output as a blob, reports `check.started`, `check.finished` and `session.saved`'s `checks`, then pushes whatever they found; a turn without changes runs none. Proved on `host` with the real executor (`apps/runner/src/task-host/turn-checks.test.ts`).
- 2026-11-19, ticket 23 (m3), live prep: GitHub's `getPullRequest` now returns the PR's `body` and `draft`, which core's checks section and draft rules read; before, on GitHub, a later turn rebuilt the description from ostra's parts (dropping a person's edits) and a person's draft wasn't seen.
- Ticket 48, 2026-11-19: the panel's check editor. A project admin adds a check from its sheet on the environment's `Services and checks` tab, and the list shows it in order with its command, repo and timeout (`apps/web/e2e/08-environment-services.spec.ts`); reordering by the handle or `Alt+↑`/`Alt+↓` saves through `environments.checks.reorder`. With core, the API and the runner in, the first row is `proved`.
- 2026-11-19, ticket 14 (m3): on `docker`, the checks run in the agent's container as the agent's user through the bridge to the box's init, with the host executor's timeouts and tree reap on the task volume. The executor contract suite's checks cases run against the `docker` executor with the real bridge in-process (`packages/adapters/adapter-executor-docker/src/docker-executor.contract.test.ts`, "F-054: runs the checks in order: one passes, one fails, one times out, each with its exit and time" and the others); the break-it: `runChecks` not delegated to the inner executor failed all three.
- 2026-11-19, tickets 23 to 25 (m3), live on `test1` (`apps/core/evidence/m3-pr-live.txt`): core's PR opener on the real GitHub adapter opened a draft for a failing check with the Checks section, then marked it ready on the next passing turn, edited the section in place and kept a person's line in the description.
