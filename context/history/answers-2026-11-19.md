## 2. Every question, answered

#### Q107 · A code task whose PRs end mixed
**Decision.** A code task's state follows its PRs, whichever order their events arrive in:
- at least one PR is open: in review
- none is open and at least one merged: merged
- none is open and none merged: stopped (`prs_closed`)

The repo whose PR closed shows "closed unmerged" on the task. Reopening the task leaves that repo's branch alone, and the task's next push to it opens a new PR. A PR that someone reopens on GitHub puts the task back in review, at "waiting for a reviewer". The ticket follows the task, as for any merge.
**Why.** This is the recommendation, plus the thing it left out: order. As the domain model was worded, "merged when the last one merges" and "stopped when every open PR closed" gave two answers for the same pair of PRs, depending on which event came last, and neither webhooks nor the reconcile (F-044) promise an order. A rule over the set of PR states gives one answer, and lets the reconcile correct a task to it. *Stopped* was the alternative: rejected, because code from the task is on the default branch and "stopped" tells a member that nothing landed. A needs-you item was the other: rejected, because a person closed that PR on GitHub on purpose, and ostra would be asking them to confirm it. Linear's own integration waits for "the final linked PR" and doesn't say what a closed one counts as (https://linear.app/docs/github), so there is nothing to match there.
**Confidence:** high for the rule, medium for the ticket moving to "done" on a mixed ending. **Revisit if:** teams close one PR of a set and expect the ticket to stay open. Then a mixed ending moves no ticket and says so on the task.

#### Q108 · Can a drained runner come back? · Changed
**Decision.** Yes, by an admin's **Resume**, and not by reconnecting.
- Draining is an admin's hold. The runner takes no new tasks, its running tasks finish, and it stays draining through disconnects and restarts.
- Resume returns it to online, or to offline when it isn't connected.
- An admin can drain a runner that is online or offline.
- A runner that shuts down for an upgrade isn't draining. It stops taking tasks by reporting no free slots, and it is online again when it reconnects, with the same identity.
- Only revoke is final (Q131).

**Why.** The recommendation's "draining → offline for a planned restart" lets a dropped connection cancel an admin's decision: a machine drained for maintenance would take tasks again after any network blip or reboot. A hold that someone placed should last until someone lifts it, which is how Kubernetes' cordon and uncordon work. The case the recommendation had in mind, an upgrade, needs no hold: on `docker` and `kubernetes` a pool runner's restart doesn't interrupt its boxes (ADR 0029), and on `host` a graceful stop is the runner's own doing. The dispatcher offers tasks to `online` runners only, so a hold kept on the server survives whatever the runner's process forgets.
**Confidence:** high. **Revisit if:** runners update themselves on the server's hint. That update then drains and resumes by itself, as one recorded action.

#### Q126 · Containing a task's processes on the `host` executor · Changed
**Decision.**
- **Windows:** a job object per task with kill-on-close, made and held by the runner through `koffi` **[new dependency]**, an FFI library. Not a helper program.
- **Linux:** the cgroup the executor already uses. Where the runner has none, the process tree plus the marker sweep below.
- **macOS:** the agent's process group and the tree snapshots, plus a new sweep: every process of the runner's user that carries the task's marker in its environment ends with the task.
- The third allowed difference stays and is reworded: containment is weaker wherever the machine gives no kernel unit. The runner reports which containment it has, and the panel says so on that runner.

**Why.** `research/host-process-containment.md` has the comparison and a run on this machine. The recommended helper program needs a second language, a Windows build for two architectures and an unsigned binary of ostra's own, which ADR 0046 keeps out of v1. `koffi` is prebuilt, MIT, about 3 MB on Windows and loaded nowhere else, and the code stays TypeScript (ADR 0008). In the run, a job made this way ended a helper that had detached itself and whose parent had exited, which the tree kill missed, and the kernel ended it when the process holding the job was killed. A runner that holds the handle can also ask the job what is in it, which a helper couldn't tell it. Node's own `node:ffi` is the same idea with no dependency, but it is experimental and absent from the Node versions the CLI supports.
**Confidence:** high for Windows, medium for macOS, where nothing has run. **Revisit if:** the CLI's minimum Node has `node:ffi` out of experimental (then `koffi` leaves), or the Mac run shows the sweep misses the contract case.

#### Q129 · A token scoped to its task for the box's sidecar
**Decision.** As recommended, with its open ends decided.
- **What it is.** A task token, made by core, that names the organization, the task, the lease epoch, the box and the runner.
- **How long it lasts.** As long as that lease is the task's current one. No clock and no renewal: a stop, a release, the grace, a new dispatch or a revoke ends the lease, and the token with it.
- **What it may do.** Connect as that box's sidecar; send that task's events, live text and command results; receive that task's commands; read that task's spec and credentials; move that task's archives and files on the bulk path. Nothing of another task.
- **How it arrives.** The runner asks core for it, for a lease it holds, when it makes the box, and hands it to the sidecar in a file that only the sidecar's container mounts. Never an environment variable or an argument, and never in the agent's container.
- **What the runner loses.** On `docker` and `kubernetes`, a task's credentials go to its task token only. The runner's own token no longer gets them.
- **`host`** is unchanged: the runner's process is the sidecar and uses its own token.

**Why.** The plan always said this (ADR 0029, ADR 0034, the domain model). Milestone 1 built the sidecar on the runner's token because the protocol had no other, and core doesn't accept a sidecar's connection at all yet. The recommendation left the lifetime as "the lease's length". A token with its own clock was the alternative: it needs renewing, and a sidecar cut off for nine of the grace's ten minutes would come back holding an expired token and lose a task the grace was there to save. The lease already ends when it should, and core checks it on every write. A one-time code traded for the token was the other alternative: rejected, because a sidecar that restarts while its runner is down could never trade again, and ADR 0029 promises that a runner's restart doesn't interrupt its boxes.
**Confidence:** high. **Revisit if:** a box needs to outlive its lease, which nothing in the plan asks for.

#### Q130 · Join tokens made in the panel are refused by core
**Decision.** As recommended, with one change. Core accepts any join token of a pool that hasn't expired and isn't revoked, the bootstrap one included, with the rule of one runner name per pool. The join's audit entry names the token. **Changed: the pool's "require approval" switch is enforced in the same change,** not in milestone 5. A runner that joins such a pool stays `joining`, gets no task, and waits for an admin to approve or reject it. The notification to admins waits for notifications (F-036). A pool runner on the `host` executor stays refused until the admin's opt-in exists (F-015).
**Why.** A token that nothing accepts is a bug, as the question says. But core moves every joining runner to online at its first connection today, whatever its pool says. Accepting panel-made tokens without the approval check would turn a harmless dead button into a pool whose approval switch does nothing, and a join token is worth every secret of every project that may use the pool (ADR 0029). The audit entry isn't something to wait for either: the code writes one at every join already. Hiding the button until milestone 5 was the alternative: rejected, because a second machine needs a token as soon as there is one, and the Linux host for F-017's live test is the first.
**Confidence:** high. **Revisit if:** never.

#### Q131 · No way to revoke a runner in the panel
**Decision.** As recommended, with two changes.
- An admin revokes a runner in any state but `revoked`. **A member can revoke their own personal runner.**
- A connected runner gets `evict` and a close with 4403 at once, and can't get a new access token.
- **Changed: its leases end in the same transaction,** not after F-045's 10-minute grace. The epochs go up, its tasks stop as `runner_lost`, and each is ready to reopen on another runner.
- The task endpoints refuse a revoked runner's access token, even one that hasn't expired yet.
- Draining stays the polite way to retire a runner.

**Why.** The grace exists for a runner that may come back, and a revoked one can't. Leaving its leases open for 10 minutes would let an access token minted just before the revoke fetch a task's credentials until it expires, which is the leak a revoke is for. A member needs it for their own machine because a lost laptop can't wait for an admin.
**Confidence:** high. **Revisit if:** never, short of dropping runner keys.

#### Q132 · A queued task while its offer is out
**Decision.** Keep what is built: the task stays `queued` while a runner's offer is open and moves to `preparing` when the runner accepts. Ticket 26's wording is corrected. **Changed in how it shows:** the task page says why a queued task waits, from data and not from a sentence core wrote: "offered to <runner>" from the task's open lease, and the reason no runner fits as a code with its values, worded in the panel's message files.
**Why.** `preparing` means a box is being made, and an offer makes none. Keeping the task queued leaves a refused or unanswered offer nothing to undo, and gives the lifecycle no arrow back. Showing it from the dispatch note, as recommended, would put a sentence composed on the server into the panel, which F-083 rules out, and core empties the note when an offer goes out. Today the panel shows neither: the note is stored and no screen reads it.
**Confidence:** high. **Revisit if:** offers stay open for long on autoscaled pools. They shouldn't: such a runner accepts at once and reports "waiting for a node" (ADR 0029).

#### Q133 · Where the agent starts, and a file written outside every repo
**Decision.** As recommended, with the task's state made precise.
- With one repo the agent starts inside it. With several it starts at the workspace root, and its instructions name each repo's folder.
- After every turn, the task host lists what sits in the workspace root beside the repos' folders and ostra's own. If there is anything, it records the paths in an event and raises a needs-you item for the driver that names them.
- The turn's other results go ahead: a repo that changed still gets its PR. When no repo changed, the task needs you for this reason and not for "no changes".
- ostra never moves, commits or uploads those files, because it can't know which repo they belong to. They stay in the box, and answering while the box is kept lets the agent move them.

**Why.** Detection is the same code on every executor. Making the workspace root read-only was the alternative: rejected, because it works differently on Windows, in a container and for a single OS user, and `AGENTS.md` makes a difference between executors a bug. Holding the PR until someone looked was the other: rejected, because a task with an open PR is in review by definition, and the work in the repos is real.
**Confidence:** medium. **Revisit if:** the item is noise in tasks across several repos, where an agent at the root leaves caches behind. Then the instructions name a scratch folder, and the list ignores it.

#### Q136 · Spec section 11's ten choices
**Decision.** Confirmed: 1, 2, 3, 4, 6, 7, 8 and 10. Changed: 9. Item 5 is Q126. Items 1 and 10 gain a guard.

| # | Choice | Verdict |
|---|---|---|
| 1 | The secrets key is generated on first start | **Confirmed, with a guard.** At start, the server checks that its key can read the database's secrets, and refuses to start when it can't. The key that signs runners' tokens gets a setting, as the other two generated keys have |
| 2 | Ports 3000 and 8787 in development | Confirmed |
| 3 | "Use an existing App" beside the manifest flow | Confirmed, and kept for good: an organization whose owners create Apps themselves needs it |
| 4 | The co-author trailer from the member's ostra name and email | Confirmed until F-119. Until a member links GitHub, their ostra email goes into commit messages, which F-119's row now says |
| 5 | Process containment on Windows | Q126 |
| 6 | OpenCode's permissions with no approval rules | Confirmed until F-026 |
| 7 | Variables and secrets in each repo's checkout on `host` | Confirmed. The spec's sentence is corrected to what was built: the setup script gets only the entries marked "available during setup" |
| 8 | One session is one turn | Confirmed for milestone 1. Milestone 2 ends it |
| 9 | The setup shell is `bash` from `PATH` | **Changed.** On Windows, `bash` means Git for Windows' own bash, found from the `git` the runner uses, and never the WSL launcher. A full path in `OSTRA_RUNNER_SHELL` is used as given |
| 10 | Branch names from the task ID's last 8 hex digits | **Confirmed, with a guard:** a unique index on a project's branch names |

**Why.**
- **Item 1.** A generated key is right for one machine, where the panel and core share the data folder, and the self-hosting rule wants an install with no settings. The failure it invites is a database restored without its key, or a second server process with a folder of its own. Every stored token is then unreadable, and today the first sign is a task that fails. A check at start says so before anything runs. The key that signs runners' access tokens lives only in that folder, with no setting, so two core replicas without a shared folder would refuse each other's tokens. ADR 0034 says any replica serves any request. Requiring the key as a setting was the alternative: rejected by the self-hosting rule.
- **Item 9.** On this machine `bash` isn't on `PATH` in PowerShell: Git for Windows puts only its `cmd` folder there, which holds `git` and no `bash` (checked: no folder on the machine's or the user's `PATH` holds a `bash.exe`). So `ostra runner`, started from PowerShell the way the panel's own command says, stops at its health check and asks for `OSTRA_RUNNER_SHELL` (read from the executor's health check, which runs `bash --version`; the runner itself wasn't started for this). Where WSL is installed, `bash` is its launcher, the check passes, and setup scripts run on another computer (from Windows' documented behaviour, not run here: this machine has no WSL). The runner needs `git` anyway, and Git for Windows always ships its bash.
- **Item 10.** Two tasks share a branch only with the same title and the same eight digits, which are 32 random bits. A schedule that starts the same title every night makes the same title ordinary: 365 such tasks in a project are about 1.5 chances in 100,000 of a shared branch in a year, and about 1.5 in 100 across a thousand projects. F-016 says two tasks never share a branch, and an index makes that true. The first eight digits, a timestamp, already collided in the demo.
- **Items 3, 4, 6, 7 and 8** stand as built. Item 4 is the one with a cost: an email in a commit message can't be taken back. ADR 0052 (Q183, settled the same day with milestone 3's spec) puts the linked account's no-reply address in the trailer, and a member who never links keeps their ostra email there.

**Confidence:** high. **Revisit if:** item 1's check gets in the way of rotating the secrets key (then the check is kept per key version, which the rows already carry).

## 3. Q109 and Q110: sharpened, not settled

These stay with the maintainer, and want a lawyer.

*Later the same day the maintainer decided otherwise, and section 5 settles both. The text below is kept as the record of what was weighed first.*

**Q110 first.** The licensor line is a GitHub handle. The license, the CLA and any commercial license all name the licensor, and each needs a legal person behind the name. Three things the recommendation didn't say:
1. **The deadline is the first of four events, not the launch:** the first contribution from anyone else, the first commercial license, the first terms for the hosted version, and the first release a company's lawyers will read. The first of these can come before milestone 7, because from milestone 3 ostra's own tickets run through ostra, driven by the maintainer's team (Q101).
2. **A person now and a company later needs a written assignment** from the person to the company, of everything written until then. That is one document while one person holds the copyright, and many once others have contributed. So if a company is planned for the hosted version, it is cheaper to form it before the CLA exists.
3. **The same legal person should hold the name.** The license leaves "the licensor's trademarks" to trademark law, and a mark needs an owner.

**Q109 then.** What the recommendation left open:
1. **It covers the team too.** "Outside contribution" reads as strangers. Anyone who isn't the licensor needs an agreement before their code goes into the hosted version or a commercial license: the maintainer's team and any contractor included. An employment or contractor agreement that assigns the work does the same job as a CLA.
2. **A license grant, not an assignment.** The contributor keeps their copyright and gives the licensor a lasting license with the right to license the contribution on any terms. That is all the hosted version and commercial licenses need. n8n, whose license ostra uses, asks for exactly this in one sentence: "I give n8n permission to license my contributions on any terms they like" (https://github.com/n8n-io/n8n/blob/master/CONTRIBUTOR_LICENSE_AGREEMENT.md).
3. **Granted to the licensor "and its successors and assigns",** so Q110's answer can change later without every contributor signing again.
4. **One agreement for the whole repo,** the Apache-2.0 packages included, so code can move between packages.
5. **Check the tool when it's needed.** The GitHub Action most projects used for a signature on the pull request was archived in March 2026 (https://github.com/contributor-assistant/github-action). Whatever replaces it should keep the signatures in a repo the licensor owns.

### Q109: the contributor agreement

**Decision.** A contributor is anyone but the licensor whose work is merged into the repo. Before that happens they agree to a six-point license grant in `CONTRIBUTING.md`, by ticking a box in their pull request. A workflow of ostra's own fails a pull request without the ticked box. **Changed** against section 3 in three ways: a box in each pull request and not a signature kept in a separate repo, one form and not two, and no lawyer's review.

**Why.**
- **What "contributor" means.** The maintainer's question was whether it is someone who pushes to the repo. It is anyone whose work ends up in it and who isn't the licensor: a teammate who pushes, a contractor, a stranger whose pull request is merged. Someone who only opens issues or reviews contributes no code, so there is nothing to license.
- **Why an agreement is needed at all.** By GitHub's terms, what a person adds to a repo with a license is licensed "under the same terms", unless "a separate agreement [...] such as a contributor license agreement" says otherwise (Terms of Service, D.6: https://docs.github.com/en/site-policy/github-terms/github-terms-of-service). For the server and the panel those terms are the Sustainable Use License, which allows internal or non-commercial use, sharing only free of charge, and is "non-sublicensable" (`LICENSE`). The maintainer would hold a contributor's lines on those terms too. The hosted version and commercial licenses, which ADR 0048 keeps for the maintainer, would then be closed to any file a contributor touched.
- **Against a DCO sign-off.** It certifies origin: "I have the right to submit it under the open source license indicated in the file" (https://developercertificate.org). It grants nothing more than that license, so it leaves the problem above as it is. ADR 0048 had already replaced it for this reason, and this confirms it.
- **Against "no outside code until it's needed".** It is the least work today. But "outside" includes the maintainer's team, and from milestone 3 they work on ostra through ostra (Q101), so it's needed within the plan, and a rule that says "nobody but me" breaks the first time someone helps. Three small files settle it for good.
- **Against a CLA service or bot.** The hosted services are a vendor, and the action most projects used is archived (section 3). `AGENTS.md` asks before either is added, and neither does more than a box and a few lines of shell.
- **Why a license and not a transfer.** The hosted version and commercial licenses need the right to license contributed code on any terms, and nothing else. n8n, whose license ostra uses, asks for exactly that: "I give n8n permission to license my contributions on any terms they like" (https://github.com/n8n-io/n8n/blob/master/CONTRIBUTOR_LICENSE_AGREEMENT.md, read 2026-11-19). ostra's text says the same in point 2 and adds what section 3 asked for: the licensor's successors and assigns, patents, the contributor's right to give it, and one yes for all of a person's contributions.
- **Why a box in each pull request, and not a list of signers.** The box is checked from the pull request's text alone, so the check needs no checkout and no stored state. A list in the repo means every first pull request also edits a shared file. The cost is a tick per pull request, which the template already holds.
- **Why one form.** Section 3 suggested an individual and a company form. Point 4 has the contributor state that their employer or client allows it, which is what a company form would establish. A company that asks for its own form is the day to add one.
- **Why `pull_request_target`.** That event "runs in the context of the default branch of the base repository" (https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), so a pull request can't edit its own check, and such workflows "will always run, regardless of approval settings" (https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository), so a first-time contributor sees the result without the maintainer approving a run. The event is dangerous when a job runs the pull request's code. This job checks out nothing, uses no action, has no permission and no secret, and reads the description through an environment variable, which the run above shows is treated as text.
- **Bots.** A bot can't agree for a person, and ostra's own agents fill in a repo's pull request template (F-078), so a ticked box in a bot's pull request proves nothing. The check passes Dependabot, which only bumps versions, and refuses every other bot unless its account is on the workflow's one-line list. ostra's own App joins that list when ostra's tickets run through ostra, once everyone who can start tasks there has agreed in a pull request of their own.
- **The repository's owner passes without a box,** because the owner is the licensor, and nobody licenses to themselves. If the repo moves to an organization, no author is the owner any more and everyone ticks the box, the maintainer included. That is right when a company is the licensor, and harmless when it isn't.
- **Nobody has to agree after the fact.** Every commit so far has one author, the maintainer.
- **Why no lawyer's review.** The maintainer said so. The license's text is n8n's, unchanged, and the agreement is the same grant n8n takes, in the plain style of that license. A review stays the maintainer's choice at any time. ADR 0064 already treats an outside penetration test that way: a paid service the maintainer hasn't chosen is not a gate.

**Confidence:** high. **Revisit if:** a company asks to contribute under a form of its own; pull requests become frequent enough that a tick in each one annoys regular contributors, in which case a list of people who agreed once replaces it; or the maintainer prefers to keep pull requests closed until v1, which is one sentence in the README and in `CONTRIBUTING.md`.

### Q110: the licensor

**Decision.** The licensor is the person who holds the GitHub account `JoeyKhd`, and the line stays "JoeyKhd (https://github.com/JoeyKhd), the maintainer of ostra". No legal name enters the repo. **Changed:** section 3 recommended naming a legal person now.

**Why.**
- **What the line is for.** It tells a reader whose terms these are and whom to ask for other terms. A handle with its profile's address does both: it names one account, one person holds it, and anyone can reach them through it.
- **The name on a notice doesn't decide who owns the work.** The author does, under whatever name: copyright "vests initially in the author" (17 U.S.C. § 201(a): https://www.law.cornell.edu/uscode/text/17/201). The law names the case: a "pseudonymous work" is one in which "the author is identified under a fictitious name" (17 U.S.C. § 101: https://www.law.cornell.edu/uscode/text/17/101), and the Berne Convention treats a pseudonym that leaves no doubt about who is meant like a name (Article 15(1): https://www.law.cornell.edu/treaties/berne/15.html). Section 3 said each document "needs a legal person behind the name". There is one: the account's holder.
- **Section 3's four events, one by one.**
  1. *The first contribution from anyone else.* The agreement grants to the licensor that `LICENSE` names "and its successors and assigns", so it works with the line as it is and survives a change of the line.
  2. *The first commercial license.* It is a contract, and a contract is signed with a legal name. That name goes on the contract, not in the repo.
  3. *The first terms for the hosted version.* Terms of service name whoever runs the service, a person or a company, and invoices do too. Again outside the repo.
  4. *The first release a company's lawyers read.* They read a license whose text is n8n's, unchanged (`NOTICE`), and a licensor they can write to. A company that needs more than that is asking for a commercial license, which is event 2.
- **A person now and a company later is cheap,** which section 3 doubted. It warned of "many" documents once others have contributed. With a license grant to "successors and assigns" there is only ever one: the maintainer's own transfer to the company. Contributors' grants follow the licensor by their own words. The other way needs no document at all: the person stays the licensor and lets the company sell the hosted version.
- **The name "ostra".** Section 3 wanted the same legal person to hold it. The same person does: the licensor uses the name for the product, and the license leaves trademarks to "applicable law" (`LICENSE`). Registering the name is optional, takes a legal name on the registration and not in the repo, and v1 doesn't wait for it.
- **Privacy.** A name in a public repo's history is there for good. Nothing above needs it there.

**Confidence:** high. **Revisit if:** a company is formed, and then the maintainer picks one of the two ways in ADR 0048 ("The licensor"); or the maintainer wants the repo to name the same party as the hosted version's terms.
