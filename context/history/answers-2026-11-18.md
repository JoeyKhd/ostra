## 1. The ten most consequential decisions

1. **The shape is Organization → Project → Task, from the first migration.**
   - An install holds many organizations, and every row carries its organization.
   - An organization holds members, its GitHub App and Linear app, model providers, runner pools, agent profiles and budgets.
   - A project holds repos, boards, one environment, automations, memory and tasks.
   - Access is per project, with two roles at each level: admin and member. (Q28, Q30, Q35, Q102)

2. **A task belongs to a project and may change any of the project's repos.** Its box has every repo checked out side by side. It uses one branch name, and opens one PR per repo it changes. This replaces "one ticket, one repo". (Q29, Q7)

3. **Runners are programs people host anywhere, and no credential ever enters the agent's container.**
   - A runner joins a pool with a join token. Its executor (`docker`, `host` or `kubernetes`) gives each task its own box.
   - A box is the agent's container, an ostra sidecar and the environment's services.
   - The sidecar holds the task's keys. It proxies model calls and git, so the agent only ever sees a fake key and never a GitHub token. (Q38, Q93, Q17, Q26, Q27)

4. **OpenCode is the only agent in v1, driven over ACP by ostra's own driver on the official SDK.** Rivet Sandbox Agent is out.
   - What the maintainer liked about Rivet stays: start as many runners as you want with one key, and the work goes faster. That comes from pools and join tokens, which Rivet never provided.
   - What Rivet itself provided is a thin HTTP wrapper around ACP, and it's close to unmaintained. (Q45, Q51, Q103)

5. **Any model, on keys only.** A model provider is an API base URL and a token. ostra lists the models from the endpoint and takes names, limits and prices from models.dev. The sidecar's key proxy counts every call, so spend, budgets and the per-task cap rest on measured numbers. (Q34, Q47, Q105)

6. **Background work runs on pg-boss, not DBOS.** ostra's own tables say where a task stands, and jobs are short and safe to repeat. Postgres stays the only store an install needs. Files go through a blob store adapter that keeps them in Postgres by default. (Q24, Q76)

7. **The live task page uses the AI SDK's message types and assistant-ui's external store, fed by ostra's own event stream.** It doesn't use `useChat`. Text that is still being written is shown but never saved, and nothing acts on it. (Q23, Q50)

8. **Reopening on a fresh box is the normal case, so it has to be routine.**
   - After every turn, unfinished work goes to a hidden ref and the agent's own session archive goes to the server.
   - After 15 idle minutes the box stops.
   - A reopened task restores both on a new box, and falls back to a fixed rebuild from the ticket, the PR and the branch.
   - While OpenCode works, a new message waits for the turn to end, unless the driver chooses "Interrupt and send". (Q42, Q52, Q53, Q99)

9. **The whole team is in v1: three task kinds, and two review loops.**
   - Kinds: refine (ends in a ready ticket), code (ends in PRs) and review (ends in a PR review).
   - Loops: failing CI goes back to the coding agent, and so do the AI review's blocking findings. Both are capped.
   - The GitHub App opens every PR. An `ostra/independent-review` check lets a team require an approval from someone who didn't drive the task. (Q64–Q77, Q12, Q55)

10. **v1 has the platform's full shape and the least depth that works.** Every noun exists in v1: organization, project, environment, pool, provider, the three kinds, memory, budgets. Each has one adapter and the simplest rules. The scale floor is 1,000 tasks at once, proven by a load test before launch. The plan runs from milestone 0 to milestone 7. (Q1, Q18, Q77)

### Second-order consequences worth knowing

These follow from the decisions above. Each one changed something else in the plan.

- **Boxes stop after 15 idle minutes, so almost every reopen lands on a fresh box.** Restoring a session there stops being the rare path of ADR 0006 and becomes the common one. Spike 2 therefore gates the choice of agent as much as spike 1 does.
- **The GitHub App opens every PR, so the person who asked for the work could approve it.** That's why the independent-review check is in v1, and why the App's manifest asks for `checks: write` on the first day: a permission added later has to be approved again by every install.
- **Sign-in is username and password only, so ostra doesn't know anyone's GitHub identity.** Co-author credit, `@ostra` and reviewers all need it. So v1 has a "link your GitHub account" step that proves the identity and keeps no token.
- **Keys everywhere means a laptop runner would hold a real key** on a machine its owner controls. An admin has to allow that per provider.
- **One task for several repos removes a whole problem:** intake no longer picks a repo. It also means a repo that sits in two projects has two sets of secrets, one in each environment.
- **The agent never holds a token, so the hard refusal of unprotected default branches (F-060) loses its reason** and becomes a warning.
- **ostra never calls a model itself, so every structured result has to come from the agent:** the PR's text, a refine draft, review findings, memory proposals and environment proposals. All of them arrive through ostra's MCP tools in the sidecar. That server is needed by five features, not only by memory.
- **Budgets are only as good as the count.** The key proxy has to read usage from the stream in both API formats. An endpoint that reports none gets an estimate, and the panel says so.
- **Loops spend money without a person.** So budgets and the spend cap are built in milestone 4, and the loops in milestone 6.
- **A join token is worth every secret of every project that may use its pool.** It needs expiry, hashing and an audit trail from the start.
- **Many organizations per install, each with its own GitHub App and Linear app,** means webhooks are routed by connection, not by one install-wide address.
- **A Kubernetes pool can't work without a registry,** although round 14 calls the registry optional.

## 3. Every open question, answered

Q16, Q22, Q25 and Q60–Q63 are already settled in the file and aren't repeated. Rounds 13 and 14 were answered "yes", so they get a list of problems at the end and no new decisions.

### Before round 7

#### Q-20 · Jira's sign-in model
**Decision.** Jira Cloud connects through a service account that the organization owns, with a scoped API token, plus one admin webhook signed with a shared secret. ostra never asks a customer to create its own 3LO app and never collects members' personal tokens.
**Why.** Atlassian's rule is aimed at "individual 3LO apps" and at collecting tokens (`research/trackers.md` §2.2), and a service account avoids both. It also writes as a bot, so ostra can tell its own changes apart, and API-token traffic is exempt from the points quota. Admin webhooks don't expire, while dynamic ones last 30 days and allow five per user.
**Confidence:** medium. **Revisit if:** service accounts turn out to need a paid Atlassian plan (S-10 in that file). Then use a dedicated bot user with a scoped token.

### Round 7

#### Q1 · What "huge" means
**Decision.** "Huge" means the whole platform shape in v1: organizations, projects, environments, runner pools, any model, the three task kinds, budgets and the audit log, on a core that scales out. Depth inside each part comes after v1: more trackers, code hosts and agents, SSO, custom roles, allowlists.
**Why.** The maintainer rejected "a small tool" in round 8, and the graphite concept already shows the platform. Shape lives in the data model, which is the expensive thing to add later (ADR 0010's own argument). Depth is one adapter or one setting at a time (ADR 0025).
**Confidence:** high. **Revisit if:** a team that adopts ostra early can't use it at all without depth in one part, such as Jira or SSO.

#### Q2 · Environments at scale · Changed
**Decision.** In v1, ostra drafts each project's environment from its repos: lockfiles, tool versions, `.env.example`, `devcontainer.json` and compose files. An onboarding task (Q49) then checks the draft by running it. Organization-wide templates, and reviewing every repo in bulk, come after v1.
**Why.** People create projects one at a time, so detection per project covers the first teams. Detection is deterministic and costs no tokens, so it's the right step before an agent runs. Bulk onboarding pays off at fifty repos, which is a later problem.
**Confidence:** medium. **Revisit if:** a team has more than about 20 repos to bring in at once.

#### Q3 · Setup step 5
**Decision.** Superseded by projects. The first-run checklist becomes: the admin account, a model provider, the GitHub App, the first project (repos and environment), a check that the runner is online, the first task from a prompt, and then Linear as an optional step.
**Why.** A project replaces "prepare your repos" (Q28). Prompt tasks (Q31) mean the first PR no longer needs a tracker, which shortens the path to F-076's 30 minutes.
**Confidence:** high. **Revisit if:** people trying the install expect to connect the tracker first.

#### Q4 · Starting many tickets at once
**Decision.** In v1, from the Inbox (select several, start) and from a rule's dry run ("start all 23"). Every start passes the same gates as a single one: the queue, the project's cap on a pool, and the budget.
**Why.** Throughput is the first of ostra's three jobs (`project.md`), and this is cheap once the queue exists. The gates stop one burst from taking a whole pool, which `research/elastic-sandboxes.md` names as the risk of shared pools.
**Confidence:** high. **Revisit if:** bursts cause surprise spend. Then a bulk start asks for a confirmation that shows the estimate.

#### Q5 · Runners page
**Decision.** As recommended: a fleet view of the organization's pools. Each pool shows its busy boxes, queue, versions and labels, and each runner its state. Built with the fleet in milestone 5.
**Why.** Pools are the organization's shared infrastructure, so admins need one place to see them. The concept screen already exists (`runner-pools-graphite`).
**Confidence:** high. **Revisit if:** never, short of dropping pools.

#### Q6 · Insights
**Decision.** In v1, per organization and per project: PRs opened and merged, median time to first PR, time waiting on people, merge rate, tokens and spend. A scheduled job computes them from ostra's own tables every few minutes. They aren't live.
**Why.** The Home concept already shows these numbers, and budgets (Q105) need the same data. `research/live-sync.md` recommends that Insights stay out of the live feed.
**Confidence:** high. **Revisit if:** the queries get slow at scale. Then they move to rollup tables.

#### Q7 · Tickets spanning several repos
**Decision.** Superseded by Q29. A ticket that needs two repos is one task with two PRs, not a group of tasks.
**Why.** See Q29.
**Confidence:** medium, the same as Q29. **Revisit if:** Q29 is revisited.

#### Q8 · Elastic runners
**Decision.** Superseded by round 14. In v1, elasticity is the `kubernetes` executor: a pod per task, with the cluster's own autoscaler adding nodes. Hosted sandbox vendors can become community executors later.
**Why.** The maintainer's answer to Q36: runners run wherever people host them and join with a key.
**Confidence:** high. **Revisit if:** the hosted version needs a vendor's sandboxes for its own pools.

#### Q9 · Runner pools
**Decision.** In v1. A pool belongs to one organization. Each project lists the pools it may use.
**Why.** Confirmed by Q32 and round 14. Pools are also what the maintainer liked about "deploying many instances".
**Confidence:** high. **Revisit if:** the hosted version needs pools shared between organizations.

#### Q10 · Schedules on intake rules
**Decision.** In v1. An automation can run on a schedule: check its ticket filter at set times, or start a prompt task (for example "update dependencies every Monday").
**Why.** pg-boss keeps schedules in the database and sends one job however many replicas run (`research/durable-execution.md`), so this is a small addition. Scheduled work is a large part of what makes agents useful unattended.
**Confidence:** high. **Revisit if:** schedules are barely used in the first months. Then they stay as they are and get no more work.

#### Q11 · Spike 1 · Changed
**Decision.** The "settled" note is void. Spike 1 tests ostra's own ACP driver with OpenCode, on the test cases in `research/rivet.md`. It doesn't run the Sandbox Agent arm.
**Why.** The re-checked facts are enough to decide: it's built on ACP SDK 0.16 while the current one is 2.7, it has had one code fix since March, its transport dies on turns over five minutes, and its delete never kills the agent. Running a dropped component through 17 cases costs days and can't change the plan.
**Confidence:** high. **Revisit if:** plain ACP fails one of spike 1's must-haves.

#### Q12 · CI failures and review comments · Changed
**Decision.** In v1, two signals reopen a code task by themselves:
- CI fails on the task's PR. The agent gets the failing checks and their logs, for at most 2 rounds *(working value)*. This is F-035, moved to v1.
- A linked member submits a GitHub review that requests changes. The agent gets that review's comments as one prompt. A person asked, so no cap applies.

Every other comment still needs `@ostra` (F-053). The rest of F-034 stays later.
**Why.** PRs that arrive green are the point of throughput. "Changes requested" is an explicit signal that GitHub already has. Sending every comment would let anyone who can comment steer an agent and spend tokens, and comments are untrusted input (`AGENTS.md`).
**Confidence:** medium. **Revisit if:** teams ask for every review comment to count. Then F-034 becomes a project setting.

#### Q13 · A reviewer agent as a profile option
**Decision.** Superseded by Q64 and Q71. Review is a task kind with its own agent profile, not an option on the coding profile.
**Why.** Round 11 is the fuller design, and one mechanism is enough.
**Confidence:** high. **Revisit if:** never.

#### Q14 · Variants ×2/×3
**Decision.** Soon after v1, as recommended.
**Why.** Variants multiply spend, so they should arrive after budgets and Insights have run for a while. Nothing in the data model blocks them: a variant is a second code task for the same ticket, which is an exception to one rule.
**Confidence:** medium. **Revisit if:** the acceptance run (Q46) shows a wide spread between runs of the same ticket. Then variants move up.

#### Q15 · YAML workflows
**Decision.** After v1, and only if automations plus the two review loops prove too rigid.
**Why.** Workflows as configuration are a second product. The chain most teams want (refine, code, review, fix) is built into v1.
**Confidence:** medium. **Revisit if:** two or more teams ask for a chain that v1 can't express.

#### Q17 · Keys the agent can see
**Decision.** In v1, no model key and no GitHub token is ever in the agent's container. They live in the box's sidecar (Q26). An environment's own secrets stay visible to the code under test, as ADR 0020 already accepts.
**Why.** The agent runs untrusted input with a shell, so anything in its container can leak. The environment concept already promises this: the agent "never holds a provider key".
**Confidence:** high. **Revisit if:** spike 3 shows the sidecar layout doesn't hold. The fallback is Q27 as first written.

#### Q18 · Scale target
**Decision.** 1,000 tasks at once per install, on three core replicas and one Postgres *(working values)*. It's a floor we test, not a cap. Every server process is stateless, and Postgres does the routing. A load test with simulated runners is a gate for launch.
**Why.** The transport and the live stream are both designed for this number (`research/runner-transport.md`, `research/live-sync.md`). Not saving deltas (Q23) keeps event writes to a few thousand rows a second, by my estimate. "Infinite" then means that no single process is a bottleneck, and Postgres is the ceiling. Partitioning comes first, and one database per group of organizations is the later step for the hosted version.
**Confidence:** medium. **Revisit if:** spikes 6 and 7 miss their bars.

#### Q19 · Subscriptions versus scale
**Decision.** Superseded by Q47: keys everywhere, no subscriptions. Clouds that sign each request, instead of taking a token, come after v1 (Q34).
**Why.** The maintainer's answer in round 10.
**Confidence:** high. **Revisit if:** never.

#### Q20 · Rate limits
**Decision.** In v1.
- **Trackers and the code host:** each adapter's base class keeps a budget per credential in Postgres, fed by the response headers. A call that would overspend waits for the reset.
- **Models:** the key proxy reports rate-limit answers. The scheduler stops new dispatches on that provider until the retry time. Admins can cap the sessions at once per provider.
**Why.** Several core replicas share each credential, so a limiter in one process's memory isn't enough (`research/integrations-platform.md` §6.3). No queue library counts requests per hour, so this is ostra's own table whichever library ships (`research/durable-execution.md`).
**Confidence:** medium. **Revisit if:** the load test shows the budget table is a hot spot.

#### Q21 · Copying modules
**Decision.** Yes, as ports of logic that are retyped to ostra's rules, never as vendored files. Each port is named in one "borrowed code" ADR and in `NOTICE`. The first two are Rivet's agent launch table (milestone 1) and Cyrus's rules for turning agent events into Linear activities (milestone 6).
**Why.** `research/integrations-platform.md` found Cyrus's files too coupled to reuse and too loosely typed for `AGENTS.md`, while its rules are proven in production. ADR 0015's title needs amending to match.
**Confidence:** high. **Revisit if:** a port would exceed a few hundred lines. Then it gets its own ADR.

#### Q23 · Token-level deltas
**Decision.** As recommended. Text that is still being written goes to browsers at most every 250 ms and is never an event. Each completed message, and everything ostra acts on, is saved first.
**Why.** No control acts on partial text, so ADR 0011 loses nothing. Saving deltas would multiply the write load roughly tenfold at 1,000 tasks (my estimate, from the rates in `research/live-sync.md`). A viewer who joins late reads the current partial from one unlogged row (`research/agent-ui-stream.md`).
**Confidence:** high. **Revisit if:** spike 7 shows the unlogged table costs too much. The fallback carries the partial in the batched notification.

#### Q24 · The durable queue · Changed
**Decision.** pg-boss runs ostra's background work: webhooks, retries, timers, schedules and reconciliation. DBOS Transact becomes the fallback. Every import of the library sits in one package, `packages/jobs`. **[new dependency: `pg-boss`]**
**Why.**
- `research/durable-execution.md` sets three rules whichever library ships: ostra's tables are the source of truth, jobs are short with IDs fixed by what they do, and a human wait is a task state. Under those rules, DBOS's durable workflows have nothing left to do.
- pg-boss supplies the rest as it comes: enqueue inside the Prisma 7 transaction, heartbeats that free a dead replica's jobs, dead-letter queues, retention, schedules in the database, limits per group across replicas, and an MIT dashboard.
- DBOS keeps those same pieces (recovering a dead replica, retention, the dashboard, upgrading running workflows) in its proprietary Conductor or its paid extension. It moved the Conductor client out of the open package in October 2026.
- Installs upgrade on their own schedule (ADR 0022). A queue of small jobs that carry only IDs can't be stranded by an upgrade. A versioned workflow can.
**Confidence:** medium. **Revisit if:** spike 8 shows pg-boss can't hold a limit per key across three replicas, or can't recover a killed replica's jobs without a duplicate side effect. Then the same scenarios run on DBOS.

#### Q26 · Keeping keys from the agent · Changed
**Decision.**
- **Model keys:** a key proxy in the box's sidecar. The agent gets a base URL that points at the sidecar and a fake key that is valid for one task. The proxy swaps in the real key, passes the stream through untouched, and counts tokens. It handles both API formats the provider form offers.
- **GitHub:** a git proxy in the same sidecar. The agent's own `git` fetches and pushes through it. The proxy adds a one-repo token, and refuses any ref except the task's branches and its hidden ref.
- **Allowlists (F-052):** later.
- **Per-repo secrets:** accepted as visible to the code under test.
**Why.** `research/credential-proxy.md` calls the git proxy the next step after a runner-side push. With a sidecar it becomes the base, because the other design would run `git push` from the sidecar on a workspace the agent controls, and so run the agent's hooks and config beside the token. The proxy also closes ADR 0020's gap that a GitHub token can't be limited to one branch. Neither proxy needs a certificate authority or TLS interception.
**Confidence:** medium. **Revisit if:** spike 4 shows LFS or large packs break through the proxy. The fallback is a push from the sidecar's own clean clone.

#### Q27 · Separate OS user · Changed
**Decision.** On the `docker` and `kubernetes` executors the boundary is a container: the sidecar holds the credentials, and the agent's container never does. The separate OS user stays the rule for the `host` executor in a pool. A personal runner keeps one user.
**Why.** Q27 was written when many tasks shared one runner container. With a box per task, a container boundary is stronger than Unix users, and it lets the agent install packages in its own container without reaching a key. Round 14 already uses sidecar containers for services.
**Confidence:** medium. **Revisit if:** spike 3 shows the sidecar layout fails on either executor. Then the box holds one container with the runner as a different user, as Q27 first said.

### Round 8

#### Q28 · The playback
**Decision.** Yes, with two additions. Agent profiles and budgets belong to the organization. Memory exists at both levels.
**Why.** One place that owns the agent setup is the brief's third job ("Control"). The concept already shows a project choosing its defaults from what the organization offers.
**Confidence:** high. **Revisit if:** projects need profiles the organization shouldn't see. Then profiles can also live in a project.

#### Q29 · What a project contains · Changed
**Decision.** Several repos, and one task can change any of them.
- The box checks every repo of the project out side by side.
- The task uses one branch name across repos and opens one PR per repo it changed. The PRs link to each other and to the ticket.
- The task is in review while any of its PRs is open, and merged when the last one merges.
- A ticket gets at most one active code task per project.
**Why.** The maintainer's picture is a project as one computer, and the environment concept shows two repos in it. One session can then change an API and its caller together, which two linked tasks can't. Intake also stops guessing a repo, the mistake `research/landscape.md` records for Cyrus ("silently falling back to the first repo"). Linear already moves a ticket only when its last linked PR merges.
**Confidence:** medium. **Revisit if:** building several PRs per task costs more than a milestone. Then v1 ships one repo per task in behaviour, and the schema stays as it is.

#### Q30 · Above projects
**Decision.** As recommended. Organization replaces team in the glossary, ADR 0010 and the ledger. SSO comes later.
**Why.** "Team" already means something in Linear, and better-auth's own word is organization.
**Confidence:** high. **Revisit if:** never.

#### Q31 · Tasks without a ticket · Changed
**Decision.** Yes: a member prompts a project directly, and that's a task with no ticket. ostra doesn't create a ticket for it by default. A project setting turns that on, and "Create ticket" on any prompt task does it once.
**Why.** The first PR should need no tracker at all, and some projects never will (the Home concept shows "Prompts only"). Writing to the team's tracker without a person asking contradicts Q67's own rule. Teams that want a ticket for every change switch the setting on.
**Confidence:** medium. **Revisit if:** teams on Linear find that prompt tasks slip past their process.

#### Q32 · Runners
**Decision.** As recommended, with the dispatch rule made explicit.
- A task goes to one of its project's pools, by labels and free capacity.
- A member can choose their own personal runner when they start a task. It runs only their own tasks.
- An organization's provider is usable on personal runners only when an admin allows it for that provider (Q47).
**Why.** F-069 was written for a team with local and remote runners. Pools per project replace it.
**Confidence:** high. **Revisit if:** members need to share a personal runner. That's a pool.

#### Q33 · The environment as the project's computer
**Decision.** As recommended, and one per project. It holds a base image (ostra's default or the team's own), a setup script, services, check commands, and variables and secrets that each belong to one repo. Its snapshot is an OCI image on `docker` and `kubernetes`. Network rules split in two: a baseline in v1 and allowlists later (see the rounds 13–14 list).
**Why.** It's the maintainer's own framing, and the environment concept shows exactly this.
**Confidence:** high. **Revisit if:** a repo in two projects needs one shared setup. Then environments gain an "inherit from" link.

#### Q34 · Models
**Decision.** As the maintainer answered: a provider is an API base URL and a bearer token, ostra lists the models from the endpoint itself, and models.dev supplies names, logos, limits and prices. Three additions:
- "Test connection" also detects which API format the endpoint speaks, and the admin can correct it.
- v1 covers endpoints that take a static token or key header. Clouds that sign each request come later, as auth strategies of the `ModelProviderAdapter`.
- The server fetches the models.dev catalog daily and serves the logos itself. Each release bundles a copy of the catalog, and one setting turns the fetch off.
**Why.** "Any base URL works" is the maintainer's rule, so the form asks for nothing that fits only one provider. Fetching the catalog on the server keeps browsers from calling a third party, and the bundled copy keeps a closed network working (ADR 0021, ADR 0001). The half of Q34 about Claude Code is superseded by Q45.
**Confidence:** high. **Revisit if:** a team's models sit behind a cloud that only accepts signed requests.

#### Q35 · Enterprise depth in v1
**Decision.** In v1:
- two organization roles, admin and member
- projects that are open to the whole organization, or restricted to listed members
- two project roles, admin and member
- the audit log (F-073 was already v1)

SSO, SCIM, custom roles and groups come later.
**Why.** An organization with 18 projects can't have its admins edit every environment, so projects need their own admins. A small fixed matrix can be tested for every kind of record, the way F-049 already demands. Custom roles can't.
**Confidence:** medium. **Revisit if:** a team needs a read-only role before SSO arrives.

### Round 9

#### Q36 · Elastic runners
**Decision.** Answered by the maintainer: no E2B and no hosted sandbox vendor. The first recommendation of `research/elastic-sandboxes.md` is rejected. Its Kubernetes findings still inform the `kubernetes` executor.
**Why.** The maintainer's answer: people run their runners wherever they want, host them themselves, and join with a key.
**Confidence:** high. **Revisit if:** see Q8.

#### Q37 · Tasks that outlive a sandbox
**Decision.** Superseded by Q99. The rule is the same without a vendor's time limits.
**Why.** See Q42.
**Confidence:** high. **Revisit if:** never.

#### Q38 · One box per task
**Decision.** Yes, and this defines what a box is.
- A box is the agent's container (the repos and the tools, no credentials), an ostra sidecar (the credentials, both proxies, the ACP driver, the event spool) and the environment's services.
- On `docker` they share a private network. On `kubernetes` they're one pod.
- The pool runner only creates and removes boxes. Each box's sidecar connects to the server itself, with a short-lived token for that one task.
- The `host` executor has no box. The task runs in a worktree, and the runner process does the sidecar's work.
**Why.** Rounds 9 and 14 disagreed on whether the runner sits inside the box or outside it. This keeps both: one program, and the same task code in every executor, which is what makes runner parity hold. A pool runner that crashes or upgrades doesn't interrupt its tasks. Round 14 cites Buildkite's Kubernetes stack for the controller. As far as I know its pods have the same split, with an agent container beside the job's containers, but the research files don't cover that, so spike 3 is the proof.
**Confidence:** medium. **Revisit if:** spike 3 shows the layout is too slow to start or too heavy (a sidecar over 100 MB *(working value)*).

#### Q39 · The project's snapshot
**Decision.** One snapshot per project, not per repo: the base image, every repo's checkout and the result of the setup script, and never a secret. It's rebuilt when the environment changes, when a lockfile changes on a default branch, and nightly if a default branch moved. A secret marked "available during setup" is mounted for the build only, and the build fails if its value is found in the image.
**Why.** A box holds all of a project's repos (Q29), so one image is the unit. `research/elastic-sandboxes.md` lists setup scripts that need a secret as an open problem, and checking the image for the value is a rule that can be tested.
**Confidence:** medium. **Revisit if:** images for large projects take too long to pull. Then repos get layers of their own.

#### Q40 · Services for tests
**Decision.** In v1, in milestone 3. The environment has a typed list of services (image, variables, port, health check), started as sidecars of the box (Q96). The `host` executor doesn't start services. That's a declared limit of the executor, and the scheduler never sends it a task whose environment needs them. Importing a compose file comes later.
**Why.** Most real test suites need a database. A typed list can be checked and shown in the panel, as the concept does. `AGENTS.md` asks that a difference between runners is declared, so this one goes into an ADR.
**Confidence:** medium. **Revisit if:** most teams already keep a compose file and want it read directly.

#### Q41 · Who commits
**Decision.** As recommended, through the git proxy. The agent may commit. After every turn, the box commits what's left and pushes the task's branches. Commits are authored by the GitHub App's bot identity, with a co-author trailer for the member whose prompt led to them (Q55). The agent never holds a credential.
**Why.** A push after every turn keeps the branch and the PR current while a member steers. The proxy makes the push safe to run from the agent's own container.
**Confidence:** medium. **Revisit if:** pushing on every turn costs teams too much CI. Then a project can choose to push only when the box goes idle.

#### Q42 · After a turn
**Decision.** 15 minutes warm *(working value)*, then the box stops.
- Before it stops, unfinished work goes to a hidden ref and the session archive is uploaded. Both also happen after every turn.
- On `docker`, a stopped box is kept until its host needs the space, so the next turn can resume in place. On `kubernetes` the pod is deleted.
- A turn that waits on a person follows the same timer: after 15 minutes the turn is cancelled and the box stops. The "needs you" item stays open, and answering it reopens the task with the decision.
**Why.** Nobody should pay for an idle box, and a box that can vanish at any time is what makes the system simple (ADR 0006). One timer for both cases is easier to explain than two. `research/rivet.md` §4 recommends the cancel-and-resume path for long approvals.
**Confidence:** high. **Revisit if:** members complain about the wait after a pause. Then the warm time becomes a project setting.

#### Q43 · Box sizes
**Decision.** As recommended. The organization names the sizes (small 2 vCPU and 4 GB, medium 4 and 8, large 8 and 16 *(working values)*). A project picks its default. A pool caps its total and each project's share. The `host` executor counts slots only.
**Why.** A named size is a request Docker and Kubernetes both understand. The cap per project is the fairness rule from `research/elastic-sandboxes.md`.
**Confidence:** high. **Revisit if:** teams need a GPU. That's a label and a larger size.

#### Q44 · Laptop runners
**Decision.** As recommended: the same program on the `host` executor, the member's own tasks only, labelled "personal, not isolated". One addition: a pool may also use the `host` executor when an admin opts in, for machines that can't run containers for the job, such as Macs that build iOS apps.
**Why.** The runner pools concept shows a fixed pool of Mac minis, which only the `host` executor can serve. On pool hosts the agent runs as a separate OS user (Q27).
**Confidence:** medium. **Revisit if:** nobody uses pool hosts without containers. Then the option goes.

#### Q48 · Pool join tokens
**Decision.** Answered by the maintainer, without Rivet. The details are Q94. Three rules are added, because a join token is as sensitive as every secret of every project that may use the pool:
- It's shown once, stored hashed, and expires after 30 days by default *(working value)*. An admin can set another lifetime, or none.
- A pool can require an admin to approve each new runner.
- Every join is an audit entry and a notification to admins.
**Why.** A leaked token would let a stranger's runner receive a project's code and secrets. GitHub's runner registration tokens expire after an hour (`research/platform-auth-github.md` §1.7).
**Confidence:** high. **Revisit if:** expiry gets in the way of autoscaled pools. Then tokens can be bound to a cluster's identity.

### Round 10

#### Q45 · The default agent
**Decision.** Answered by the maintainer: OpenCode. I add that it's the only agent in v1.
- Its version is pinned in the base image, and ostra writes its provider and permission config for each task.
- The contract suite also runs a scripted fake ACP agent that declares what OpenCode lacks, such as steering mid-turn. That keeps the agent interface honest with one real agent.
- After v1, agents arrive one adapter at a time through the same driver: Claude Code, then Codex (ADR 0025's order), each on keys through the key proxy.
**Why.** OpenCode takes any model through a base URL, a key and a model ID, which is the maintainer's rule for models. One agent keeps the test matrix small while the platform is built. `AGENTS.md` requires adapter parity, and a fake agent with other capabilities is the cheapest way to test it.
**Confidence:** high. **Revisit if:** the acceptance run (Q46) misses its bar on two different models, or spike 2 shows an OpenCode session can't move to a fresh box.

#### Q46 · The bake-off · Changed
**Decision.** No agent-against-agent bake-off in milestone 0. It becomes an acceptance run: the same 10 realistic tickets through OpenCode, three runs each, on the model that `model.env` names, and on a second model if the endpoint offers one. The PRs are rated blind. The harness is kept, so any agent added later runs the same tickets.
**Why.**
- An Omnara arm can't change a decision. ADR 0015 rejects it as a foundation for reasons a bake-off doesn't measure: its language, its second store, and its own robustness core.
- A Claude Code arm needs an endpoint in one API family. That would tie the spike to a provider, against the maintainer's "any base URL works" (Q106).
- The default agent is already chosen (Q45). What milestone 0 still has to learn is whether OpenCode on an ordinary model produces PRs a reviewer would merge, what a task costs, and how many events it emits.
**Confidence:** medium. **Revisit if:** fewer than half the runs *(working value)* give a PR that a reviewer would merge as it is or with small edits. Then agents get compared before more is built on OpenCode.

#### Q47 · Keys everywhere
**Decision.** Yes. Every runner, a member's own laptop included, runs on provider keys through the key proxy. No subscription login is used, stored or passed on anywhere. One addition: an organization's provider is usable on personal runners only when an admin switches that on for the provider. It's off by default.
**Why.** The maintainer chose keys, and the terms forbid a platform from routing subscription logins (`research/agent-harnesses.md` §1.4). On a laptop the key proxy runs on a machine its owner fully controls, so a key sent there can be read by that member. An admin should choose that knowingly.
**Confidence:** high. **Revisit if:** members want to use their own key on their own runner. That's a small later feature.

#### Q49 · Onboarding a new project
**Decision.** As recommended, in v1 (milestone 6). The onboarding task is a code task started from a built-in template, not a fourth kind.
- It starts from the detected draft (Q2), in a box built from the base image.
- It runs the setup, the services and the checks until they pass.
- It proposes the corrected environment through an ostra MCP tool, for a project admin to accept. It writes an `AGENTS.md` as a PR if the repo has none.
**Why.** It turns the hardest part of setup, a working environment, from guesswork into something tested. It needs nothing new: the box, the MCP server that memory already requires (Q85), and the PR flow.
**Confidence:** medium. **Revisit if:** the proposals are wrong often enough that admins stop trusting them.

#### Q50 · The live agent UI
**Decision.** As recommended. The task page uses the AI SDK's `UIMessage` types as its view model, and renders them with assistant-ui's `useExternalStoreRuntime`. The stream is ostra's own tRPC SSE subscription, one per tab. `useChat`, the chat transports and `resumable-stream` aren't used. The fallback renderer is shadcn's AI Elements. **[new dependencies: `ai` for its types only, `@assistant-ui/react`, `@assistant-ui/react-markdown`]**
**Why.** The maintainer asked for the AI SDK and assistant-ui, and both are in: the message format, the tool states, the thread, the composer and the approval card. Only the transport is ostra's. `useChat` assumes one browser that posts a request and reads one response, and its resume needs Redis (`research/agent-ui-stream.md` §3). A task has many turns, many viewers and one driver, and resumes by sequence number. The AI SDK's types are never stored and never cross the runner protocol, so a new major version can't force a data migration.
**Confidence:** medium. **Revisit if:** spike 7 shows assistant-ui's churn or its `any` types cost more than they save. Then the fold stays and the renderer is swapped.

#### Q51 · Keep Rivet Sandbox Agent?
**Decision.** No. The runner drives agents with the official ACP SDK 2.x over stdio. What ADR 0024 got right stays: ACP underneath, every agent-specific import in one package, ostra's own event model, pinned versions, and a contract suite per agent. **[new dependency: `@agentclientprotocol/sdk`]**
**Why.** See Q11. Two more facts from `research/rivet.md`: its telemetry is on by default, against ADR 0021, and its "universal schema" was removed in February, so it adds no normalization over plain ACP.
**Confidence:** high. **Revisit if:** spike 1 fails on plain ACP.

#### Q52 · Steering with OpenCode · Changed
**Decision.** Steering mid-turn is a declared agent capability, as recommended. For an agent without it, such as OpenCode over ACP:
- **Send** queues the message. Everyone sees it in the thread as "queued", and it's delivered when the turn ends.
- **Interrupt and send** cancels the turn and sends the message as the next prompt.

An agent with the capability gets the message mid-turn.
**Why.** An interrupt marks the tool calls in flight as failed and can leave an install or a migration half done. So it should be a choice, never the default. `research/agent-ui-stream.md` recommends the queue, and `research/landscape.md` shows that other tools let the member choose. Spike 1 also checks whether OpenCode's own HTTP API can steer (`research/agent-harnesses.md` §2.2).
**Confidence:** medium. **Revisit if:** members interrupt most of the time. Then the default flips per profile.

#### Q53 · Reopening on another runner
**Decision.** As recommended, with two additions.
- The agent's own session archive is uploaded after every turn, because a fresh box is the normal case once boxes stop after 15 minutes (Q42).
- Step 3 uses a fixed template and no model call by ostra: the ticket, the PR's text, every member message, the agent's last message and the branch's log.
**Why.** Rivet's replay of 12,000 characters is weaker than either. OpenCode's export and import have failed a round trip before (`research/rivet.md` §5), so step 3 has to be good on its own. The brief says ostra never calls a model itself, and a template keeps that true.
**Confidence:** medium. **Revisit if:** spike 2 shows the archive can't be restored reliably. Then step 3 becomes the normal path, and F-033 says so.

### Round 11

#### Q64 · Kinds of task
**Decision.** Yes. A task has a kind: refine, code or review. The kind is in the schema from milestone 1. Two refinements:
- The lifecycle is a discriminated union per kind. Every kind has queued, preparing, running, needs you and stopped. Only code tasks have in review and merged. Refine and review tasks end in done.
- An AI review is its own task, linked to the code task it reviews, with its own box, session and profile.
**Why.** The maintainer wants one product for the whole team, and one task model keeps the box, the driver, steering and "needs you" written once. A separate review task keeps "one active session per task" true and lets the reviewer use another model. The kind goes in the first migration for ADR 0010's reason: adding it later is a rewrite.
**Confidence:** high. **Revisit if:** refine or review turns out to need different isolation from code.

#### Q65 · What to call the work before the code
**Decision.** Refine, as recommended. "Plan first" (F-063) stays a step inside a code task.
**Why.** It's the word product people already use for this work.
**Confidence:** high. **Revisit if:** the first product people to use it call it something else.

#### Q66 · What a refine task may do
**Decision.** As recommended. A refine task may read the code, answer questions about it and prototype inside its box. It can't push to a branch or open a PR, because its git proxy accepts fetches only. Its default profile is read-only, on a cheaper model that the admin picks.
**Why.** The limit is enforced by ostra, not by trusting the agent. That matters here, because a refine task's input is ticket text from anyone in the tracker (ADR 0020).
**Confidence:** high. **Revisit if:** prototypes need to be shared. That arrives with Q69.

#### Q67 · How refine ends
**Decision.** As recommended. The agent hands in its draft through an ostra MCP tool, as typed fields: description, acceptance criteria, edge cases, open questions and a split into sub-tickets. A finished draft is a "needs you" item. A member edits it, and then "Update ticket" writes it to the tracker and "Mark ready" moves the ticket to the board's ready status. The board's status mapping gains "ready".
**Why.** Typed fields can be edited one by one and checked, where free text would have to be parsed. Nothing reaches the tracker without a person, which is the right rule for text an agent wrote from untrusted input.
**Confidence:** high. **Revisit if:** a tracker can't take one of the fields. Then its adapter declares that, and the field goes into the description.

#### Q68 · Seeing the running app
**Decision.** After v1, as Q77 recommends, and first in line there. The environment then gains "how to start the app", and the base image gains a headless browser.
**Why.** It needs three things v1 already builds: services, the blob store and the review screen. So it's a short step afterwards. Until then, members attach their own images to a draft.
**Confidence:** medium. **Revisit if:** product people can't use refine without screenshots. Then it moves into milestone 6.

#### Q69 · Mockups
**Decision.** After v1, as recommended: a prototype built from the repo's real components, then screenshots. Image models come later still, through an `ImageProvider` adapter kind. In v1, members upload their own images to a draft.
**Why.** It depends on Q68.
**Confidence:** medium. **Revisit if:** Q68 moves.

#### Q70 · Who uses ostra
**Decision.** As recommended. Non-coders are ordinary members. An admin can limit an agent profile to some members.
**Why.** A new role would have to be tested for every kind of record (Q35). A list of members on a profile is one field.
**Confidence:** high. **Revisit if:** organizations want product people kept out of code tasks by rule. That's a custom role, later.

#### Q71 · AI review
**Decision.** In v1, as recommended.
- The review task runs in its own box on the PR's head, read-only, with its own profile.
- It hands in its findings through an ostra MCP tool: each one blocking or a nit, with a file and a line.
- ostra posts them to GitHub as a comment-type review with line comments. The review agent never approves and never requests changes on GitHub.
**Why.** The maintainer wants review done by the system or by a developer (round 11). A reviewer on another model, reading the diff against the ticket's acceptance criteria, is an independent check that costs no person's time. A bot that requested changes would block merging until someone dismissed it, and an approval from a bot would mean nothing.
**Confidence:** medium. **Revisit if:** findings are mostly noise. Then AI review becomes off by default per project.

#### Q72 · Fixing what the AI review finds
**Decision.** As recommended: blocking findings go back to the coding agent for at most 2 rounds *(working value)*, and nits are only listed. Together with the CI rounds (Q12), a task gets at most 4 automatic turns *(working value)* before a person has to act. Every automatic turn also stops at the task's spend cap and at the budget (Q105).
**Why.** A loop that spends money without a person needs a hard stop. Budgets are built in milestone 4 and the loops in milestone 6, in that order on purpose.
**Confidence:** medium. **Revisit if:** two rounds rarely settle anything. Then the cap drops to one.

#### Q73 · Human review in ostra
**Decision.** As recommended. A review screen shows the diff with a file tree, the ticket with its acceptance criteria, and the AI's findings inline with "Fix this". Line comments go to the agent as one prompt (F-072). The reviewer is a role on the task, taken from the PR's requested reviewers or CODEOWNERS and matched to members by their linked GitHub account. Approving and merging stay on GitHub.
**Why.** GitHub is where a person's approval counts for branch protection. ostra adds what GitHub lacks: the ticket beside the diff, and comments that turn into a prompt.
**Confidence:** medium. **Revisit if:** reviewers stay on GitHub and ignore the screen. The "changes requested" loop (Q12) already serves them there.

#### Q74 · Changing the code by hand
**Decision.** As recommended: `ostra checkout CALC-161`, or plain git, puts the task's branch on the developer's machine. When the task reopens, the agent starts from the branch as it is. F-041 (`ostra attach`) moves to later.
**Why.** A branch is the simplest shared state there is. Attach would run the agent on a laptop, and with keys everywhere (Q47) that needs a provider setup of its own. Q80's CLI already has no `attach`.
**Confidence:** high. **Revisit if:** members miss pairing with the agent in their own terminal.

#### Q75 · Reviewing PRs that people wrote
**Decision.** After v1, as recommended. The review task kind already allows a PR as its source.
**Why.** It's a new way in, not a new capability, so it can wait.
**Confidence:** high. **Revisit if:** teams ask for it before Jira.

#### Q76 · Where screenshots and files live
**Decision.** Files go through a `BlobStoreAdapter`, the eighth adapter kind.
- Its built-in adapter keeps blobs in Postgres, in chunks, with a size cap per blob (64 MiB *(working value)*).
- An adapter for any S3-compatible store is optional, and recommended above a few hundred tasks a day. **[new dependency: an S3 client such as `@aws-sdk/client-s3`]**
- Runners upload through the server, so they still need only one address.
- Copies go to the tracker as attachments where its adapter can. On GitHub, ostra links to the file. It doesn't upload it.
**Why.** A fresh install must work with only the required settings, and ADR 0017 wants one backup to cover everything. But a session archive after every turn, at 1,000 tasks, is too much to write into the same database (my own arithmetic: several megabytes each, every few minutes). `research/runner-transport.md` already plans a bulk path off the session, and `research/elastic-sandboxes.md` notes that no blob store exists yet. As far as I know, GitHub has no API for uploading an image into a PR comment. That stays to verify.
**Confidence:** medium. **Revisit if:** spike 2 shows archives are small. Then Postgres alone is enough for far longer.

#### Q77 · What ships in v1
**Decision.** As recommended, with three additions. In v1: the task kind in the schema, AI review with its fix rounds, the review screen, hand edits, and refine without screenshots. Added: the CI loop and the "changes requested" loop (Q12), and the onboarding task (Q49). After v1: seeing the running app, prototype mockups, and reviewing people's PRs.
**Why.** It's the cut that serves the whole team without building a browser into every box first.
**Confidence:** medium. **Revisit if:** milestone 6 runs long. Section 5 lists what slips first.

### Round 12

#### Q78 · The layout
**Decision.** As recommended, with two more packages and one rule.
- `packages/jobs` is the only package that imports pg-boss (Q24).
- `packages/task-view` holds the fold from events to `UIMessage`, shared by the panel and its tests (Q50).
- `adapter-sdk` holds eight base classes. Their shared plumbing (rate budgets, idempotency keys, logging) is written against small interfaces that the server implements with Postgres. So no Apache-2.0 package imports `db`.
**Why.** A package boundary is the one seam a lint rule can enforce. The plumbing in ADR 0025 needs Postgres, and the licence line in Q79 forbids the import, so it has to be injected.
**Confidence:** high. **Revisit if:** the package count slows the build. Then `jobs` folds into `domain` behind a lint rule.

#### Q79 · Enforcing the licence line
**Decision.** As recommended: every package declares its licence, and CI fails when an Apache-2.0 package depends on an AGPL-3.0 one.
**Why.** ADR 0009 only holds if a machine checks it.
**Confidence:** high. **Revisit if:** never.

#### Q80 · One CLI
**Decision.** As recommended: one Apache-2.0 `ostra` binary with `ostra runner`, `ostra login` and `ostra checkout`. The name `ostra-runner` is retired. The sidecar is the same binary in an internal mode. The npm package's name depends on which names are free. That's a check for the maintainer, since `ostra` itself is taken (`build-order.md`).
**Why.** One binary is one thing to version, sign and document. It talks to the server only through the schemas in `protocol`, which keeps it clear of the AGPL code.
**Confidence:** high. **Revisit if:** no reasonable package name is free. Then the CLI ships in the runner image and as a download.

#### Q81 · Publishing to npm
**Decision.** As recommended, with Changesets. **[new dev dependency: `@changesets/cli`]** All published packages share one version line, which is ostra's release version. Publishing starts at the v1 launch.
**Why.** Server and runner versions are tied by ADR 0022, so one version line is the simplest truth. Publishing the adapter SDK before v1 would promise a stability it doesn't have yet.
**Confidence:** high. **Revisit if:** an adapter needs to release faster than the server.

#### Q82 · The server image
**Decision.** As recommended: one image, one entrypoint, `ostra-server web`, `core` or `all`. Two more images ship beside it: the runner (the pool runner and the sidecar) and the base image for boxes (the tools, the pinned agent and a small init program).
**Why.** One server image keeps a compose install and a Kubernetes install on the same build. The base image is where an agent's version is pinned and its checksum verified, which `research/rivet.md` asks for.
**Confidence:** high. **Revisit if:** the base image grows too large. Then it splits by language.

#### Q105 · Spend limits
**Decision.** As recommended, with the mechanics added.
- A monthly budget per organization and per project. At 80%, admins are told in the panel and by mail. At 100%, new tasks and automatic rounds wait, and running tasks finish their current turn.
- Spend is counted at the key proxy: the tokens of each call, priced from models.dev, from the endpoint's own model list where it carries prices, or from a price the admin enters for a custom model.
- Each task also has a spend cap (25 USD *(working value)*), enforced by the proxy.
**Why.** The loops in Q12 and Q72 spend money without a person, so a limit has to exist before they do. An agent's own cost figure is an estimate (`research/agent-harnesses.md`, unknown 11). The proxy sees every call.
**Confidence:** medium. **Revisit if:** an endpoint reports no usage in its stream. Then that provider's spend is estimated from token counts, and the panel says so.

#### Q106 · Test accounts for the spikes
**Decision.** Answered by the maintainer, in three parts.
- **Linear:** the maintainer sets up a workspace for the tests.
- **Models:** the spikes read one neutral file, `model.env`: a base URL, a token and a model ID. No spike, test or default assumes a provider.
- **GitHub:** the spikes need a GitHub org that is used only as a sandbox. It holds the test repos and the test GitHub App, so no real repo is ever touched.

Three things remain that only the maintainer can provide: that sandbox org, a filled-in `model.env`, and a public HTTPS address for the dev server (any tunnel or reverse proxy), which spike 5 needs.
**Why.** `AGENTS.md` limits development to the test workspaces. Spikes 2, 3, 4 and 10 push branches and open PRs, so they need somewhere harmless to do it.
**Confidence:** high. **Revisit if:** never.

### Rounds 13 and 14: problems only

Both rounds were answered "yes". These are the places where they conflict with something else, or leave a hole.

**Round 13, project memory**

1. **Scopes.** Q83 has three scopes and Q92's v1 list has two. v1 has organization and project notes. Repo and path scopes come later.
2. **The question at the end of each task (Q87) costs a turn on every task.** That's tokens with no person asking, on top of the two loops. Make it a standing instruction instead: the agent calls the "propose a note" tool while it works. The extra closing turn becomes a profile option, off by default.
3. **"An MCP server in the box" (Q85) must not put an ostra credential in the agent's container.** It runs in the sidecar, with a token for that one task. The same server carries the typed tools that refine drafts, review findings, PR text and environment proposals come through. **[new dependency: `@modelcontextprotocol/sdk`]**
4. **The secret scan (Q88) is a safety rule, so it's v1.** Q92 doesn't list it on either side.
5. **Q91's research hasn't landed.** Q92's v1 cut stands until it does. If the research changes how notes are found, only the search changes.

**Round 14, runners without a vendor**

1. **What runs inside a box is undefined.** Round 9 puts the runner inside, and round 14 outside. Q38 resolves it.
2. **Build order.** Q93 builds `host` first. I build `docker` first, because the box layout decides the proxies, snapshots and services (section 1).
3. **`host` in pools.** Q93 limits it to laptops, and the concept shows a pool of Mac minis. Allowed when an admin opts in (Q44).
4. **The registry isn't optional for Kubernetes** (Q95). A `kubernetes` pool requires one, and its images are built by a rootless BuildKit pod. Spike 3 checks that.
5. **Join tokens are highly sensitive.** See Q48.
6. **The default compose file mounts the Docker socket into its runner.** That's root on that machine (Q97). It's right for a one-machine install, and the docs must say that pools belong on dedicated hosts.
7. **Identity on Kubernetes.** Q94's key pair belongs to the pool runner. Each box's sidecar gets a short-lived token for one task, tied to the task's lease.
8. **`ExecutorAdapter` runs in the runner, under Apache-2.0** (Q98). `AGENTS.md` still names `RunnerProviderAdapter`.
9. **Two runner differences need an ADR,** as `AGENTS.md` requires: the `host` executor has no services and no box sizes.
10. **Autoscaled pools.** A pool runner must accept a dispatch at once and report "waiting for a node". Otherwise the two-minute offer timeout in `research/runner-transport.md` fires while the cluster is still adding a node.
11. **Egress.** A pool that serves many projects needs a baseline: a box can't reach private address ranges, the cloud metadata address or another box (`research/elastic-sandboxes.md`, isolation rule 5). v1 ships it as a network policy on `kubernetes` and as host rules on `docker`. Allowlists per environment (F-052) stay later.

**New terms.**

| Term | Definition | Avoid |
|---|---|---|
| **Organization** | The people and settings that share one space in an ostra install: its members, projects, runner pools and model providers | team (a Linear team is something else), tenant, workspace |

**Terms that change.**

- **Team** leaves the glossary. Organization replaces it.
- **Task:** ostra's long-lived unit of work in one project. It has a kind, and it starts from a ticket or from a prompt.
- **Board:** each board belongs to one project. The ban on "project" becomes the rule in the Project row.
- **Intake rule:** an automation that turns matching tickets into tasks. "Automation" leaves its avoid list.
- **Runner:** ostra's runner program on a machine. It joins a pool, or belongs to one member, and gives each task a place to run through its executor. "Executor" leaves its avoid list. "Local" and "remote" runner become personal and pool runner.
- **Workspace:** the checkouts of a project's repos inside a task's box, on the task's branches.
- **Environment:** a project's recipe for every box: a base image, a setup script, services, checks, and variables and secrets that each belong to one repo. The panel may call it "the computer every task starts from". "Image" stays on its avoid list, because the image is its snapshot.
- **Agent profile:** belongs to the organization. A project picks a default per task kind.
- **Admin, Member:** exist at two levels, the organization and the project.

### 4.5 The domain model

**What exists.**

```
Install ── Organization ─┬─ Member (admin | member)
                         ├─ Connection (the GitHub App, the Linear app)
                         ├─ Model provider ── Model
                         ├─ Runner pool ── Runner        (a personal runner belongs to one member)
                         ├─ Agent profile
                         ├─ Memory note, Budget, Audit entry
                         └─ Project ─┬─ Project member (admin | member), when the project is restricted
                                     ├─ Repo (linked), Board
                                     ├─ Environment ── Variable or secret (per repo), Service, Check, Snapshot
                                     ├─ Automation (intake rule | schedule)
                                     ├─ Memory note, Proposal, Budget
                                     └─ Task (refine | code | review)
                                          ├─ Session ── Turn ── Event
                                          ├─ Needs-you item, Approval
                                          ├─ Task repo (branch, PR)        one per repo the task changed
                                          ├─ Box (through a lease)
                                          └─ Draft (refine) · Finding (review)
```

**Changes to make.**

1. **Organization replaces Team** as the owner of every record. Records inside a project also carry the project.
2. **Environment moves** from the repo to the project. Secrets, variables and files inside it each name one repo.
3. **Task gains a kind and a source.** The source is a ticket, a prompt or, later, a PR. "Task repo" replaces the single repo, branch and PR on the task. A review task links to the code task it reviews.
4. **A task's lifecycle becomes a discriminated union per kind.**
   - Every kind: awaiting approval, queued, preparing, running, needs you, stopped.
   - Code only: in review (with a sub-state: CI running, fixing CI, AI review, fixing findings, waiting for a reviewer) and merged, when its last PR merges.
   - Refine and review: done.
5. **A session records how it began:** resumed in the same box, restored from an archive, or rebuilt from the template.
6. **New lifecycles, each a discriminated union:**
   - **Box:** creating → preparing → ready ⇄ idle → stopped → released, or failed.
   - **Runner:** joining (possibly waiting for approval) → online ⇄ offline → draining → revoked.
   - **Snapshot:** queued → building → ready → replaced, or failed.
   - **Approval:** open → answered, answered by a rule, or closed (cancelled or expired).
   - **Proposal:** proposed → approved, rejected, or merged into another note.
7. **Events get two numbers.** The runner numbers them per session, which makes saving them idempotent. The server numbers them per task when it saves them, which is the cursor browsers resume from.
8. **Needs-you items gain an audience:** the driver, the reviewer, or the members of the project.

**Rules that always hold, revised.**

- **One organization.** No query crosses organizations. A restricted project's records are visible only to its members and the organization's admins.
- **One ticket, one active code task per project.** A ticket with sub-issues still becomes one task per sub-issue (F-077).
- **One driver,** and **one active session per task,** as before.
- **The branches are the task's.** The git proxy enforces it: only the task's sessions can push to them.
- **A box serves one task** and is never reused for another.
- **No credential in the agent's container.** Model keys and GitHub tokens stay in the sidecar.
- **Saved before acted on.** Partial text is the one thing shown without being saved, and nothing acts on it.
- **Rebuildable.** A task can always be rebuilt from its branches, its hidden ref, its session archive and its stored history.
- **Nothing reaches the tracker or memory from an agent without a person:** drafts and proposals wait for a member.
- **Nothing automatic runs without a limit:** every loop has a cap of rounds, a spend cap and a budget above it.
- **Branded IDs** now include `OrganizationId`, `ProjectId`, `PoolId`, `BoxId`, `ProviderId` and `NoteId`.

## 5. The v1 cut

### How I balanced ambition and shipping

The maintainer pushed back on shrinking the product, and they were right about what was being lost: the shape. So three rules decide the cut.

1. **Every noun in the maintainer's picture exists in v1,** and is in the first migration where it shapes the data: organization, project, environment, pool, provider, the task kinds, repos per task. Adding a noun later is a rewrite.
2. **Each noun gets the least depth that works:** one tracker, one code host, one agent, password sign-in, two roles per level, one catalog. The exception is executors, where all three were already answered "yes". Adding depth later is one adapter or one setting.
3. **Anything that spends money or widens access ships with its limit:** loops with caps and budgets, pools with join-token rules, boxes with the egress baseline.

A fourth rule keeps it honest: **the team uses it early.** From milestone 3, ostra's own tickets run through ostra, long before the launch.

This is a large v1, about 104 ledger rows against 67. It's shippable because the depth is thin and because nothing in it is a research project: each hard part has a spike with a pass bar and a named fallback (section 6).

### In v1

- **The organization:** many organizations per install, accounts with username or email and a password, invite and reset links, two organization roles, the audit log, search, budgets and Insights.
- **Projects:** several repos, boards from Linear or none at all, open or restricted access, two project roles.
- **The environment:** detection, a setup script, variables and secrets per repo, services, checks, snapshots, and the onboarding task that tests it.
- **Models:** any endpoint with a base URL and a token, in either API format, with the models.dev catalog. Keys never reach the agent, and every call is counted.

- **Tasks:** from a ticket, a prompt, an intake rule, a schedule, Linear's agent mode, or `@ostra` on a PR. Three kinds. Live activity for many viewers, one driver, take over, stop, reopen on any box months later.
